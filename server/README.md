# server

[skyblip.eu](https://skyblip.eu) runs as one Rails app on the crooz server. Public content lives under `Content`, and `/briefing` is the app a pilot installs to activate, set up and update a device, beside the Bluetooth console and the editable simulator. Users sign in to an admin area, and `/briefing/activate` gives each unit its serial (#126).

Every command here runs from this directory, not from the repo root.

## Running it

```sh
mise trust && mise install   # Ruby, and fnox
bin/setup                    # gems, the databases, then bin/dev
bin/dev                      # http://skyblip.localhost:8119
bin/ci                       # the gate before handoff, the checks CI runs as separate jobs
bin/rails test:system        # Cuprite, on the Chrome or Chromium it finds, BROWSER_PATH otherwise
bin/screenshots              # retake the device screens off the firmware next door
```

Rails 8.1 on Ruby 4, SQLite with Solid Cache, Queue and Cable, Hotwire over Propshaft and Importmap, Minitest with Cuprite for system tests and VCR for GitHub, Kamal to deploy ([DEPLOYMENT.md](DEPLOYMENT.md)).

Tests that reach GitHub replay a cassette from `test/vcr_cassettes/github/`, system tests included: the app server runs in the test process, so the cassette a test inserts answers the request a Turbo Frame makes. `CASSETTES_RECORD=1` records them again against the real API.

## Credentials

The credentials keys live in Bitwarden, in the secure note `skyblip-repository`, which [fnox](https://fnox.jdx.dev) reads through the `bw` CLI as `fnox.toml` maps it. It is named after the repository rather than `skyblip` alone because `bw` finds an item by searching names, usernames and URLs, and a login for the site would match too.

- `config/master.key` decrypts the development credentials, `config/credentials.yml.enc`, and stays on disk. The dotfiles bootstrap writes it from the note's `RAILS_DEVELOPMENT_KEY`, mode 600. A worktree has none, so `bin/setup --skip-server`, run once inside one made by `git wt`, links it from the main checkout.
- The production key never touches the disk. It is the note's `RAILS_PRODUCTION_KEY`, which `mise.toml` grants to two tasks only, as `RAILS_MASTER_KEY`, the name Rails and Kamal read: `mise run kamal ...` and `mise run credentials:production`. Rails reads `RAILS_MASTER_KEY` before any key file, whatever the environment, so it must never reach a development command, and nothing else sees it: not the shell, `mise env`, the shims, or an agent. The tasks' output shows it as `[redacted]`, except the credentials editor, which needs the terminal.

The production credentials do not exist yet. To create them, add `RAILS_PRODUCTION_KEY` to the note, 32 hexadecimal characters as `ruby -rsecurerandom -e 'puts SecureRandom.hex(16)'` prints them, then run `mise run credentials:production`: Rails finds the key in the environment, writes no key file, and creates `config/credentials/production.yml.enc` with a `secret_key_base`. Commit that file, and give the same key to the GitHub `server_production` environment as `RAILS_MASTER_KEY`.

## Admin and analytics

A user has a first name, a last name, an email and a password, and a role: `user` or `admin`. Nothing links to the sign-in page, `/session/new`, which robots are asked not to index. Once signed in, an admin finds `Admin` in the site nav, which opens the admin area: analytics, insights, errors, events, the users, the units, the coding agents connected to the MCP server, and Mission Control's jobs at `/admin/jobs`, which open in a window of their own named `mission_control`. Every admin controller inherits `Admin::ApplicationController`, which answers `403` to anyone but an admin, the way Fizzy guards its own, and Mission Control is mounted on it too. There is no sign-up and no password reset: an admin creates the accounts and sets their passwords. The first admin is created in the production console, `mise run kamal console`:

```ruby
User.create!(first_name: "[first name]", last_name: "[last name]", email: "[email]", password: "[password]", role: :admin)
```

Ahoy records visits and events in their own database, `analytics`, from the server (every controller action) and from the browser (`app/javascript/ahoy-module.js`, posting to `/hoy`). Each visit is then computed into an `Analytics::Visit`, which knows its pages, duration, channel, section (`public`, `briefing` or `admin`) and segment. The segment is how your own browsing stays out of the numbers: a visit is `internal` when it belongs to an admin, or comes from a browser an admin once signed in from, `user` for any other account, `non_user` otherwise. The `Admin` link opens the overview on `non_user`. Development and test track nothing, `Ahoy.api_only` is on there. Firmware downloads are not tracked, so their year-long public cache never carries a cookie.

A click on a link or a button is a `$click` event with the link's address, words and page, and a middle click counts too, which `ahoy-module.js` records from `auxclick`. A click on a link to another site is outbound (`Ahoy::Event.outbound_clicks`), the affiliate links of the buy and mount pages among them. A link sits in the `data-section` of the closest element that has one, which Ahoy records as `section`: each row of the buy page's offers names its product, `go`, `go-plus` or `bravo`, so a click on a price says what it buys. The overview lists the outbound links with their visitors, clicks and conversion, as Plausible lists its outbound link goal, and a link filters the overview and the visitors to the visits that clicked it (`Analytics::OutboundClicks`, the `outbound` filter). An agent reads the same through `list_outbound_clicks`. A link opened from a long press or the context menu fires no event and goes uncounted.

An activation the server accepts is a `unit_activated` event on the visit of the browser that asked, with the unit's id, its device slug and the briefing's support code from the `X-Briefing-Browser` header. That one event ties the analytics to the briefing: the overview counts the visitors who activated, the `activation` filter keeps their visits, a visitor's page lists the units it activated with links to each unit and to its support code's events, and a unit's page links the visitors that activated it. Before `unit_activated`, an activation showed only as `registrations#create`, which `Ahoy::Event.activations` still counts but which names no unit. A refused activation is not tracked, and a pilot who browses on a computer and activates from a phone is two visitors.

A coding agent connected to the MCP server reads the analytics as the admin does: `get_analytics` for the overview, `list_visitors` and `get_visitor` for the visitors and one visitor's timeline, and `list_outbound_clicks` for the links out. They take the overview's filters by the same names, `segment` is `non_user` unless an agent asks for another or `all`, and the period is the last 30 days unless it gives `days` or `start_on` and `end_on`. `AnalyticsTool` holds the filters they share, and each read is logged as `analytics.listed`.

The site follows the CNIL's terms for audience measurement without consent ([Cookies : solutions pour les outils de mesure d'audience](https://www.cnil.fr/fr/cookies-solutions-pour-les-outils-de-mesure-daudience)): a tracker lives 13 months, and what it collects is kept 25 months at most. The two periods are `config.x.tracker_lifetime` and `config.x.retention`, and every tracker and every log in the app keeps to them. `Ahoy::Visit.prune` deletes visits older than 25 months every night, with their events and what was computed of them.

A visit keeps no IP. `Ahoy::Store#track_visit` places it in memory, while the request runs, with the MaxMind GeoLite City database, `storage/GeoLite2-City.mmdb`, then drops it, and keeps the user agent Ahoy reads the browser, the system and the device type from. No job carries the IP to a queue. The database comes from `Maxmind::UpdateGeoliteCityDatabaseJob` downloads and keeps current. The job is scheduled in `config/recurring.yml` only once the production credentials hold the MaxMind account, so until then visits keep no place and nothing fails:

```yaml
maxmind:
  account_id: [account id]
  license_key: [license key]
```

`mise run credentials:production` adds them. The first nightly run after the next deploy downloads the database.

## Addresses

The database keeps no IP address but an admin's session. A visit keeps its user agent and the city its IP was placed in while the request ran (Analytics above). Rails' `rate_limit` counts requests in Solid Cache under a key that holds the client's IP, or its network for activation and attestation, as Rails does by default, and the counter expires with its window. The activation's network cap counts the same way: `Unit.enrollments_from` increments a cache counter per network that lives 24 hours from the network's first new unit, so a unit keeps no trace of where it enrolled from. A cache that loses the counter, by eviction or a clear, forgets the network's enrollments, as it would a rate limit's. An admin's session keeps the IP and the user agent it signed in with, as Rails' authentication generator writes them. Rails logs each request with its IP, and so does kamal-proxy, outside the app.

## Events, errors and the MCP server

Everything that happens on the site and in the briefing app is an event in a SQLite database of its own, `events`: the server's requests, jobs, activations and errors, through `Rails.event` and `Rails.error`, and each browser's journal, which `app/javascript/skyblip/journal.js` keeps in `localStorage` and posts to `/events` until the server takes it, so a phone offline at the airfield loses nothing. A pilot's journal carries a support code, eight letters shown under Settings and beside a failed install, by which an admin reads that pilot's story. The errors of the server and of every page's scripts are grouped by fingerprint into errors an admin resolves and that reopen when they happen again, which does the job of an error tracker such as Sentry, except for alerts. [`app/models/event/README.md`](app/models/event/README.md) says what is recorded, what is kept out, and how to read it.

Admins read it under `Insights`, `Errors` and `Events` in the admin area, and a unit's page links its timeline. A coding agent reads the same through the admin MCP server at `/admin/mcp`, which an admin connects with OAuth and a client metadata document: [`app/models/oauth/README.md`](app/models/oauth/README.md). From a laptop that deploys, `mise run kamal app exec "bin/rails events:review DAYS=30"` prints the numbers, and `events:tail DEVICE=go-00012a` or `CODE=ABCD-EFGH` a pilot's events.

## Activation

A unit transmits nothing until it holds a serial that this server signed for it, and `/briefing/activate` is where it gets one: the glass prints `skyblip.eu/activate`, which redirects there. The wire protocol is the activation frames of [`schemas/link.v1.json`](../schemas/link.v1.json) on the unit's half and [`schemas/activation.v1.schema.json`](../schemas/activation.v1.schema.json) on the server's: the page asks the unit for a nonce, `POST /activation/challenges` signs it, the unit asks on its glass and signs its registration with its own key, `POST /activation/registrations` checks that signature and answers the serial with an unlock code, and the unit stores the code. [`activation.v1.vectors.json`](../schemas/activation.v1.vectors.json) is one exchange signed with the public test key, which `test/models/identity/message_test.rb` holds OpenSSL to and the firmware's host suite holds Monocypher to: Ed25519 is deterministic, so two libraries that sign the vectors alike sign everything alike.

`Unit` is a DEVICEID, any product's, and once activated its serial, dense from 1 to 65535 (0 would put 0x000000 on the air, which decoders read as no address), and `Unit::Key` the public keys it registered with, `active`, `pending` or `revoked`. A unit with a serial is one that transmits on ADS-L, `Unit.activated`, the list an authority asks for. A DEVICEID with no serial yet, new or already recorded from a browser's report, gets the next serial at its first registration, with `activated_at`, and its key is bound. The same key gets the same serial in a fresh unlock code. Another key is refused as `other_key` and kept as `pending`, with the date and the firmware it came with. A unit keeps its five newest pending keys and forgets older ones, since anyone can sign a fresh key for a DEVICEID the server knows. In the admin area, `Units` lists them: promote makes a pending key the active one and revokes the old, revoke leaves the unit with no key, so the next registration binds its key as a first one does. A revoked key stays revoked: it is refused as `revoked_key`, and the page shows the DEVICEID and the start of the key, which is what an owner writes in with and what the `Units` page lists. A key registered under two DEVICEIDs is a key reused by a script or custom firmware, or an RNG that failed, since this firmware never lets a copied key slot be a key on another chip: the server binds it to each, and `Units` counts the units that share it in a banner, names the first ten, and lists them beside the key. The unlock code is signed inside the transaction that bound the key, so a revocation lands before it or after it. `Activation::Challenge` is the server nonce, kept five minutes, used once, and forgotten hourly by `config/recurring.yml`.

Both endpoints take ten requests a minute per network (`rate_limit`, on Solid Cache). Past the daily cap, 50 units activated in a UTC day until an admin changes it under `Units` (`Activation::Cap`), a DEVICEID with no serial is refused as `daily_cap`, and past 5 new units in 24 hours from one network, an IPv4 address or an IPv6 /56, the block a home line holds, as `network_cap`, so one client cannot spend the whole day's cap. A private, loopback or link-local address counts toward no network and logs an error, because Docker on crooz hands Rails its gateway, 172.18.0.1, for every IPv6 client until #205 is fixed. The enrollment that reaches the daily cap logs an error, and the admin `Units` page carries a banner until midnight UTC: the app has no mailer to alert by, so those two are the alert. Every refusal is also an `activation.refused` event with its reason, which Insights counts. The network cap neither logs nor shows a banner, since one network reaching it is the cap working. The daily cap is there because anyone can make up a DEVICEID and a key, and a serial is given for good, so a script spread over many networks could otherwise spend all 65535 in a day. Insights compares it with the busiest day of the period and advises raising it to three times that day once it covers less than twice it (`Event::Review#daily_cap`). A server nonce is spent only by a registration its unit signed, since it travels in clear over Bluetooth.

Only skyblip.eu signs for a unit. It holds one Ed25519 key, the server key, which signs every message a unit must trust from it about its identity: the challenge and the unlock code today, any later command that touches identity tomorrow, each under its own `skyblip:<purpose>:v1` label (`Identity::Message`). Every device build, a pull request, `main`, a release or a local build, carries only its public half, `firmware/keys/server.pub`, so a build needs no secret to be activated. The seed, 64 hexadecimal characters, lives in the production credentials alone:

```yaml
identity:
  server_private_key: [seed]
```

The name says private because this is the one place the secret half sits, beside values that are not secret; its public half is `server.pub` in the firmware, and the server key, unqualified, is the pair. `openssl rand -hex 32` makes a seed: in Ed25519 the 32 random bytes are the private key. Add it with `mise run credentials:production`. `Identity::ServerKey` derives the public key from it, and names it by the first four bytes of the SHA-256 of that public key, which is how the unit names the key it trusts in its `challenge` reply. The admin `Units` page shows both, to check against `firmware/keys/server.pub`. To get the public half before a deploy, in your own terminal:

```sh
read -rs seed && ruby -ropenssl -e 'k = OpenSSL::PKey.new_raw_private_key("ED25519", [ARGV[0]].pack("H*")).raw_public_key; puts k.unpack1("H*"), OpenSSL::Digest::SHA256.digest(k)[0, 4].unpack1("H*")' "$seed"; unset seed
```

Development and test sign with the public test key of the vectors (`config/initializers/identity.rb`), which only the firmware's host suite and simulator trust, so a local server can never activate a real unit, nor hand one a serial the registry gave another. With no key at all, the activation endpoints fail with an error and the `Units` page says so.

The registration also says whether the unit runs a release build, signed with the rest, and the `Units` page shows it as the build, release or development. Nothing on the air tells them apart: a development unit is a real aircraft with a real serial.

### The firmware each unit runs

The server keeps which firmware each unit runs on the unit's own word, so the firmware the fleet runs, and the ADS-L version each release carries, rests on the units' signatures rather than on what a browser says. The registration is the first statement: its signature covers the version, so an active key's registration records it. After that, on every connection of an activated unit to the briefing app, the page asks `POST /attestation/challenges` for a nonce, sends it to the unit as `attest`, and posts the unit's signed `attestation` frame to `POST /attestation/statements` (`firmware/core/comms/README.md`, Attestation). The signature covers the product and the variant beside the version and the build, so the variant the unit found at boot, a Go+ or a Go, is on its own word too. `Attestation::Statement` checks the signature against the unit's active key, spends the nonce and calls `Unit#attest_firmware`, which records the product and the variant on the unit. `Unit::Firmware` holds one row per stretch on one version, build and variant: the same firmware signed again moves its row's `updated_at`, and another one, a return to an earlier one, or another variant, opens a row. The registration signs no product nor variant, so the row it opens names none until a read or an attestation fills it. Each is a `unit.firmware_attested` event, and each refusal an `attestation.refused`. `Attestation::Challenge` is kept five minutes and used once, as the activation's nonce is, and both endpoints take twenty requests a minute per network. Neither request carries the support code, and neither table keeps an address, so the record ties a version to a unit and to no pilot or browser.

### Every unit a browser meets

Every unit names itself on every connection, a Bravo and a Go not yet activated included: the page asks its `identity` frame, the product, the variant, the firmware version and build, the DEVICEID and the Bluetooth tag (`firmware/core/comms/README.md`, Identity), and journals them in `device.read`. `Event::Journal` hands the uuids of the entries it kept for the first time to `Unit.hear_later`, a job (`Unit::HearingJob`) that runs one at a time, so two journals naming the same new unit cannot both create it, and a failure stays in the queue to retry rather than losing the reads. `Unit.hear_now` (`Unit::Reporting`) checks each entry's fields as `Unit::Report` and records the unit by its DEVICEID, so a unit exists on the server from its first connection and never before. A unit first heard gets no serial. One network records at most 20 new units a day, counted in the cache as the activation's network cap is, and a known unit is heard from anywhere. A browser sets the product, the variant and the tag of a unit that is not activated, and only with an entry newer than the last one heard, since a journal can arrive up to 30 days late. An activated unit signs its product and variant in its attestation on every connection, so no browser changes them. A unit read or signed on another variant than the last, such as a Go+ whose haptic driver stopped answering, is a `unit.variant_changed` event that names its source.

`Unit::Firmware` keeps the firmware for good, after the events are pruned: one row per stretch on one version, build and variant, which the read opens or extends. Its `source` only gains trust: `read`, a browser's report that nobody vouches for, `installed` once `device.installed` says the unit came back on the version the app sent, with the version it left and how long the install took, still a browser's word, and `attested` once the unit signs it. A source fills the variant of a row only when it ranks at least as high as the row's, and a statement that names no variant, a registration, opens its own row over one whose variant only a browser named. A firmware installed outside the app, such as a `.uf2` dropped over USB, shows from the next connection on as `read`. Firmware built before the identity frame names no DEVICEID, so its unit is recorded only once it is activated.

The `Units` list shows every unit, newest seen first, with its product and its variant read apart, its newest firmware and that firmware's source, or the version it registered with until it has one, and filters the activated ones. A unit page lists the stretches newest first. Both pages open on a help, `admin/units/_help.html.erb`, that says what each column means. It also says why the rows record neither a full nor a base image: both carry the same firmware at the same version, a full one adds the motion sensor's firmware, and what the hub holds is the unit's state, which the briefing app reads on every connection and offers to fix (`app/javascript/skyblip/README.md`). Both reach a coding agent through `get_unit`, which finds a unit by its slug: `go-00012a` by its serial, `activate-3f2a` and `bravo-3f2a` by their tag, which can name several units.

## Content

Pages are files, not database rows: `content/pages/<slug>.html.erb`, with YAML frontmatter for `title`, `nav_title`, `description` and an optional localized `slug`. A page is bilingual by convention, `<slug>.html.erb` and `<slug>.fr.html.erb`, and the locale switcher offers a language only where the twin exists.

The `title` is what a search result shows, followed by ` · skyBlip` unless it already names skyBlip, and it labels the links `link_to_page` draws without a label. Keep the rendered title within 60 characters and the `description` within 155: `test/integration/content/meta_test.rb` fails past either. Write French metadata with its own typography, a no-break space before `:` and `€`, as characters rather than entities, since the meta tags escape them. Every page also carries `updated_on`, quoted as `"2026-11-09"` because the frontmatter parser refuses YAML dates. Set it to the day of the change whenever the page changes significantly: its main content, its links, or what its head tells a search engine, such as the title, the description or the structured data. A typo or a style fix does not count. It is the sitemap's `lastmod`, taken from the file rather than from git, because CI checks out one commit and a page's commit date is not known until the sitemap is committed with it. The optional keys feed the structured data that `StructuredDataHelper` renders as JSON-LD: `published_on` makes a page an `Article`, `parent` names the page a `BreadcrumbList` passes through (the guides name `guides`), and `product` marks up a `Product` with the lowest price the site shows. `features`, the Go, and `skyblip-bravo` have one. Tango has none: it pairs a Go priced in euros with an X1 priced in dollars, and a `Product` takes one currency. A page that answers questions puts each in a `<details>` inside a `.faq` container, its `<summary>` the question and what follows the answer, and `StructuredDataHelper` reads them from the rendered page into an `FAQPage`. A `.faq` with no `<details>`, such as the parts lists on `mount`, stays out of it.

`Content::Page` reads the collection, and the content route accepts only existing localized slugs, leaving application routes separate. Every published page is listed in the sitemap, whether another page links to it or not. Run `bin/rails content:sitemap:generate` after changing the collection. `bin/rails content:sitemap:check` and the test suite catch drift. Canonical URLs always use `config.x.public_url`, not the incoming request host.

Every page also answers in Markdown, for coding agents, following Evil Martians' [Making your site visible to LLMs](https://evilmartians.com/chronicles/how-to-make-your-website-visible-to-llms). It answers at its address with `.md`, as `/radar.md` or `/fr/a-propos.md`, and `/index.md` and `/fr/index.md` for the homes. It also answers at its own address to a request whose `Accept` names `text/markdown` at least as high as HTML (`Content::Negotiation`), which Claude Code and Cursor send and a browser never does. `Content::Page#to_markdown` renders the page's HTML, and `Content::Markdown` converts it with reverse_markdown. The conversion drops the controls, the drawings and the frames, keeps the promo code its button shows, and names each country's offers on Buy. It makes every link absolute, and a link to a page leads to that page's Markdown. The HTML points at its Markdown with a `<link rel="alternate" type="text/markdown">` and a `Link` header, and the Markdown names the HTML as canonical in its own `Link` header, so search engines index the HTML alone. A Markdown request for no page gets a Markdown 404 that links the `llms.txt` of its language. Write a page so its text reads right without its controls and scripts, since the Markdown and the chat assistants that read the HTML both see it that way.

`/llms.txt` lists the English pages by section, each with its frontmatter description, and every page's footer links the one of its language. Each language has its own, `/fr/llms.txt` and the others, which lists a page not translated yet in English, as the ADS-L pages are (`Content::Page.read_in`). Its guides, ADS-L and blog sections take every page under `guides`, `ads-l` and `blog`, and a new top-level page goes into its section in `app/views/content/llms/show.text.erb` by hand. `/llms-full.txt` and `/fr/llms-full.txt` hold every page of their language but the legal notice in one file, cached per language and deployed revision. `/feed.atom` and `/fr/feed.atom` list the same pages in Atom, latest `updated_on` first, with each page's description and a link to its Markdown, and every page's head links the feed of its language. `robots.txt` carries Cloudflare's `Content-Signal` and allows search, AI answers and training, so assistants can cite the site and models learn about skyBlip.

The public MCP server at `/mcp` serves the same pages to an agent or a chat connector with no account, so Claude or ChatGPT can answer a pilot from the site. `list_pages` lists a language's pages, `search_pages` ranks them against the words of a question (`Content::Search`), and `get_page` reads one in Markdown. `Content::Search` weighs each word by how few pages hold it, folds accents, and keeps each page folded for the life of the process, as `Content::Page#markdown` keeps its Markdown. The server is stateless, writes nothing and allows 300 requests a minute per address. Each call is logged as `mcp.answered` with the path `/mcp`, and `get_insights` counts them under `connectors`, apart from the admins' agents. A client that knows only the domain finds the server through `/.well-known/ai-catalog.json`, an [AI Catalog](https://ai-catalog.io/) 0.9 whose one entry points at the server's card at `/mcp/server-card`, an [MCP Server Card](https://github.com/modelcontextprotocol/experimental-ext-server-card) (SEP-2127). The card's name, version, title and description are `McpsController`'s constants, which the server also answers `initialize` with, and its test validates it against the schema in `test/fixtures/files/mcp/`. Bump `McpsController::VERSION` when a tool changes. The admin server stays out of the catalog.

Visitors try the radar, choose a device, buy the hardware, install the software and check it before flying. The nav links to Try it (`skyblip-go`, served as `/try`), Devices (`features`, served as `/go`), Buy (`buy`), Install (`install`, served as `/install` and `/fr/installer`) and Guides (`guides`). Briefing stays in the utility links. The footer groups links by choosing, using and learning about the project. `index` introduces the three configurations and loads the live simulator in a lazy Turbo frame. Try it gives the same simulator its own page and a guided exercise. Go, Bravo (`skyblip-bravo`) and Tango (`skyblip-tango`) use `shared/_device_tabs.html.erb` and keep their own metadata. `buy` holds the hardware comparison and seller links. It sends visitors to Install, which links to Briefing setup and covers manual installation. `guides` starts with the first steps for Go and Bravo, which Briefing links after setup. It then indexes `radar`, `instruments`, `displays`, `controls`, `power` and `phone` for using the Go, and `radio`, `timing`, `gps` and `traffic` for how it works. `index` opens on the cases a pilot recognises, a club fleet, a borrowed aircraft or a small cockpit, and closes on its questions and on cards to the guides, the blog and `compare`. Go, Bravo and Tango each end on the questions pilots asked about that device on the forums. `blog` lists longer answers to those questions, each a page under `blog/` that names `parent: blog` and a `published_on`, and that cites its sources. `compare` sets Go and Tango beside other devices, portable and installed, with the prices their sellers showed on the date it gives. `about` states the project's purpose and pledge. `roadmap` covers projects not yet available.

Build pages with a centred `page-hero` and alternating `band` and `band--tint` sections, each opened by a `section-title` (`sections.css`). The Tango diagram is `shared/_tango.html.erb`, drawn in SVG from the colour and type tokens. Each Go feature links to the relevant section of the guide that explains it. Put layout labels and shared diagram text in `config/locales/`.

Go and Go+ run on a LilyGO T-Echo and T-Echo Plus. Bravo runs on a Seeed SenseCAP MeshTracker X1. A Go paired with a Bravo makes a Tango. Bravo and Go firmware are published as development builds. Purchase buttons have no firmware note. Every affiliate link carries `rel="sponsored"` with its disclosure nearby. The X1 offer shows the struck price without the code, the price with code `5GO3A5DD` and shipping to France. Write MeshTracker X1 in a hero, card, note or order link, and the X1 in running text. Use the full name in body text away from these places and in alt text.

The legal notice (`legal-notice.*`, `/fr/mentions-legales`) names the hosting provider only, as article 1-1 II of the [LCEN](https://www.legifrance.gouv.fr/loda/id/JORFTEXT000000801164) allows a site published non-professionally, provided the host holds the publisher's identity. It reads the host from the credentials, not from the source, added to production with `mise run credentials:production`. Development has them already. Without them, as in CI, which has no key, the fields render empty:

```yaml
legal:
  host: [hosting provider]
  host_address: [hosting provider address]
```

A link shared on WhatsApp, a forum or a mailing list shows the page's share image, a 1200x630 JPEG under `content_images/share/`: `go` by default, or the card a page names in `share_image` (`radar`, `bravo`, `tango`). The cards are drawn from the site's own wordmark, photos, screens, tokens and fonts by `bin/rails content:share_images:generate`, which renders `lib/share_images/card.html.erb` in Chrome through Ferrum, a test gem, so it runs where the test bundle is installed. Bravo shows Seeed's X1 photo, as the Bravo page does, and Tango shows the Go and the X1 side by side. The device name and the device sit inside the centred 630x630 square, the crop WhatsApp and Slack show in a compact preview. Its alt text lives in `config/locales/` under `share.images`. Run the task again after changing a card or anything it draws from.

The ADS-L declaration of conformity for skyBlip Go is the `ads-l/conformity` page's declaration section, and a one-page A4 PDF to sign. `bin/rails content:adsl_declaration:generate` prints `lib/adsl_declaration/declaration.html.erb` to `content_images/pages/ads-l/skyblip-go-ads-l-declaration.pdf` in Chrome, the same way as the share cards. The declaration itself is one partial, `app/views/shared/_adsl_declaration.html.erb`, which the page and the PDF both render. It keeps the wording of the appendix to ADS-L 4 SRD-860 Issue 2 and fills its fields. The PDF is not committed: run the task when the declaration is to be signed.

Images live in `content_images/pages/<slug>/` and are drawn with `pages_image_tag`, or `content_image_tag` with the full path, which read the file's width and height so the page keeps its layout while the image loads. The device screens under `pages/skyblip-go/` are drawn with `screen_image_tag` from whichever page shows them, and they are not artwork: each is the 200x200 framebuffer of the WASM simulator, driven to that state and read out of `simulator_panel()`, so a page that changes on the device is a capture that has to be taken again. They are stored at 200x200 in two colours and scaled by an integer factor on the page (`features.css`), because any other factor resamples a panel pixel.

Every other image, a photo or an app screenshot, is AVIF, encoded by libvips from a lossless source: `vips heifsave in.png out.avif --Q 75 --compression av1 --effort 4 --strip --subsample-mode auto` for a photo, `--Q 70 --subsample-mode off` for a screenshot, whose text loses its edges to chroma subsampling. Where libvips is not installed, `ffmpeg -i in.png -c:v libaom-av1 -still-picture 1 -crf 30 -cpu-used 4 -pix_fmt yuv420p -map_metadata -1 out.avif` encodes a photo the same way. The X1 photo under `pages/skyblip-bravo/` is Seeed Studio's product shot, cropped to the device and credited where it is shown large, until our own photos replace it. Rails registers no AVIF type, so `config/initializers/mime_types.rb` does, or the dev server sends the files without a Content-Type.

A device's controls are marked on its photo by `shared/_device.html.erb`, an SVG that draws the photo with an arrow or a ring on each contact a page names and the word for it, and its LED colour beside it. `DevicesHelper` holds where each contact sits on the photo. The first-steps guides, Briefing's setup page and Bravo's prompts all draw from it. RESET and the button sit on the left side of the T-Echo and of the T-Echo Plus, out of view in the Go's photo, so their arrows point at that edge: RESET is the upper one and the button the lower (`../firmware/boards/lilygo/t_echo_plus/factory/README.md`). The X1's LED sits just above its button and is ringed there, with its colour drawn beside the photo (`../firmware/boards/seeed/meshtracker_x1/README.md`).

The legend under `pages/skyblip-go/blips/` is the other half of the same rule: one PNG per traffic blip, each drawn on its own 19x25 canvas by `ui::draw_blip`, the widget the radar page itself calls, so the table on the page cannot drift from the glass. `bin/blips.cpp` is that dumper, a host binary linked against `ui/canvas.cpp` and `ui/widgets/blip.cpp` and nothing else.

Taking them again is `bin/screenshots`: it builds the firmware's WASM, flies one device per scene, compiles the dumper, and writes the PNGs over the ones in the tree. A scene names the page, the menu and the alarm level it expects and the script stops on the first one that does not hold, because a capture of the wrong glass is worse than a stale one. The page ids and the menu rows are read out of `pages/page.h` and `pages/menu.cpp` rather than copied into the script, so a scene opens `NEARBY_MENU.SelfTest` by name: the copy that used to sit here went stale when a page was inserted, the self-test scene opened the row below and the check passed on the wrong glass. The scenes are the file: to change what a screen shows, change the sky it is flown in. The radar is captured both ways for `displays`, a `-to-scale` shot beside the one of the same sky on `ALL`, which is what a fresh device boots on, so every other radar capture is `ALL` too. `PLOT` is pressed through the menu like any other row. Node runs the same `skyblip-simulator-embed.js` a browser does, so the only thing it hands Emscripten is `instantiateWasm`, which is how the module is loaded off the disk rather than fetched.

Running it takes the Emscripten version `.github/pins/action.yml` pins, which Dependabot updates, and `make browser` installs it: when the `emcc` on your `PATH` runs another version, it clones or pulls emsdk in `$EMSDK`, else `~/.local/opt/emsdk`, installs and activates the pin there, and builds with that `emcc` (`scripts/emsdk.rb`). The first build after a bump downloads the release, about 1.7 GB installed, and recompiles every file. The firmware workflow runs it on every firmware change and fails when a picture in the tree differs from the one the firmware draws, so a change to the glass carries its pictures.

The briefing's prompt is drawn the same way: `briefing/_glass.html.erb` is a canvas, and `glass_controller.js` paints the Go's confirm page into it with the simulator's `paintPrompt` (`../firmware/simulator/README.md`). `/briefing/prompt_glass` sends the browser to the simulator embed it is drawn with: in development and test the one `make -C firmware browser` built, served as release `local` from `config.x.simulator_build`, and in production the release the simulator page runs. A release older than the export shows the title alone. The canvas is labelled with the page's words, which the firmware hands back with the pixels, so a screen reader hears the prompt as the glass shows it. The system tests read the glass by that label, and test runs only ever use the local build, so the server workflow restores it from a cache keyed on the firmware's sources and builds it only when they changed. The WASM is 544 KB and 234 KB gzipped, which Thruster sends compressed. The browser fetches it the first time a prompt shows, and keeps it for a year.

Look and layout come from the token sets in `app/assets/stylesheets/`. Colors, spacing and type are CSS variables in `_global.css`; components never hardcode a value.

Every page links the stylesheets at the top of `app/assets/stylesheets/`, one `<link>` per file (`site_stylesheet_link_tags`), and nothing else, so a file added there reaches every page. An area's stylesheets live in a subdirectory and reach only the pages that ask for them with `<% content_for :stylesheets, area_stylesheet_link_tags("simulator") %>`: `admin` for the admin layout and the sign-in page, `briefing` for every page under `/briefing` (its layout links it), `simulator` for `/try` and the briefing simulator, `workbench` for the briefing simulator and console, and `ownship` for the ownship editor. The frames those pages load, `/briefing/firmwares` and `/briefing/simulator_build`, ask for the same areas, so they render styled when opened on their own. Propshaft's `stylesheet_link_tag :app` takes every file under `app/assets`, subdirectories included, which is why the layout lists the top level itself. An area's links carry `data-turbo-track="dynamic"`, so Turbo adds them on the way into the area and removes them on the way out instead of reloading the page. `_global.css` sorts first and declares the `@layer` order for every file, whichever are linked. `test/integration/stylesheets_test.rb` fails when a public page links an area it does not use.

The palette is the wordmark's: `--ink` for text and the footer, `--paper` for the page, `--sky`, the grey-blue of "sky", and `--blip`, the orange of the signal. Each of the last two has a soft tint for a band (`--sky-soft`, `--blip-soft`) and a deep shade for text (`--sky-deep`, `--blip-text`). A page alternates paper and sky bands, keeps one blip band for its closing message, and ends on the ink footer.

The ownship editor, `/briefing/ownship`, draws the symbol at the centre of the radar, one per aircraft type. The drawings and the outlines they are made against are files in `content/ownships/`, beside a README on what a drawing must be, where each outline comes from, why the glider is a JS3, and the link registry's `ownship` frame a device could take one in, which the editor shows by name and counts in CBOR bytes: a proposal, which no firmware reads yet. The editing runs in the browser, in `ownship_controller.js` over `#skyblip/ownship`, and sends nothing to the server: the page is loaded once per aircraft type, and a drawing travels as text.

The simulated device case is `app/assets/stylesheets/simulator/device.css`, shared by the public simulator and the editable simulator under `/briefing/simulator`.

## The briefing app

`/briefing` is the app a pilot installs, and the only place that offers it: `layouts/briefing.html.erb` links the manifest, `/briefing/manifest`, whose start URL and scope are `/briefing`, and the public layout links none. The app has one address per page in every language, so it has no language switcher. It speaks the language chosen in its settings, `/briefing/preferences`, which keep it in the `locale` cookie the site's switcher also writes. Before any choice it speaks the browser's language from `Accept-Language`. A frame a public page embeds, such as the simulator, follows that page's language through its `locale` parameter. The old `/fr/briefing` addresses redirect to the same page without the prefix. The app has no public nav and no footer. It opens on the devices this browser has met (`/briefing`), or straight on the page of the only one, and each device has a page, `/briefing/devices/go-00012a` or `/briefing/devices/bravo-3f2a`, its settings first, and a firmware page and a terminal page under it, the terminal printing every Bluetooth frame the device sends and receives. `/briefing/activate` activates a new Go, `/briefing/tools` lists the console, the traffic comparison, the simulator and the ownship editor. `/activate`, `/update`, `/configure` and `/manage`, the addresses of the public pages these replace, redirect into the app, `/activate` because the glass prints it.

A device is known to the server only by the address in its page's URL: everything else lives in the browser. `app/javascript/skyblip/fleet.js` remembers, in `localStorage`, every device this browser connected, by its name, with what it last read, and holds one `Updater` per device, so a Go and a Bravo stay connected side by side across Turbo visits. Its README says how a remembered device connects again. The app shows what goes wrong where it goes wrong, in one sentence: every refusal the device or the server can answer has its words in `config/locales/briefing.*.yml`, which the layout hands to the page as `data-briefing-words`. `test/i18n/briefing_words_test.rb` fails when a `config_*.cpp` in `firmware/products/common/services/` gains a refusal that either language has no words for.

The system tests under `test/system/briefing/` walk every screen against `test/system/fake_fleet.js`, several units in range of a fake `navigator.bluetooth`. Run them with `BRIEFING_SCREENS=dir` and each step saves its screen at phone and laptop sizes, which is how the pull request that changes a screen shows it.

## Firmware and simulator releases

GitHub Releases hold firmware and the simulator runtime. Loading an app page never waits for GitHub. A separate eager Turbo Frame requests the shelf or simulator build from Rails, which lists the published releases live. A release, `v*` or `dev-*`, carries every product's images, and each file names its product. Newest means the latest commit: a release is dated by `created_at`, which GitHub sets from its commit, never by `published_at`, so a build whose run finished late is not taken for the newest. The shelf offers the newest stable release and the kept development builds. It lists every base image newest first, then every full one (`Release.firmware_shelf`). Once a connected unit's settings are read, the device page loads the newest base image of its track and product, once per connection, unless a file is already chosen or a notice is showing, and offers it when it is newer than the running firmware. The firmware page swaps in the full image of the same release and product when the unit's sensor hub needs it. The simulator uses the newest stable release when it carries the simulator files, and the newest main development build otherwise. It never chooses a feature-branch simulator automatically.

The browser fetches selected files through `/releases/:tag/:file`, because GitHub's download host does not allow browser CORS requests. The endpoint accepts only our repository, recognized release tags, firmware filenames and the four simulator filenames. Redirects are limited to GitHub's asset hosts, downloads are size-bounded, and successful immutable responses are browser-cacheable. The server does not retain release files or metadata between requests.

Release type selects the offered channel, not proof of a signing key. Each firmware file is named after its product, `skyblip-go-*` or `skyblip-bravo-*` (`Release.product_of`), and the shelf offers a unit only its own product's files, by the `product` its `update` frame names, a skyBlip Go for a unit that names none or whose frame never arrived. The update client reads the chosen binary and checks its actual key, version, product and sensor-hub requirements before uploading. MCUboot independently verifies its signature. Each release's `SHA256SUMS`, and a production release's provenance, stay published on GitHub. The server does not add checksum or attestation verification.

A GitHub failure is contained in the frame. The firmware page reports the unavailable list and keeps its file picker. The simulator reports an unavailable build instead of blocking the page. Requests start without a GitHub token, sharing the unauthenticated limit of 60 API calls per hour on the crooz IP. #132 tracks adding a token. #131 tracks Litestream and kamal-backup before durable device registrations.

`firmware.yml` and `release.yml` publish `skyblip-simulator.js`, `skyblip-simulator.wasm`, `skyblip-simulator-embed.js` and `skyblip-simulator-scenarios.json` with firmware images (`../firmware/simulator/README.md`, The browser). v0.8.0 and the builds before it carry them as `skyblip_simulator.js`, `skyblip_simulator.wasm`, `embed.js` and `scenarios.json`, and `Release::SimulatorFiles` reads both names until the release after v0.8.0 ships (#483). Older releases without those files cannot run in the simulator. Publishing or pruning firmware never deploys Rails. Changing app JS, CSS or content does.

The pages speak the companion link in CBOR, with the numbered keys of [`schemas/link.v1.json`](../schemas/link.v1.json), through `#skyblip/link`, and call the simulator embed in the words #151 gave them (`command`, `acknowledge`, `panel`, `setSatellites`), and no others. Above the codec every page works with the registry's full names. On a link that never exchanged its MTU, 23, a notification carries 20 bytes: the status and every acknowledgement fit, so an install still runs, but the update frame with its hub digest, an activated unit's config reply, and an unactivated one's once it carries a callsign or an aircraft address, and the activation's challenge reply do not, and `register` and `unlock` are longer than the two prepare segments the unit reassembles. `app/javascript/skyblip/README.md` has the sizes.
