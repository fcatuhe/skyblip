# server

[skyblip.eu](https://skyblip.eu) runs as one Rails app on the crooz server. Public content lives under `Content`, and `/briefing` is the app a pilot installs to activate, set up and update a device, beside the Bluetooth console and the editable simulator. Users sign in to an admin area, and `/briefing/activate` gives each unit its serial (#126).

Every command here runs from this directory, not from the repo root.

## Running it

```sh
mise trust && mise install   # Ruby, and fnox
bin/setup                    # gems, the databases, then bin/dev
bin/dev                      # http://skyblip.localhost:8119
bin/ci                       # the gate before handoff, the checks CI runs as separate jobs
bin/rails test:system        # Cuprite, on the Chrome or Chromium it finds, BROWSER_PATH otherwise
bin/screenshots              # retake the device screens off the firmware next door
```

Rails 8.1 on Ruby 4, SQLite with Solid Cache, Queue and Cable, Hotwire over Propshaft and Importmap, Minitest with Cuprite for system tests and VCR for GitHub, Kamal to deploy ([DEPLOYMENT.md](DEPLOYMENT.md)).

Tests that reach GitHub replay a cassette from `test/vcr_cassettes/github/`, system tests included: the app server runs in the test process, so the cassette a test inserts answers the request a Turbo Frame makes. `CASSETTES_RECORD=1` records them again against the real API.

## Credentials

The credentials keys live in Bitwarden, in the secure note `skyblip-repository`, which [fnox](https://fnox.jdx.dev) reads through the `bw` CLI as `fnox.toml` maps it. It is named after the repository rather than `skyblip` alone because `bw` finds an item by searching names, usernames and URLs, and a login for the site would match too.

- `config/master.key` decrypts the development credentials, `config/credentials.yml.enc`, and stays on disk. The dotfiles bootstrap writes it from the note's `RAILS_DEVELOPMENT_KEY`, mode 600. A worktree has none, so `bin/setup --skip-server`, run once inside one made by `git wt`, links it from the main checkout.
- The production key never touches the disk. It is the note's `RAILS_PRODUCTION_KEY`, which `mise.toml` grants to two tasks only, as `RAILS_MASTER_KEY`, the name Rails and Kamal read: `mise run kamal ...` and `mise run credentials:production`. Rails reads `RAILS_MASTER_KEY` before any key file, whatever the environment, so it must never reach a development command, and nothing else sees it: not the shell, `mise env`, the shims, or an agent. The tasks' output shows it as `[redacted]`, except the credentials editor, which needs the terminal.

The production credentials do not exist yet. To create them, add `RAILS_PRODUCTION_KEY` to the note, 32 hexadecimal characters as `ruby -rsecurerandom -e 'puts SecureRandom.hex(16)'` prints them, then run `mise run credentials:production`: Rails finds the key in the environment, writes no key file, and creates `config/credentials/production.yml.enc` with a `secret_key_base`. Commit that file, and give the same key to the GitHub `server_production` environment as `RAILS_MASTER_KEY`.

## Admin and analytics

A user has a first name, a last name, an email and a password, and a role: `user` or `admin`. Nothing links to the sign-in page, `/session/new`, which robots are asked not to index. Once signed in, an admin finds `Admin` in the site nav, which opens the admin area: analytics, insights, errors, events, the users, the units, the coding agents connected to the MCP server, and Mission Control's jobs at `/admin/jobs`, which open in a window of their own named `mission_control`. Every admin controller inherits `Admin::ApplicationController`, which answers `403` to anyone but an admin, the way Fizzy guards its own, and Mission Control is mounted on it too. There is no sign-up and no password reset: an admin creates the accounts and sets their passwords. The first admin is created in the production console, `mise run kamal console`:

```ruby
User.create!(first_name: "[first name]", last_name: "[last name]", email: "[email]", password: "[password]", role: :admin)
```

Ahoy records visits and events in their own database, `analytics`, from the server (every controller action) and from the browser (`app/javascript/ahoy-module.js`, posting to `/hoy`). Each visit is then computed into an `Analytics::Visit`, which knows its pages, duration, channel, section (`public`, `briefing` or `admin`) and segment. The segment is how your own browsing stays out of the numbers: a visit is `internal` when it belongs to an admin, or comes from a browser an admin once signed in from, `user` for any other account, `non_user` otherwise. The `Admin` link opens the overview on `non_user`. Development and test track nothing, `Ahoy.api_only` is on there. Firmware downloads are not tracked, so their year-long public cache never carries a cookie.

The site follows the CNIL's terms for audience measurement without consent ([Cookies : solutions pour les outils de mesure d'audience](https://www.cnil.fr/fr/cookies-solutions-pour-les-outils-de-mesure-daudience)): a tracker lives 13 months, and what it collects is kept 25 months at most. The two periods are `config.x.tracker_lifetime` and `config.x.retention`, and every tracker and every log in the app keeps to them. `Ahoy::Visit.prune` deletes visits older than 25 months every night, with their events and what was computed of them.

A visit keeps no IP. `Ahoy::Store#track_visit` places it in memory, while the request runs, with the MaxMind GeoLite City database, `storage/GeoLite2-City.mmdb`, then drops it, and keeps the user agent Ahoy reads the browser, the system and the device type from. No job carries the IP to a queue. The database comes from `Maxmind::UpdateGeoliteCityDatabaseJob` downloads and keeps current. The job is scheduled in `config/recurring.yml` only once the production credentials hold the MaxMind account, so until then visits keep no place and nothing fails:

```yaml
maxmind:
  account_id: [account id]
  license_key: [license key]
```

`mise run credentials:production` adds them. The first nightly run after the next deploy downloads the database.

## Addresses

The database keeps no IP address but an admin's session. A visit keeps its user agent and the city its IP was placed in while the request ran (Analytics above). Rails' `rate_limit` counts requests in Solid Cache under a key that holds the client's IP, or its network for activation and attestation, as Rails does by default, and the counter expires with its window. The activation's network cap counts the same way: `Unit.enrollments_from` increments a cache counter per network that lives 24 hours from the network's first new unit, so a unit keeps no trace of where it enrolled from. A cache that loses the counter, by eviction or a clear, forgets the network's enrollments, as it would a rate limit's. An admin's session keeps the IP and the user agent it signed in with, as Rails' authentication generator writes them. Rails logs each request with its IP, and so does kamal-proxy, outside the app.

## Events, errors and the MCP server

Everything that happens on the site and in the briefing app is an event in a SQLite database of its own, `events`: the server's requests, jobs, activations and errors, through `Rails.event` and `Rails.error`, and each browser's journal, which `app/javascript/skyblip/journal.js` keeps in `localStorage` and posts to `/events` until the server takes it, so a phone offline at the airfield loses nothing. A pilot's journal carries a support code, eight letters shown under Settings and beside a failed install, by which an admin reads that pilot's story. The errors of the server and of every page's scripts are grouped into problems by fingerprint, which does the job of an error tracker such as Sentry, except for alerts. [`app/models/event/README.md`](app/models/event/README.md) says what is recorded, what is kept out, and how to read it.

Admins read it under `Insights`, `Errors` and `Events` in the admin area, and a unit's page links its timeline. A coding agent reads the same through the MCP server at `/mcp`, which an admin connects with OAuth and a client metadata document: [`app/models/oauth/README.md`](app/models/oauth/README.md). From a laptop that deploys, `mise run kamal app exec "bin/rails events:review DAYS=30"` prints the numbers, and `events:tail DEVICE=go-00012a` or `CODE=ABCD-EFGH` a pilot's events.

## Activation

A unit transmits nothing until it holds a serial that this server signed for it, and `/briefing/activate` is where it gets one: the glass prints `skyblip.eu/activate`, which redirects there. The wire protocol is the activation frames of [`schemas/link.v1.json`](../schemas/link.v1.json) on the unit's half and [`schemas/activation.v1.schema.json`](../schemas/activation.v1.schema.json) on the server's: the page asks the unit for a nonce, `POST /activation/challenges` signs it, the unit asks on its glass and signs its registration with its own key, `POST /activation/registrations` checks that signature and answers the serial with an unlock code, and the unit stores the code. [`activation.v1.vectors.json`](../schemas/activation.v1.vectors.json) is one exchange signed with the public test key, which `test/models/identity/message_test.rb` holds OpenSSL to and the firmware's host suite holds Monocypher to: Ed25519 is deterministic, so two libraries that sign the vectors alike sign everything alike.

`Unit` is the DEVICEID and its serial, dense from 1 to 65535 (0 would put 0x000000 on the air, which decoders read as no address), and `Unit::Key` the public keys it registered with, `active`, `pending` or `revoked`. A new DEVICEID gets the next serial and its key is bound. The same key gets the same serial in a fresh unlock code. Another key is refused as `other_key` and kept as `pending`, with the date and the firmware it came with. A unit keeps its five newest pending keys and forgets older ones, since anyone can sign a fresh key for a DEVICEID the server knows. In the admin area, `Units` lists them: promote makes a pending key the active one and revokes the old, revoke leaves the unit with no key, so the next registration binds its key as a first one does. A revoked key stays revoked: it is refused as `revoked_key`, and the page shows the DEVICEID and the start of the key, which is what an owner writes in with and what the `Units` page lists. A key registered under two DEVICEIDs is a key reused by a script or custom firmware, or an RNG that failed, since this firmware never lets a copied key slot be a key on another chip: the server binds it to each, and `Units` counts the units that share it in a banner, names the first ten, and lists them beside the key. The unlock code is signed inside the transaction that bound the key, so a revocation lands before it or after it. `Activation::Challenge` is the server nonce, kept five minutes, used once, and forgotten hourly by `config/recurring.yml`.

Both endpoints take ten requests a minute per network (`rate_limit`, on Solid Cache). Past 50 new units in a day, a new DEVICEID is refused as `daily_cap`, and past 5 new units in 24 hours from one network, an IPv4 address or an IPv6 /56, the block a home line holds, as `network_cap`, so one client cannot spend the whole day's cap. A private, loopback or link-local address counts toward no network and logs an error, because Docker on crooz hands Rails its gateway, 172.18.0.1, for every IPv6 client until #205 is fixed. The enrollment that reaches the daily cap logs an error, and the admin `Units` page carries a banner until midnight UTC: the app has no mailer to alert by, so those two are the alert. Every refusal is also an `activation.refused` event with its reason, which Insights counts. The network cap neither logs nor shows a banner, since one network reaching it is the cap working. A server nonce is spent only by a registration its unit signed, since it travels in clear over Bluetooth.

Only skyblip.eu signs for a unit. It holds one Ed25519 key, the server key, which signs every message a unit must trust from it about its identity: the challenge and the unlock code today, any later command that touches identity tomorrow, each under its own `skyblip:<purpose>:v1` label (`Identity::Message`). Every device build, a pull request, `main`, a release or a local build, carries only its public half, `firmware/keys/server.pub`, so a build needs no secret to be activated. The seed, 64 hexadecimal characters, lives in the production credentials alone:

```yaml
identity:
  server_private_key: [seed]
```

The name says private because this is the one place the secret half sits, beside values that are not secret; its public half is `server.pub` in the firmware, and the server key, unqualified, is the pair. `openssl rand -hex 32` makes a seed: in Ed25519 the 32 random bytes are the private key. Add it with `mise run credentials:production`. `Identity::ServerKey` derives the public key from it, and names it by the first four bytes of the SHA-256 of that public key, which is how the unit names the key it trusts in its `challenge` reply. The admin `Units` page shows both, to check against `firmware/keys/server.pub`. To get the public half before a deploy, in your own terminal:

```sh
read -rs seed && ruby -ropenssl -e 'k = OpenSSL::PKey.new_raw_private_key("ED25519", [ARGV[0]].pack("H*")).raw_public_key; puts k.unpack1("H*"), OpenSSL::Digest::SHA256.digest(k)[0, 4].unpack1("H*")' "$seed"; unset seed
```

Development and test sign with the public test key of the vectors (`config/initializers/identity.rb`), which only the firmware's host suite and simulator trust, so a local server can never activate a real unit, nor hand one a serial the registry gave another. With no key at all, the activation endpoints fail with an error and the `Units` page says so.

The registration also says whether the unit runs a release build, signed with the rest, and the `Units` page shows it as the build, release or development. Nothing on the air tells them apart: a development unit is a real aircraft with a real serial.

### The firmware each unit runs

The server keeps which firmware each unit runs on the unit's own word, so the firmware the fleet runs, and the ADS-L version each release carries, rests on the units' signatures rather than on what a browser says. The registration is the first statement: its signature covers the version, so an active key's registration records it. After that, on every connection of an activated unit to the briefing app, the page asks `POST /attestation/challenges` for a nonce, sends it to the unit as `attest`, and posts the unit's signed `attestation` frame to `POST /attestation/statements` (`firmware/core/comms/README.md`, Attestation). `Attestation::Statement` checks the signature against the unit's active key, spends the nonce and calls `Unit#attest_firmware`. `Unit::Firmware` holds one row per stretch on one version and build: the same firmware signed again moves its row's `updated_at`, and another one, or a return to an earlier one, opens a row. Each is a `unit.firmware_attested` event, and each refusal an `attestation.refused`. `Attestation::Challenge` is kept five minutes and used once, as the activation's nonce is, and both endpoints take twenty requests a minute per network. Neither request carries the support code, and neither table keeps an address, so the record ties a version to a unit and to no pilot or browser. A unit on firmware from before `attest` answers `unknown_command` and stays on the version it registered with until it is updated.

A unit page in `Units` lists that signed firmware, newest first, apart from the firmware browsers reported, which `Unit::ReportedFirmware` folds from the journal's `device.read` and `device.installed` events. Those cover installs made outside the app, such as a `.uf2` dropped over USB, from the next connection on, but any browser can post a journal naming any device, so nobody vouches for them, and they go when the events do, after 25 months. The `Units` list shows each unit's newest signed firmware, or the version it registered with until it signs one. Both reach a coding agent through `get_unit`.

## Content

Pages are files, not database rows: `content/pages/<slug>.html.erb`, with YAML frontmatter for `title`, `nav_title`, `description` and an optional localized `slug`. A page is bilingual by convention, `<slug>.html.erb` and `<slug>.fr.html.erb`, and the locale switcher offers a language only where the twin exists.

The `title` is what a search result shows, followed by ` · skyBlip` unless it already names skyBlip, and it labels the links `link_to_page` draws without a label. Keep the rendered title within 60 characters and the `description` within 155: `test/integration/content/meta_test.rb` fails past either. Write French metadata with its own typography, a no-break space before `:` and `€`, as characters rather than entities, since the meta tags escape them. Every page also carries `updated_on`, quoted as `"2026-11-09"` because the frontmatter parser refuses YAML dates. Set it to the day of the change whenever the page changes significantly: its main content, its links, or what its head tells a search engine, such as the title, the description or the structured data. A typo or a style fix does not count. It is the sitemap's `lastmod`, taken from the file rather than from git, because CI checks out one commit and a page's commit date is not known until the sitemap is committed with it. The optional keys feed the structured data that `StructuredDataHelper` renders as JSON-LD: `published_on` makes a page an `Article`, `parent` names the page a `BreadcrumbList` passes through (the guides name `guides`), and `product` marks up a `Product` with the lowest price the site shows. `features`, the Go, and `skyblip-bravo` have one. Tango has none: it pairs a Go priced in euros with an X1 priced in dollars, and a `Product` takes one currency.

`Content::Page` reads the collection, and the content route accepts only existing localized slugs, leaving application routes separate. Every published page is listed in the sitemap, whether another page links to it or not. Run `bin/rails content:sitemap:generate` after changing the collection. `bin/rails content:sitemap:check` and the test suite catch drift. Canonical URLs always use `config.x.public_url`, not the incoming request host.

The site sells three devices, and every page is built from the same sections: a centred `page-hero`, then `band`s that alternate with `band--tint`, each opened by a `section-title` (`sections.css`). skyBlip Go and Go+ run today on a LilyGO T-Echo and T-Echo Plus. skyBlip Bravo is a Seeed SenseCAP MeshTracker X1, sold through a Seeed affiliate link with a promo code, and a Go paired with a Bravo is a skyBlip Tango. Bravo's firmware is published as development builds, as the Go's is. Purchase buttons have no firmware note. Every affiliate link carries `rel="sponsored"` with its disclosure nearby, and every X1 price shows the struck price without the code, the price with the code `5GO3A5DD` and the shipping to France. The nav names the devices, `features` (labelled Go, served as `/go`), `skyblip-bravo` (`/bravo`) and `skyblip-tango` (`/tango`), then `buy`, `guides` and `about`, with `update` and the simulator (`skyblip-go`, served as `/try`) on the right. The footer carries everything, the devices in its first column and the guides in the second. `index` introduces the three devices and sells the Go, `features` walks through what the Go does with a link per feature to the guide paragraph that explains it, `skyblip-bravo` routes a visitor to the device that fits what they want to see, `skyblip-tango` explains the pair, `buy` says where to get each device and how to install a Go, `guides` indexes the subject pages (`radar`, `instruments`, `controls`, `power`, `phone`, `radio` and `displays`), `about` holds the why and the pledge, and `roadmap` the devices and firmware that come next. The diagram of the pair is `shared/_tango.html.erb`, drawn in SVG from the colour and type tokens, with its words in `config/locales/`. A feature gets its block in `features` and its paragraph in the guide that owns the subject, and the paragraph's `h3` carries the anchor the block links to. The words the layout itself speaks (nav, footer, the call to action that closes a section, `shared/_cta.html.erb`) live in `config/locales/`.

The legal notice (`legal-notice.*`, `/fr/mentions-legales`) names the hosting provider only, as article 1-1 II of the [LCEN](https://www.legifrance.gouv.fr/loda/id/JORFTEXT000000801164) allows a site published non-professionally, provided the host holds the publisher's identity. It reads the host from the credentials, not from the source, added to production with `mise run credentials:production`. Development has them already. Without them, as in CI, which has no key, the fields render empty:

```yaml
legal:
  host: [hosting provider]
  host_address: [hosting provider address]
```

A link shared on WhatsApp, a forum or a mailing list shows the page's share image, a 1200x630 JPEG under `content_images/share/`: `go` by default, or the card a page names in `share_image` (`radar`, `bravo`, `tango`). The cards are drawn from the site's own wordmark, photos, screens, tokens and fonts by `bin/rails content:share_images:generate`, which renders `lib/share_images/card.html.erb` in Chrome through Ferrum, a test gem, so it runs where the test bundle is installed. Bravo shows Seeed's X1 photo, as the Bravo page does, and Tango shows the Go and the X1 side by side. The device name and the device sit inside the centred 630x630 square, the crop WhatsApp and Slack show in a compact preview. Its alt text lives in `config/locales/` under `share.images`. Run the task again after changing a card or anything it draws from.

Images live in `content_images/pages/<slug>/` and are drawn with `pages_image_tag`, or `content_image_tag` with the full path, which read the file's width and height so the page keeps its layout while the image loads. The device screens under `pages/skyblip-go/` are drawn with `screen_image_tag` from whichever page shows them, and they are not artwork: each is the 200x200 framebuffer of the WASM simulator, driven to that state and read out of `simulator_panel()`, so a page that changes on the device is a capture that has to be taken again. They are stored at 200x200 in two colours and scaled by an integer factor on the page (`features.css`), because any other factor resamples a panel pixel.

Every other image, a photo or an app screenshot, is AVIF, encoded by libvips from a lossless source: `vips heifsave in.png out.avif --Q 75 --compression av1 --effort 4 --strip --subsample-mode auto` for a photo, `--Q 70 --subsample-mode off` for a screenshot, whose text loses its edges to chroma subsampling. Where libvips is not installed, `ffmpeg -i in.png -c:v libaom-av1 -still-picture 1 -crf 30 -cpu-used 4 -pix_fmt yuv420p -map_metadata -1 out.avif` encodes a photo the same way. The X1 photo under `pages/skyblip-bravo/` is Seeed Studio's product shot, cropped to the device and credited where it is shown large, until our own photos replace it. Rails registers no AVIF type, so `config/initializers/mime_types.rb` does, or the dev server sends the files without a Content-Type.

The legend under `pages/skyblip-go/blips/` is the other half of the same rule: one PNG per traffic blip, each drawn on its own 19x25 canvas by `ui::draw_blip`, the widget the radar page itself calls, so the table on the page cannot drift from the glass. `bin/blips.cpp` is that dumper, a host binary linked against `ui/canvas.cpp` and `ui/widgets/blip.cpp` and nothing else.

Taking them again is `bin/screenshots`: it builds the firmware's WASM, flies one device per scene, compiles the dumper, and writes the PNGs over the ones in the tree. A scene names the page, the menu and the alarm level it expects and the script stops on the first one that does not hold, because a capture of the wrong glass is worse than a stale one. The page ids and the menu rows are read out of `pages/page.h` and `pages/menu.cpp` rather than copied into the script, so a scene opens `NEARBY_MENU.SelfTest` by name: the copy that used to sit here went stale when a page was inserted, the self-test scene opened the row below and the check passed on the wrong glass. The scenes are the file: to change what a screen shows, change the sky it is flown in. The radar is captured both ways for `displays`, a `-to-scale` shot beside the one of the same sky on `ALL`, which is what a fresh device boots on, so every other radar capture is `ALL` too. `PLOT` is pressed through the menu like any other row. Node runs the same `embed.js` a browser does, so the only thing it hands Emscripten is `instantiateWasm`, which is how the module is loaded off the disk rather than fetched.

Running it takes Emscripten 6.0.9, the version CI pins: `git clone https://github.com/emscripten-core/emsdk.git ~/.local/opt/emsdk`, then `./emsdk install 6.0.9 && ./emsdk activate 6.0.9` in it, and `source ~/.local/opt/emsdk/emsdk_env.sh` in the shell that runs the script. The firmware workflow runs it on every firmware change and fails when a picture in the tree differs from the one the firmware draws, so a change to the glass carries its pictures.

The briefing's prompt is drawn the same way: `briefing/_glass.html.erb` is a canvas, and `glass_controller.js` paints the Go's confirm page into it with the simulator's `paintPrompt` (`../firmware/simulator/README.md`). `/briefing/prompt_glass` sends the browser to the `embed.js` it is drawn with: in development and test the one `make -C firmware browser` built, served as release `local` from `config.x.simulator_build`, and in production the release the simulator page runs. A release older than the export shows the title alone. The canvas is labelled with the page's words, which the firmware hands back with the pixels, so a screen reader hears the prompt as the glass shows it. The system tests read the glass by that label, and test runs only ever use the local build, so the server workflow restores it from a cache keyed on the firmware's sources and builds it only when they changed. The WASM is 544 KB and 234 KB gzipped, which Thruster sends compressed. The browser fetches it the first time a prompt shows, and keeps it for a year.

Look and layout come from the token sets in `app/assets/stylesheets/`. Colors, spacing and type are CSS variables in `_global.css`; components never hardcode a value.

Every page links the stylesheets at the top of `app/assets/stylesheets/`, one `<link>` per file (`site_stylesheet_link_tags`), and nothing else, so a file added there reaches every page. An area's stylesheets live in a subdirectory and reach only the pages that ask for them with `<% content_for :stylesheets, area_stylesheet_link_tags("simulator") %>`: `admin` for the admin layout and the sign-in page, `briefing` for every page under `/briefing` (its layout links it), `simulator` for `/try` and the briefing simulator, `workbench` for the briefing simulator and console, and `ownship` for the ownship editor. The frames those pages load, `/briefing/firmwares` and `/briefing/simulator_build`, ask for the same areas, so they render styled when opened on their own. Propshaft's `stylesheet_link_tag :app` takes every file under `app/assets`, subdirectories included, which is why the layout lists the top level itself. An area's links carry `data-turbo-track="dynamic"`, so Turbo adds them on the way into the area and removes them on the way out instead of reloading the page. `_global.css` sorts first and declares the `@layer` order for every file, whichever are linked. `test/integration/stylesheets_test.rb` fails when a public page links an area it does not use.

The palette is the wordmark's: `--ink` for text and the footer, `--paper` for the page, `--sky`, the grey-blue of "sky", and `--blip`, the orange of the signal. Each of the last two has a soft tint for a band (`--sky-soft`, `--blip-soft`) and a deep shade for text (`--sky-deep`, `--blip-text`). A page alternates paper and sky bands, keeps one blip band for its closing message, and ends on the ink footer.

The ownship editor, `/briefing/ownship`, draws the symbol at the centre of the radar, one per aircraft type. The drawings and the outlines they are made against are files in `content/ownships/`, beside a README on what a drawing must be, where each outline comes from, why the glider is a JS3, and the link registry's `ownship` frame a device could take one in, which the editor shows by name and counts in CBOR bytes: a proposal, which no firmware reads yet. The editing runs in the browser, in `ownship_controller.js` over `#skyblip/ownship`, and sends nothing to the server: the page is loaded once per aircraft type, and a drawing travels as text.

The simulated device case is `app/assets/stylesheets/simulator/device.css`, shared by the public simulator and the editable simulator under `/briefing/simulator`.

## The briefing app

`/briefing` is the app a pilot installs, and the only place that offers it: `layouts/briefing.html.erb` links the manifest, `/briefing/manifest`, whose start URL and scope are `/briefing`, and the public layout links none. The app has one address per page in every language, so it has no language switcher. It speaks the language chosen in its settings, `/briefing/preferences`, which keep it in the `locale` cookie the site's switcher also writes. Before any choice it speaks the browser's language from `Accept-Language`. A frame a public page embeds, such as the simulator, follows that page's language through its `locale` parameter. The old `/fr/briefing` addresses redirect to the same page without the prefix. The app has no public nav and no footer. It opens on the devices this browser has met (`/briefing`), or straight on the page of the only one, and each device has a page, `/briefing/devices/go-00012a` or `/briefing/devices/bravo-3f2a`, its settings first, and a firmware page and a terminal page under it, the terminal printing every Bluetooth frame the device sends and receives. `/briefing/activate` activates a new Go, `/briefing/tools` lists the console, the traffic comparison, the simulator and the ownship editor. `/activate`, `/update`, `/configure` and `/manage`, the addresses of the public pages these replace, redirect into the app, `/activate` because the glass prints it.

A device is known to the server only by the address in its page's URL: everything else lives in the browser. `app/javascript/skyblip/fleet.js` remembers, in `localStorage`, every device this browser connected, by its name, with what it last read, and holds one `Updater` per device, so a Go and a Bravo stay connected side by side across Turbo visits. Its README says how a remembered device connects again. The app shows what goes wrong where it goes wrong, in one sentence: every refusal the device or the server can answer has its words in `config/locales/briefing.*.yml`, which the layout hands to the page as `data-briefing-words`. `test/i18n/briefing_words_test.rb` fails when `firmware/core/comms/config.cpp` or `identity_link.cpp` gains a refusal that either language has no words for.

The system tests under `test/system/briefing/` walk every screen against `test/system/fake_fleet.js`, several units in range of a fake `navigator.bluetooth`. Run them with `BRIEFING_SCREENS=dir` and each step saves its screen at phone and laptop sizes, which is how the pull request that changes a screen shows it.

## Firmware and simulator releases

GitHub Releases hold firmware and the simulator runtime. Loading an app page never waits for GitHub. A separate eager Turbo Frame requests the shelf or simulator build from Rails, which lists the published releases live. A release, `v*` or `dev-*`, carries every product's images, and each file names its product. The shelf offers the newest stable release and the kept development builds. It lists every slim image newest first, then every full one (`Release.firmware_shelf`). Once a connected unit's settings are read, the device page loads the newest slim image of its track and product, once per connection, unless a file is already chosen or a notice is showing, and offers it when it is newer than the running firmware. The firmware page swaps in the full image of the same release and product when the unit's sensor hub needs it. The simulator uses the newest stable release when it carries the simulator files, and the newest main development build otherwise. It never chooses a feature-branch simulator automatically.

The browser fetches selected files through `/releases/:tag/:file`, because GitHub's download host does not allow browser CORS requests. The endpoint accepts only our repository, recognized release tags, firmware filenames and the four simulator filenames. Redirects are limited to GitHub's asset hosts, downloads are size-bounded, and successful immutable responses are browser-cacheable. The server does not retain release files or metadata between requests.

Release type selects the offered channel, not proof of a signing key. Each firmware file is named after its product, `skyblip-go-*` or `skyblip-bravo-*` (`Release.product_of`), and the shelf offers a unit only its own product's files, by the `product` its `update` frame names, a skyBlip Go for a unit that names none or whose frame never arrived. The update client reads the chosen binary and checks its actual key, version, product and sensor-hub requirements before uploading. MCUboot independently verifies its signature. Each release's `SHA256SUMS`, and a production release's provenance, stay published on GitHub. The server does not add checksum or attestation verification.

A GitHub failure is contained in the frame. The firmware page reports the unavailable list and keeps its file picker. The simulator reports an unavailable build instead of blocking the page. Requests start without a GitHub token, sharing the unauthenticated limit of 60 API calls per hour on the crooz IP. #132 tracks adding a token. #131 tracks Litestream and kamal-backup before durable device registrations.

`firmware.yml` and `release.yml` publish `skyblip_simulator.js`, `skyblip_simulator.wasm`, `embed.js` and `scenarios.json` with firmware images. Older releases without those files cannot run in the simulator. Publishing or pruning firmware never deploys Rails. Changing app JS, CSS or content does.

The pages speak the companion link in CBOR, with the numbered keys of [`schemas/link.v1.json`](../schemas/link.v1.json), through `#skyblip/link`, and call `embed.js` in the words #151 gave them (`command`, `acknowledge`, `panel`, `setSatellites`), and no others. Above the codec every page works with the registry's full names. A development pre-release built before #151 no longer loads in the simulator. A unit running a build from before the link spoke CBOR answers in JSON, which the pages cannot read, so it cannot be asked to install from the briefing app: it takes a newer build as a drag-and-drop `.uf2`. On a link that never exchanged its MTU, 23, a notification carries 20 bytes: the status and every acknowledgement fit, so an install still runs, but the update frame with its hub digest, an activated unit's config reply, and an unactivated one's once it carries a callsign or an own ICAO, and the activation's challenge reply do not, and `register` and `unlock` are longer than the two prepare segments the unit reassembles. `app/javascript/skyblip/README.md` has the sizes.

Deployments use `.github/workflows/server.yml` and Kamal on the existing Debian crooz host. Setup, production credentials, the remote builder and the one-time DNS cutover are documented in [DEPLOYMENT.md](DEPLOYMENT.md). No C++ or Emscripten toolchain is needed in the Rails image.
