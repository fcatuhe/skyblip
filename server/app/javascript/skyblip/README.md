The Rails app serves the simulator, the Bluetooth console and the traffic comparison under `/briefing/simulator`, `/briefing/console` and `/briefing/comparison`.

Reusable browser modules live here and their Node tests live in `server/test/javascript/`. Rails importmap pins `#skyblip/*` to digested assets, and `server/package.json` maps those same module names for Node's native test runner. Serving the app needs no Node runtime, package install, or bundler.

The simulator loads `skyblip-simulator-embed.js`, Emscripten's loader and the WASM from same-origin `/releases/:tag/:file` URLs after a Turbo Frame selects a release. When a local browser build exists, `/try` and `/fr/essayer` use it instead. The simulator's case styling is app-owned in `server/app/assets/stylesheets/simulator/device.css`. The firmware's own `firmware/simulator/web/embed.js` remains usable by `server/bin/screenshots` without Rails.

On the public simulator, the Bravo checkbox starts a fresh Go alone or loads the firmware's `paired` scenario. It appears once the simulator runs. Both modes generate ADS-L and FLARM traffic 0.8 to 4.8 km away. Paired mode adds a separate group of ADS-B aircraft 8 to 30 km away. `simulated_traffic.js` draws that traffic for the public simulator and the workbench alike. The simulated Bravo receives those messages on 1090 MHz and relays the traffic to the Go over the firmware's peer link.

## The console

`ble.js` is the transport and knows nothing about what a page draws: it connects, reassembles the stream, and hands whole lines and decoded frames back. `controllers/console_controller.js` renders the console UI. `test_ble.mjs` pins down the reassembly, because a sentence cut across two notifications is the failure that looks like a firmware bug from the page. `ble.js` stops a characteristic's notifications before it starts them. Chrome on Linux keeps the notify session of a link that dropped and answers the next start from it, so a reconnect in the same page would hear nothing until a reload. `fake_skyblip.mjs` does the same with `keepsNotifySessions`.

The picker lists anything advertising Nordic UART or HM-10, which is skyBlip and SoftRF both, so the same page is how you read one and configure the other.

**The serial endpoint** is the traffic picture: `$PFLAU`, `$PGRMZ`, `$LK8EX1`, a `$PFLAA` per target, `$GPRMC`/`$GPGGA` with a fix. A notification is a slice of a byte stream and not a sentence, so `ble.js` splits on line ends rather than on notifications, the way an EFB does.

Writing to it reaches skyBlip's `on_stream_write`, which discards everything: that characteristic exists because XCSoar refuses a UART service without one (`firmware/hardware/platform/zephyr/link.cpp`). SoftRF is the opposite and takes its whole configuration there, as `$PSRFC` sentences. `$PSRFC,?` dumps the current settings; echoing that line back with one field edited and field 1 set to the protocol version (`1`) stores it, after which SoftRF drops Bluetooth, writes EEPROM and reboots. A sentence typed without a `*` leaves with its checksum appended, because SoftRF drops what it cannot verify. Send all 19 fields: an empty term still counts as updated and reads back as zero.

**The config endpoint** is skyBlip's own, `69c21302`, one CBOR frame per write and one per notification, its keys the numbers of [`schemas/link.v1.json`](../../../../schemas/link.v1.json). `link.js` turns a plain object keyed by full names into that frame and back, so the console shows each reply as JSON and its text field takes JSON, byte strings in hex either way. The buttons cover `get`, `defaults`, `status`, `timing`, `flash`, `radio`, `update` and `diagnostics`; the text field sends anything else, `set` included, and refuses a name or a value the registry does not hold before anything is written. The rules the firmware enforces are in `firmware/core/comms/README.md`: the first session to write claims the endpoint, a `set` is refused in flight and on a low cell, and what survives those two is staged for a button press on the device.

A frame travels in one write because the unit reads each write as one whole CBOR map and answers one cut short `no_command`. `ble.js` writes config with response and chunks only the serial stream, where 20 bytes is what BLE guarantees and Web Bluetooth exposes no MTU to do better.

**The capture panel** arms, stops and fetches a diagnostics capture without `blip.py`. Arm and Stop send `{"command":"capture","profile":...}` with the profile chosen, or `"stop"`, on the config endpoint, as `scripts/blip_capture.py` does, and word the prompt and the verdict from the acknowledgements the console already hears. Fetch speaks the log endpoint, `69c21303`, through `log.js`: `list` for the count of sessions, `list` with the last index for its entry, then `read` windows of eight chunks from the index reached until a chunk `ends_session`, which is `blip.py fetch --log diagnostics` without `--all`. A truncated session starts at the index its entry names as `first`. A chunk that starts past the index asked for is the unit answering from the first record its ring has not recycled, and Fetch goes on from there (`firmware/core/comms/README.md`, A record keeps its index while the ring rotates). `diagnostics.js` decodes each 24-byte record through `diagnostics_layout.js`, the tables `scripts/diagnostics_layout.py` generates from `schemas/diagnostics_layout.v1.json` for `scripts/blip_records.py` too, so a record type or a field is added there and regenerated, never edited here. It writes the NDJSON lines `scripts/blip_ndjson.py` writes, a `session` note, the records and a `torn` note for the last record of a session the unit never closed and is not still recording, with Python's `json.dumps` spacing, so the panel's download and `blip.py fetch --out` are the same file. Fetch passes over a frame that answers no question it asked, such as a chunk of a window an earlier fetch abandoned, because the console keeps its link between fetches. The unit answers no command while a window goes out, so such a chunk arrives before the answer to the next `list`. The panel gives up on a verdict after 35 s, as `blip_capture.py` does. The table keeps the latest `adsb` record of each address. The `Adsb` record carries no callsign, so the table has none.

## The update client

`update.js` is what the device and firmware pages of the briefing app run, one `Updater` per device that `fleet.js` holds, and it knows nothing about the pages either: it holds the device's update dialect as a state machine and hands every change to one callback. The page renders that state and looks the words up in its own tables, so the two languages live in the page and not here. Importmap resolves the shared module names directly to Rails assets, with no build-time copy.

The update is two channels, and the device refuses the usual mcumgr sequence on purpose (`firmware/products/common/services/config_service.cpp`, `core/dfu/smp_policy.h`). The frames below are written as `link.js` decodes them, and an acknowledgement's `"command":"acknowledgement"` is left out.

On every connect, before anything else, `update.js` asks `identity`, and the unit answers who it is and what it runs: its product, `go` or `bravo`, its variant, `standard` or `plus`, its firmware version and build, its DEVICEID and its Bluetooth tag (`firmware/core/comms/README.md`, Identity). `state.identity` holds them and `productOf(state)` reads the product there. The frame never fits a 20-byte link, so the unit answers `small_mtu` there, and firmware built before the frame answers `unknown_command`. `update.js` takes either refusal, and `no_version`, without a notice: the page then knows no product, offers no published image and leaves the product check to the unit.

Before any of it, the page checks the chosen file against what the device said in its `identity` and `update` frames, and refuses what the bootloader would. `bootloader_keys` names the keys the bootloader verifies, each by the first four bytes of its hash as imgtool writes it in the image's KEYHASH TLV, which the page reads in hex: a file signed by none of them is `wrong_key`. A development bootloader names the development and production keys, a release one the production key (`firmware/keys/README.md`). Firmware that names no `bootloader_keys` has a bootloader with one key, the one that signed the running image, which `key` names, so `trustedKeys()` takes `key` alone. The shelf offers the images whose `data-key`, the key of their channel (`Release::KEYS`), is one of those keys, and of the unit's product, and the newest of the unit's own track is the one it reads on connect. A unit without `downgrade` is offered nothing older than it runs, by the same rule as `older`. A stable tag carries no build number, so a release is held to the running version's triple, and the release the unit runs stays on offer. The pages name a release by its tag, `v0.8.0`, and a development build by its version, `0.8.0+2405`: the unit runs a release when its track is `release`, and a file is one when it was taken from a release on the shelf. `downgrade: true` marks a development unit: without it, a file older than the running image is `older`, and the same version passes, so a release can be installed again. A file whose image class names another product than the unit's is `wrong_product` (`firmware/core/dfu/README.md`). A file naming no product, an image built before the class, is `unmarked_image` for a unit that names its product, which every unit with the identity frame does. The product also keeps the not-activated note off a skyBlip Bravo, which has no address.

The device checks all three again for any client, page or not: the version at `dfu` and on the first chunk, the product on the chunk that completes the image's protected TLVs, refused as image error 5 (`IMG_MGMT_ERR_INVALID_TLV`), which the page words as `wrong_product`, or as `unmarked_image` for a file naming no product, the one the page cannot refuse before it is sent to a unit that named no product, and the key once the image has landed.

1. `{"command":"dfu","version":"0.2.0+15"}` on the config endpoint, the version read off the image header. The device answers `confirm_dfu` and asks on its glass, naming that version; one press answers `{"acknowledge":true,"reason":"dfu"}` and open a ten-minute upload window, on the ground only. A trusted browser is not asked, and the device answers `dfu` at once (Trusted browsers). A `dfu` without a version is refused as `no_version`, and on a release unit a version older than the running one as `older`. An install also runs on a link that never exchanged its MTU (see "A link that never exchanged its MTU" below).
2. The image over MCUmgr/SMP, image group, upload command: the only SMP write the device accepts, and only inside that window. `smp.js` sends SMP v2 headers, so the image group's own error codes come back (`err`) rather than the generic `rc` the original protocol folds them into; a refusal by the command hook is still a bare `rc` 11. An image older than a release unit allows is refused on its first chunk with the image group's 27, read as `older`: the check `dfu` makes, for a client that never sent one.
3. Nothing more is asked. The glass says DOWNLOAD through the upload, and a tap of the pad answers `{"acknowledge":false,"reason":"cancelled"}` and closes the window. Once the last chunk is on flash the device closes the window and gives its verdict unasked: `{"acknowledge":true,"reason":"install"}`, or a refusal, `not_approved` for an image other than the version the glass named, `wrong_key` for one signed by a key its bootloader would not verify, `nothing_staged` for a slot it cannot read back, `low_power` as at the door. A take-off does not stop the upload, and an image that lands in flight installs once the unit is back on the ground. The verdict can arrive before the reply to the last chunk. An SMP `image state` write or `os reset` is refused, so none is sent.
4. After `install` the device paints INSTALLATION, reboots into the swap, and the link drops. On the next connect it pushes the `update` frame unasked whenever the image is not confirmed, or (with #90) its settings fell back, and `update.js` reads that frame whenever it comes. `reverted` is an image that started and never confirmed itself, so the bootloader swapped the old one back. `refused` is an image the bootloader never started: it scrambles slot 1 instead, which is how the device tells the two apart.

5. On every connect, `update.js` also asks `install_report`. A unit with an install on record answers what it found in slot 1 before the restart, the swap it marked, its restarts since and how far the new image got on probation (`firmware/core/dfu/README.md`, The install report). A unit with none answers a bare frame. `install_report.js` turns the report into the cause the firmware page words from `briefing.notices.install_report`. It also names `no_record` when the unit came back from the install's restart on another version with nothing on record. The journal sends each failure's report as `device.install_reported`, with every field of the report and the cause, and the page tells the pilot it was received and shows their support code.

   When the unit refuses an upload that landed, `nothing_staged`, `not_approved` or `wrong_key`, `update.js` asks `install_report` at once. The unit answers what it found in slot 1 at the refusal, `landed_check` and `staged_key`, and `landingOf()` puts them in `state.landing`. The journal sends them as `device.upload_refused`, beside the key the unit runs, the file's key and the version sent, so the events alone tell an image signed by another key from a slot the unit could not read back (`firmware/core/dfu/README.md`, The install report).

6. On every connect, `update.js` also asks `protocols`, and the unit answers the version of each radio protocol stack it carries (`firmware/core/comms/README.md`, The radio protocols). `state.protocols` lists them under the names the release notes use, ADS-L, ALP-TAS and ADS-B, and the device page shows them in one line under its facts, such as `Radio protocols: ADS-L 0.1.0, ALP-TAS 0.1.0`. The release's `PROTOCOLS.md` says what each version implements. A stack whose version is not text is passed over. The answer is 18 bytes on a Go, so it reaches every link.

7. On every connect of an activated unit, once the reads and the trusted browsers are in, `update.js` has the unit state its firmware to this server, without waiting for it (`server/README.md`, The firmware each unit runs). `attestation.js` posts to `/attestation/challenges` for a nonce, sends it as `{"command":"attest","server_nonce":...}`, and posts the `attestation` frame the unit answers to `/attestation/statements` beside the nonce, its product, variant, version, build and DEVICEID with the signature over all of them, byte strings in hex, as the activation relays its frames. Neither post carries the support code. It asks the unit nothing when the server cannot be reached, nor when the pilot started something while the server answered, and a refusal from either side ends it with a warning on the console and nothing on the page, such as `in_flight` from an activated unit in flight. The unit answers in order, so `FirmwareAttestation` takes the first `attestation` frame, or the first acknowledgement whose reason only `attest` gives, after its command, through the same `Replies` queue as the trusted-browser exchange (`replies.js`), which gives an answer five seconds from the moment its write went out, since a config write waits behind every SMP write of an upload. A unit not yet activated has no address, and states nothing until it does.

The same client edits the settings. On connect it sends `get` and `defaults` beside `update` and `status`: the stored settings, and the values the firmware ships on, so the page compares the two without a copy of the defaults of its own. `saveSettings()` sends a `set` carrying only the keys that differ from what the device reported; `resetSettings()` is the same call with the defaults. The device answers `confirm` and asks on its glass, one press answers a bare `{"acknowledge":true}`, which a trusted browser gets at once, and the client asks `get` again so the page shows what the device stored rather than what it sent.

The same client arms a unit's diagnostics capture (#247). `orderCapture(profile)` sends `{"command":"capture","profile":"power_run"}`, or `stop`. The unit answers `confirm_capture` and asks, a Go on its glass with the profile and the flights it erases, a Bravo on its lamp, and one press answers `{"acknowledge":true,"reason":"capture"}`, which the client turns into the `capture_armed` or `capture_stopped` notice and follows with a fresh dump. A unit refuses an arm while a capture runs as `capturing`, a stop while none runs as `not_capturing`, and a unit with no capture flash as `no_storage`. Every notice about a capture is marked `during: 'capture'`.

The client reads the diagnostics dump once the settings are answered, so a `small_mtu` that follows is the dump's own and raises no notice. `state.dump` keeps every group it read, by name, and `captureOf()` turns the capture group into `state.capture`: whether a capture runs, its profile, session and records, when it started, the span it keeps, and the price of the next one. A session is named by the UTC second it opened, or by the second since boot when the unit had no time yet. A second since boot stays below 4,294,967, where the unit's 32-bit millisecond clock wraps, while a UTC second is far above it. So a session below that wrap started `uptime_s - session` seconds before the dump was read, counted across the wrap, and a session above it is its own UTC start. A unit with no capture flash sends no capture group and gets `null`, and the device page then offers no capture control. The device page shows the state and the price above Arm. While a capture runs, it names the profile, the time it started and how long it has run, counted on the page between two dumps, and offers only Stop. While none runs, it offers only the profile and Arm.

`fetchCapture()` reads the last session of the diagnostics store over the log endpoint, through the `LogReader` the console uses (`log.js`), and reports `state.fetching` as it goes. The device page then hands it to `capture_upload.js`, which gzips the NDJSON `diagnostics.js` writes, the file `blip.py fetch --log diagnostics` writes too, and posts it to `/briefing/devices/:slug/captures` with the profile its boot record names and the browser's support code. The server reads the session, the records and the firmware off the file (`app/models/capture/README.md`). `Send a report` records `device.diagnosed`, the dump by group, in the journal, and says the support code.

An install, a recovery and a `set` are refused on the page as `in_flight` while the last `status` says `airborne` (`inFlight`), before the device would refuse them itself, except a `set` from a trusted browser, and asked on `ground` and on `unknown`, a unit with no fix since boot (`firmware/core/comms/README.md`, The flight gate). The page holds Install, Restart into the USB drive, Save and Back to defaults while `inFlight`, and only the first two on a trusted browser. The device pushes `status` when its flight state changes, so the page unlocks on landing without polling.

A release has two OTA images of one commit and one version, because the BHI260AP's firmware lives on its own partition of the external flash rather than in every image: `skyblip-go-<version>.signed.bin` (`skyblip-go.signed.bin` from a local build), the base one, boots the sensor hub from that partition, and `skyblip-go-<version>.full.signed.bin` carries the blob and writes it there once it is confirmed, if the partition does not already hold it. Each image says which it is in two protected TLVs, signed with it: `0x00a0`, the SHA-256 of the blob it pins, and `0x00a1`, one byte, `1` for the full image. `image.js` reads both off the protected TLV area, and an image without one (anything built before the split) pins nothing. The device's `update` reply says what its partition holds in `imu`: `none` (no hub answered, a plain T-Echo), `missing`, `corrupt`, `unreadable` (the external flash did not answer), `writing` (a full image is writing it now, up to a minute), or `held`, with the first eight bytes of the verified blob's SHA-256 in `imu_digest`, which `update.js` turns into the 16 hex characters it compares. `fullImageNeeded()` turns the two into the file the device should get, `state.advice`: base for `none` or a digest the chosen file pins, full for everything else. The page names it by its ending, `.signed.bin` or `.full.signed.bin`, since the version in front is the release's. A base file chosen for a device that needs the full one raises `needs_full` without blocking the install, because the device refuses to confirm a base image without its blob and the next reset reverts it. While the device reports `writing`, or an image on probation, `state.settling` asks the page to send `update` again.

`update.js` refuses only an image strictly older than the running one (`not_newer`), not an equal one: the base and full images of a release share its version, and reinstalling the full image of the running version is how a device gets its blob.

A confirmed image over a motion sensor, the BHI260AP, that reports `missing`, `corrupt` or `unreadable` is `state.motionSensorWithoutFirmware`: a motion sensor fitted after the install, or whose flash failed, boots nothing, and the slip ball is off, though the unit runs the newest image. An image on probation is not counted, since a base one over such a motion sensor reverts by itself. The device page says so in its banner and its firmware row instead of "up to date", and the fleet marks the unit. The firmware page says it in its status and shows Install for the full image of the running version, which the page swaps in for the newest base one as for any unit that needs it. It counts the install done only once the motion sensor holds its firmware. The pages call the BHI260AP the motion sensor, as the site does, since only its accelerometers are used.

Every refusal is a `reason` on the config endpoint or an error on the SMP one, and the state machine passes it on as a notice key without deciding what it means. A key the page has no words for is still shown, under its own name.

The unit asks one question at a time, and stops asking a connection whose question the pilot refused (`firmware/core/comms/README.md`, One prompt at a time). While a question stands, a command that would ask another is refused `prompt_pending`, and the standing one keeps its thirty seconds. After the pilot refuses a question on the device, every command that would ask one is refused `refused_on_device` until that connection drops. Neither client sends a command while a question stands, because both send only from `ready`. So a page meets `refused_on_device` after a refusal on the glass, and words it, and `cancelled` before it, as disconnect and connect again. The update client marks the connection `refusedOnDevice` on a `cancelled` that answers a standing question, not one that stops an upload, and on a `refused_on_device`, and clears it when the link closes. While it is set, the device page shows the `refused_on_device` note with Reconnect, and holds every button that asks a question. A notice about a `set` is marked `during: 'set'`, and the device page shows it under Save rather than on the firmware page.

Sizes come from the device, never from a constant. Web Bluetooth exposes no MTU, but smp_bt cuts every reply at MTU-3, so before the first upload `smp.js` sends an OS echo longer than any ATT payload, in 20-byte writes, and reads the write size off the first slice of the reply. This device's local ATT MTU is 498 (`CONFIG_BT_BUF_ACL_RX_SIZE` 502 less the L2CAP header, and `CONFIG_BT_L2CAP_TX_MTU`), so a Chrome that asks for 517 settles on 498: 495-byte writes. Each image-upload request is then one write of that size, carrying about 470 bytes of image, the way mcumgr-web sizes a chunk to one write. If the browser refuses a write anyway, the size steps down through 244 and 182, the payloads of MTU 247 and 185, to 20, and the upload resumes. A device that does not echo gets the whole `buf_size` packet (`CONFIG_MCUMGR_TRANSPORT_NETBUF_SIZE`, read from the OS group's parameters) in 20-byte slices, which `CONFIG_MCUMGR_TRANSPORT_BT_REASSEMBLY` puts back together. Replies are reassembled on the length in the header. The first upload packet carries the image's SHA-256: img_mgmt answers a second upload of the same image with the offset it reached, so a window that closed mid-image resumes rather than restarts, as long as the device has not rebooted.

### A link that never exchanged its MTU

The unit asks for a larger MTU itself right after a connection, so a link stays at the default only when the phone answers 23 or refuses (`firmware/core/comms/README.md`, Three endpoints). At the default ATT MTU of 23 a notification carries 20 bytes, and the unit answers a reply that does not fit with `{"acknowledge":false,"reason":"small_mtu"}`, 8 bytes, and counts it in `link_drops` (`firmware/core/comms/README.md`, "A reply too wide for its link"). `update.js` and `activation.js` turn it into the `small_mtu` notice whatever they were doing, and the briefing app words it: the phone or browser kept Bluetooth's smallest packet size, so disconnect and connect again, and failing that update the browser and the phone or use another one; the console prints the same under the frame. The status, 20 bytes at its widest, and every acknowledgement, 11 at most, always fit, so the page knows the flight state and hears every prompt and verdict. The `update` frame fits only while it carries neither versions nor a digest: 15 bytes for a confirmed image on a release build whose hub holds no verified blob, 17 on a development build, which adds `downgrade`, and 19 once it also reports a settings fallback; `imu_digest` takes it to 25. The `identity` reply, 31 bytes at the least, never fits, and the page goes on without it. Asked for, a wider one is answered `small_mtu`; pushed at connect, before most centrals exchange their MTU, it is dropped without a word, and the exchange's late `Up` pushes it again. The config reply is 20 bytes for a unit not yet activated with an empty callsign and no aircraft address, 22 with an address from 1 to 23, 23 from 24 to 255 and 24 past it, every callsign character adds one, and an aircraft address up to four: past 20 the page shows no settings and says `small_mtu`, so only a unit not yet activated, with no callsign and no aircraft address, shows its settings at this MTU. `defaults` fits, and so does the `protocols` reply, 18 bytes on a Go and 11 on a Bravo. The challenge reply, 27 bytes, never does: an activation stops at its first step with `small_mtu`, with nothing sent to the server. The writes arrive, as long writes Zephyr reassembles from up to `CONFIG_BT_ATT_PREPARE_COUNT` (2) prepare segments, 36 bytes, which carries every command but `register` (88) and `unlock` (74): `dfu` at its widest version is 18. SMP answers too, because smp_bt cuts its replies at MTU-3, so an install runs on such a link, asked on the glass, in 20-byte writes; without the `identity` and `update` frames the page knows neither the unit's product nor its key, so the published list stays empty and the unit checks the product and the key of the file chosen by hand itself.

`ble.js` queues every GATT write, config and SMP alike, behind the one before it, because a write issued while another is in flight can fail.

`cbor.js` is the one CBOR codec, for SMP and the link: integers, strings, byte strings, arrays, maps, booleans and null, definite and indefinite length (zcbor opens every map as indefinite), floats and tags on the way in only. `decode(bytes, { deterministic: true })` is the link's grammar, the one the firmware and `blip.py` read too: one map, its keys unsigned and ascending, every head in its shortest form with an argument of at most 32 bits, no indefinite length, float, tag or null, nothing nested but an array of unsigned integers, and text that is UTF-8. It hands the map back as a `Map` keyed by number, and leaves the generic decoding SMP needs untouched. `link.js` holds the link's names over it, from `link_registry.js`, which `scripts/link_registry.py` generates from the registry and `scripts/check_link_registry.py` holds to it, so it is regenerated, never edited. `encodeFrame()` takes an object keyed by full names, an enumeration by its name or its code and a byte string as a `Uint8Array` or hex, refuses a value its key's type does not take (`blip.py` refuses the same ones), and writes the keys in ascending order; `decodeFrame()` gives the names back, enumerations by name and byte strings as `Uint8Array`, and a key or a code the registry does not hold stays a number. Both throw `FrameError`, and `schemas/link.v1.vectors.json` lists what each refuses. Everything above `ble.js` sees only names.

## Trusted browsers

A unit trusts a browser that proves a key a press once approved, and asks it for no press after that (`firmware/core/comms/README.md`, Trusted browsers). `trust.js` holds both halves of the browser's side.

- **The key.** `storedBrowserKey()` generates an Ed25519 key pair the browser cannot export, the first time, and keeps it in IndexedDB, database `skyblip`, store `keys`. One key serves every unit this origin meets in this browser profile, so clearing the site's data loses it and the next save asks for the press again. A browser without IndexedDB or without Ed25519 in WebCrypto has no key and asks for presses as before. Chrome has Ed25519 since version 137.
- **The proof.** On every connection, before the page reads anything, `BrowserTrust.prove()` sends `browser_challenge`, signs `skyblip:browser:v1` followed by the nonce, and sends `trust_browser` with the key and a label, such as `Chrome on Android`, that `labelOf()` builds from `navigator.userAgentData`, in English whatever the page's language, since the unit stores it as it came. The verdict sets `state.trust`: `trusted`, `proven` for a key the unit does not hold yet, or null when the browser has no key or no verdict came. A save or an install that a press then allows turns `proven` into `trusted`, as the unit does.
- **What it changes.** A trusted page saves with no prompt, in flight too, so the settings form stays open in flight and the notes say everything else waits for the landing. Its install opens the upload window with no prompt, its activation gets the `registration` frame with no prompt, and its pairing starts on the Go and stands armed on Bravo with no press (Pairing from the briefing). Every other question still goes to the glass. A save, an install, an activation or a pairing that a press allows turns `proven` into `trusted`, as the unit stores the key on that press.
- **Trust from the install.** A unit installed over USB from this browser trusts it from its first boot, so the browser never sees `proven` on it (The installer).
- **The list.** On a trusted unit the device page lists the trusted browsers under `Trusted browsers`, marks this one, and offers to forget one or all the others. A browser that forgets itself is untrusted from then on.

## The devices a browser knows

`fleet.js` holds every device the app has met, as a `Unit` named by its slug, `go-00012a` for `skyBlip Go 00012A` and `skyBlip Go+ 00012A` alike, `bravo-3f2a` for `skyBlip Bravo 3F2A`, `activate-3f2a` for a Go not yet activated. A unit connected once is written to `localStorage` under `skyblip.devices.v1` with its name, product, address, firmware and track, the newest image it was offered and whether that image is a release, its settings, the tag of the unit it is paired with and when it was last seen, and listed again after a reload. `tangoGroups()` orders the list: Go first, then Go+, then Bravo, a Go by its address and a Bravo by its tag. A Bravo goes under the Go it is paired with, by either unit's `paired_tag`. The rail nests it under its Go on a computer, and joins the two chips into one on a phone. A unit not yet activated is written only once it holds its address, under its new name.

`ble.js` holds one GATT link per device and shares it between every client of that device, the `Updater` and the `Activator` alike, so several devices stay connected at once. A device connected once in a page's life connects again with `device.gatt.connect()`, without the chooser: Reconnect after a refusal on the glass, and the `Updater` itself after an install restarts the device, trying every three seconds for two minutes. A device remembered from another visit has no handle, so Connect opens the chooser filtered to its name, and the pilot sees one entry. A handle Chrome lost track of, on a page left open for hours, fails with `NetworkError`, `Bluetooth Device is no longer in range.`, until a scan sees the device again: the `Updater` drops it, and the same Connect opens the chooser filtered to its name. `navigator.bluetooth.getDevices()` hands back the devices a browser granted, but only behind Chrome's `#enable-web-bluetooth-new-permissions-backend` flag today: where it answers, `restore()` connects the remembered ones on its own.

## What the browser lacks

`readiness.js` says whether this browser can reach a device over Bluetooth, and what to switch on when it cannot. Chrome and Edge ship Web Bluetooth on Android, ChromeOS, macOS and Windows. On Linux they keep it behind `chrome://flags/#enable-web-bluetooth`, and `navigator.bluetooth` is missing until it is set. `getAvailability()` says whether an adapter is present, not whether it is on, and `availabilitychanged` says when that changes. `BluetoothReadiness` turns them into three checks: the Linux flag, the adapter, and the optional flag `getDevices()` needs. Connect shows only while Web Bluetooth is present and the adapter is not known to be missing. While either required check fails in a Chromium browser, the rail shows `briefing/_bluetooth_check.html.erb`, which lists each step with the address or the command to copy. A flag clears once Chrome's relaunch reloads the page, and the adapter clears as soon as Chrome reports it. A browser no flag fixes, such as Firefox or Safari, gets the words that send the pilot to another browser. A page can neither read `chrome://flags` nor link to it, so the list reads only what the APIs expose.

## The installer

`/briefing/setup` takes a unit that still runs Meshtastic to a connected skyBlip in one page, `controllers/setup_controller.js`, over its USB cable first and Bluetooth after. `installer.js` holds the steps as a state machine, `meshtastic.js` the little of Meshtastic's serial API it needs, and `uf2.js` the release file. It needs Web Serial and the File System Access API's folder chooser, which only Chrome and Edge on a computer have. A phone or a tablet never installs, even where its browser has both, because Samsung Internet on Android closed its port chooser empty within 17 ms every time: `browserSupport()` reads the system from the client hints, or from the user agent, before the APIs.

1. **Restart.** Install opens the serial chooser, filtered by USB vendor: Adafruit's 0x239A, which the T-Echo's Meshtastic uses, and Seeed's 0x2886. `MeshtasticLink` frames the serial API as Meshtastic does, `0x94 0xC3` and a 16-bit length before each protobuf, skips the log text the node prints until it hears a frame, and asks `want_config_id` with Meshtastic's config-only nonce, 69420. It reads `my_info.my_node_num` and the metadata's `hw_model`: 7, a T-Echo, and 33, a T-Echo Plus, are Go boards, 128, a MeshTracker X1, is Bravo's. Meshtastic numbers a nRF52 node by the low four bytes of FICR DEVICEADDR, and skyBlip tags a unit by the low two, so the node number's low 16 bits are the tag the unit will advertise, `activate 3F2A skyBlip` or `skyBlip Bravo 3F2A`. It then sends an admin packet to its own node with `enter_dfu_mode_request`, which Meshtastic accepts from its local client without a session key, and which restarts the board into the factory bootloader as a USB drive. A port that does not answer in four seconds is no Meshtastic node, and the page shows each product's gesture to start the bootloader by hand, each beside its photo with the contact marked (`shared/_device.html.erb`): RESET twice on a Go, the button held while plugging in on Bravo until its LED turns white. Serial DFU is no shortcut, because the bootloader would store a CRC that the first MCUboot swap breaks (`scripts/mkuf2.py`).
2. **Write.** Choose the drive opens the folder chooser. The page reads `INFO_UF2.TXT` and takes the product from its `Board-ID`, `nRF52840-TEcho` or `nRF52840-MeshTracker-X1`, over what the port said, and refuses any other drive before writing. It downloads the release `.uf2` the `installers` frame names, the newest stable release holding one for that product or else the newest main build (`Release.installers`), and checks that the image at slot0 names the product. With a browser key, `withTrustRecord()` adds the install trust record on the first 4096-byte page after the image and its TLVs: `skyblip:trust:v1`, the browser's raw Ed25519 public key, the label length and the label in 24 bytes, and a CRC-32 over the 73 bytes before it, as `firmware/core/comms/README.md` lays it out. The page replaces whatever blocks the release wrote at that page, so the bootloader sees one block per address. The file goes to the drive as `SKYBLIP.UF2`. The bootloader restarts the board once the last block lands, and the drive going away can fail the write that carried that block or the close, as Chrome did on a T-Echo. Closing the drive picker records `drive_closed` and lets the pilot try again without reopening the serial port. The page writes the last block on its own. A failure before it is `write_failed`. A failure on the last block or close leaves the write ready for verification and keeps the browser's error in `installer.wrote`.
3. **Verify.** The page opens the Bluetooth chooser filtered to the name the tag gives, or to `activate` and `skyBlip Bravo` when it knows no tag. It records `installer.verified` when the product and exact build match the UF2 image and the unit reports a confirmed image. `installer.finished` records setup completion and whether the pilot saved aircraft settings separately. A Go also lists under `skyBlip Go`, since a Go activated before keeps its activation through the install and advertises its address, which the page cannot know. A Go is then activated without a click: the unit trusts this browser from the record, so `register` asks no press. One activated before goes straight to its aircraft.

### From a computer to a phone

A unit installed over USB still needs Bluetooth to be activated and set up, and a computer often has none, or Chrome on Linux has Web Bluetooth off. The page reads `bluetoothReadiness()` before anything else. Where Bluetooth does not work and the flag is not the cause, the start step says the setup ends on a phone. After the write, the Connect step shows a QR code instead of Connect, and still offers the fix on the computer below it. The code opens `/briefing/setup` on the phone with the product, optional tag and expected build. `Briefing::Handoff` checks the parameters, and `Briefing::Setups::HandoffsController` draws the code as SVG with rqrcode. If a Go's activation still returns `small_mtu` after one reconnect, the pilot can disconnect the Go and open setup on an Android phone. The activation notice records the last command sent, so support can distinguish a failure near the challenge from one near registration. The phone opens on the Connect step, with the chooser filtered to the unit's name. The phone holds no trust record, so the Go asks for one press to activate. The activation then makes the phone trusted.

The page also keeps the unit it installed in `sessionStorage`, under `skyblip.setup.installed.v1`, until the setup ends. A pilot who leaves the page and comes back in the same tab finds the unit on its Connect step, with Install another device beside it. That is the trail of the first pilot who installed without an adapter: Windows had no Bluetooth, and the pilot opened the activation and the console, then went back to Install.

On a phone with Bluetooth and no parameters, the page opens on Connect it, for a unit installed from a computer, and says how a new unit gets installed. A Go not yet activated is activated on the page, rather than on `/briefing/activate`, so the setup goes on to the aircraft. A typed `skyblip.eu/setup` redirects to the setup. A phone without Web Bluetooth, such as an iPhone, gets the link to copy into Chrome on Android. `installer.handed_off` and `installer.resumed` record each side.
4. **Pair.** When the page was opened from a unit's offer to set up its partner, `?for=go-000003`, and that unit is still connected, it pairs the two with `pairTango()` (Pairing from the briefing).
5. **The aircraft.** The last step names the aircraft in the order a pilot can: a Go alone asks for its type and callsign, both optional, with the transponder address folded under them. A Tango asks for nothing, because the Go offers the address, callsign and type its Bravo hears once the transponder is on `ALT` in the aircraft, and one press on the Go takes them. A Bravo alone says to open Briefing in the aircraft, where the device page proposes the address Bravo hears, and folds the address under the text for a pilot who knows it. Set them now, or a typed value, turns Done into Save, which sends one `set` to the Go, or to Bravo alone, with no press from a trusted browser. The page then says the unit is ready, opens it, offers to set up the other product when this browser knows none, and links the first-steps guide of each product it set up, `go-first-steps` or `bravo-first-steps`, both for a Tango. Every setting stays on the device page.

The port's USB ids say what the unit runs before anything is sent (`portOf()`): 0x239A:0x0029 or 0x002A is the T-Echo's bootloader, which goes straight to its drive, 0x239A:0x8029 is SoftRF, which has no way to restart into the drive and gets the RESET gesture at once, and 0x239A:0x4405 is Meshtastic. Any other port is asked as Meshtastic, and one that answers nothing in four seconds gets its product's gesture, taken from the USB vendor, or both gestures when the vendor names no product. These ids come from the firmwares' build files and are unverified on a unit. The words never name Meshtastic or SoftRF, since a pilot need not know what the unit shipped with. An empty or closed port chooser most often means a charge-only cable, or a unit already running skyBlip, which has no USB port, so the notice offers Bluetooth. Chrome reports a port another program holds and a port the user may not open with the same `NetworkError`. On Linux the serial device belongs to the `dialout` group, `uucp` on Arch, so there the notice adds the `usermod` command that lets the user open it.

No page can check a Linux computer's setup before it fails, so on Linux the start step lists what to do once per computer: join `dialout`, then log out and back in, and let Snap Chromium see USB drives with `snap connect chromium:removable-media`. While Web Bluetooth is off, it asks to turn it on first, because Chrome restarts to apply the flag and the page loses its step. The drive step says to open the drive in the file manager when Linux has not mounted it. After the install, Connect waits for Bluetooth: once the flag is on, the pilot connects from Your devices after the restart, and once the adapter is back, Connect appears on the page without a reload.

The installer records its trail in the journal as `installer.*` (`app/models/event/README.md`): each step with how long the one before lasted, the port's USB ids and the firmware they point to, the board and firmware version Meshtastic gives, the drive's Board-ID, the write with its version, whether it carried the trust record and how long it took, every notice with its step, and the end card with what the unit became and whether the aircraft was named. None of it holds what a pilot typed.

## Pairing from the briefing

A Go and a Bravo connected in the same page are offered the pairing on either device page, under the settings (`controllers/tango_controller.js`). `tango.js` decides what the card offers from the fleet: the pairing when the other product is connected, Connect when it is only remembered, Set up and Connect when none is known, and Pair instead when the unit is paired with a unit other than the one connected. A unit's tag comes from the `identity` frame and is kept in the fleet's record, and the unit it is paired with from the config reply's `paired_tag`. Nothing is offered in flight or before a Go is activated.

`pairTango()` sends Bravo `pair` with the Go's tag first, so its acceptance stands armed when the Go's request arrives, then the Go `pair` with Bravo's tag. A trusted Go starts at once and an untrusted one asks on its glass, `confirm_pair`, which the device page draws. The Go answers `pair` when it starts and `paired` once both sides hold the pin, or its refusal, `not_found` and the others the firmware names. The page then reads Bravo's config again. A Bravo that does not trust this browser is not sent `pair`: it pairs by its own press on the blue blink, which the card asks for beside Bravo's photo with its button marked, and its `untrusted` refusal would read as a trust verdict to `trust.js`.

## The activation client

`activation.js` is what `/briefing/activate` runs, and like `update.js` it holds the dialect as a state machine and hands every change to one callback; `controllers/activation_controller.js` draws it with the words of `config/locales/briefing.*.yml`. It rides the link the device's `Updater` opened, so activating needs no second connection. It speaks to two parties: the unit over the config endpoint, and this server through `httpServer()`, which posts JSON with the page's CSRF token. The frames are [`schemas/link.v1.json`](../../../../schemas/link.v1.json)'s, the requests to this server and the messages their signatures cover [`schemas/activation.v1.schema.json`](../../../../schemas/activation.v1.schema.json)'s.

Connect sends `get`: a unit that reports no `address` is not activated, and `update.js` reads the same key, so the app sends such a Go here. Activate sends `challenge`, posts the nonce and the server key id it answers to `/activation/challenges`, and hands the signed answer to the unit as `register`. The two requests to this server stay JSON over HTTPS, where every byte string is hex: the client hexes the byte strings of the frames it relays, and the server's hex goes back to the unit as byte strings through `encodeFrame()`. The unit asks on its glass (`confirm_register`), and one press answers the `registration` frame, which the client posts to `/activation/registrations` beside the server nonce. A unit that trusts this browser answers `registration` at once, with no prompt, which the client takes in place of the press. The serial and its unlock code go back to the unit as `unlock`, and `{"acknowledge":true,"reason":"unlock"}` ends it: the client sends `get` again and shows the address.

A refusal from the unit is its `reason`, a refusal from the server its `error` prefixed `server_`, so the two `bad_signature` and the two `expired` keep their own words.

Once the unit holds its serial, the page opens the device's settings, where the aircraft type, the callsign and the aircraft address come first. The aircraft address is the one setting the form shows in another shape than the unit holds it: `settingsOf` turns the unit's 24-bit `aircraft_address` into its six hex digits, and 0, unset, into an empty field, and `settingsFrame` turns them back into the number a `set` carries, 0 for an empty field, which clears it. The field takes six hex digits or nothing, so a partial address never reaches the unit. Since ADS-L F.2.3 the Go transmits under that address, and it refuses two: `FFFFFF`, which ICAO assigns to no aircraft, as `out_of_range`, and any address other than the transponder a paired Bravo hears as the aircraft's own, as `not_own_transponder`. The page words both under `set_notices`. While the unit's `status` names the transponder Bravo hears on the ground, the page proposes it at the top of the Aircraft section: a table lists each field it would change, what the form holds now and what Bravo hears, on a Go the aircraft type, then the callsign and the address, as the Go's `AIRCRAFT` menu stores them. One button fills them in, and nothing reaches the unit until Save. A Bravo stores only `aircraft_address` and `alarm`, so the page hides and disables the field of every setting the unit's `config` does not carry, rather than show one whose edit Save would never send. A Go's `config` says `annunciator_fitted`, whether it has a buzzer or a haptic, and `soundsOf` reads it. A Go with neither refuses `soft` and `loud` unless it is paired with a Bravo, so the page offers it only `off` and `visual`, and `soft` and `loud` too, named `Bravo soft + visual` and `Bravo loud + visual`, while its `status` carries `bravo`, which a paired Go always sends. Its `defaults` answer `loud` while paired and `visual` alone, so the default line follows. The page's copy of the Go's prompt is told the same two facts, so it reads `BRAVO SOFT` and `BRAVO LOUD` as the Go's glass does. A Bravo paired with a Go plays that Go's alarm, which the Go's `ALARM` row sets for both, so its `config` carries the Go's `alarm` with `alarm_from_go` true and it refuses a `set` of `alarm` as `set_on_go`. `settingsOf` then leaves `alarm` out of the settings the form edits and sends, `goAlarmOf` keeps it apart, and the page shows it in a closed, dimmed field over the hint `Your Go's ALARM row sets it for both units.`, which the field names as its description only then, so no save can leave Bravo disagreeing with its Go.

## The traffic comparison

`/briefing/comparison` puts two receivers side by side in one page: a SoftRF Retro Mk II on USB serial and a skyBlip Bravo on Bluetooth, each named by the view and its transport with it, so a test flight shows which aircraft each one heard, how far, how steadily, and which heard it first. `controllers/comparison_controller.js` draws it, `controllers/comparison/tables.js` builds its tables, and the modules below know nothing about the page.

`serial.js` opens the port Web Serial offers at the chosen baud rate, 38400 by default, which is what the Retro Mk II speaks over its CH340 (SoftRF wiki, Retro Edition MkII). Web Serial runs in Chrome or Edge on a computer. Chrome on Android lists no USB serial adapter, so the Retro needs a laptop. Every read goes to both decoders at once, because SoftRF sends GDL 90 by default and NMEA when set to: `gdl90.js` frames and checks GDL 90, and `nmea.js` splits and checks NMEA. NMEA text never holds the GDL 90 flag, `0x7E`, and a binary line fails the NMEA checksum, so neither decoder takes the other's bytes. The Bravo arrives through `ble.js` as the console's stream does.

`nmea.js` reads `$PFLAA`, `$PFLAU`, `$PGRMZ`, and `RMC` and `GGA` from any talker. A `$PFLAA` ID may carry the callsign after a `!`, as skyBlip and OGN send it. `gdl90.js` reads the heartbeat, the ownship report, the ownship geometric altitude and the traffic report of the GDL 90 Data Interface Specification, 560-1058-00 Rev A, and `test_gdl90.mjs` holds it to the specification's own heartbeat and traffic report examples. A field the message marks unavailable decodes to `null`, never to 0.

`traffic.js` folds both into one `TrafficPicture`, by receiver and by 24-bit address. A `$PFLAA` is relative to its receiver, so its distance is its own and its position needs that receiver's fix. A GDL 90 report is absolute, so its distance and its height above us are measured from the reference: the first receiver of `referenceOrder` with a fix heard within `LIVE_MS`, 10 s, and its pressure altitude. The page orders the Bravo first, because the two ride in one aircraft and a Retro without its own GNSS has no ownship report to measure from. A target is live while its receiver reported it within `LIVE_MS`.

Both receivers send their whole table every second whether they heard the aircraft again or not, so a report count measures how long a receiver held a target, not how often it heard it. The picture keeps one sample a second for each target and receiver, and reads steadiness from those. Listed is the share of the seconds either receiver listed the aircraft that this one did. A dropout is a gap longer than `DROPOUT_S`, 3 s, and the longest gap is kept too. A new position is a GDL 90 report whose position differs from the one before: SoftRF exports the last position it decoded, so a repeat means nothing new was heard. `$PFLAA` cannot tell them apart, since the Bravo dead-reckons every target to the moment it sends and SoftRF's NMEA moves with the receiver, so a `$PFLAA` target counts no new positions. The RSSI is the last `$PFLAA` field, shown when a receiver fills it. SoftRF on the Retro's STM32 sends none, in either protocol.

The two lists show different fields because the two receivers speak different protocols: GDL 90 sends an absolute position, the pressure altitude, NIC, NACp and the ADS-B emitter category, and `$PFLAA` a position relative to its receiver, a FLARM aircraft type, and on a skyBlip the source. SoftRF also filters what it exports. It leaves out of GDL 90 an aircraft farther than 25.5 km while it has its own fix (`ALARM_ZONE_NONE`), out of NMEA an ADS-B aircraft farther than 75.5 km (`ALARM_ZONE_NONE_EXT`), and out of both one it has not heard for 5 s (`EXPORT_EXPIRATION_TIME`). The Bravo forgets an airborne aircraft after 6 s and one on the ground after 60 s (`docs/TUNING.md`), so a ground target stays listed longer on the Bravo.

Picking an aircraft in the table or on the chart opens it beside the chart: its fields in common units for each receiver and their difference, how far apart the two receivers place it, and `timeline.js`, the last 15 minutes at most as one lane per receiver, a mark for each second it was listed and a tall one for each new position, over its distance and its RSSI.

`chart.js` draws the France OACI 1:500 000 chart from IGN's Géoplateforme, whose WMTS template is `config.x.oaci_chart.tiles`, with the receivers' aircraft over it. IGN serves the chart at zooms 6 to 11 and allows browser fetches, and the chart stretches zoom 11 for 12 and 13. IGN's terms make SCAN OACI free for professional and non-profit use and charge for a commercial product sold to the public, so the chart stays on this internal page. Save the chart offline fetches the area around a point, 100 km around Merignac by default, at zooms 7 to 11, 353 tiles, into Cache Storage, and every tile is read from there first, so the chart draws with no network in flight. Cache Storage needs https or localhost, and the page itself is not saved, so it is opened before takeoff.

The page keeps every sentence and frame it decoded, with the raw line or frame in hex, and Download NDJSON saves them for analysis after the flight. The log lives in memory until the page closes.

## The terminal

Each device page has a terminal under it, `/briefing/devices/go-00012a/terminal`, which prints every frame this browser exchanges with the device, in both directions: NMEA lines, config and log frames by their registry names, and SMP packets by op, command and sequence number. `controllers/terminal_controller.js` draws it, and `terminal.js` turns each frame into its line. The terminal opens no link of its own. It calls `tap()` in `ble.js` with the device's handle, which hangs a listener on the device rather than on its link: the listener hears every client's writes and every notification, and it keeps listening when the link drops and comes back, so a reconnect shows from its first `update`. A tap must never cost the update client its link, so it hears a notification before the clients do, which also prints a write a client makes in answer after the frame it answers. A listener that throws is logged on the console and fails no write. A tap opens the NMEA and log endpoints, which no page client asks for, through the same queue as the writes, so a terminal opened during an upload subscribes between two chunks. When the last tap lets go, the endpoints no client asked for stop notifying, so NMEA takes nothing from a later install. A write the browser refuses prints as `failed` with its endpoint and reason. A frame is printed as it was sent, so an SMP reply cut at MTU-3 shows as its slices, and a byte string past 16 bytes, such as an image chunk, shows its first bytes and its length. An SMP reply carrying `rc` or `err` is marked as a refusal. The tape keeps the newest 2000 lines. An endpoint unchecked keeps no lines, so NMEA cannot push the config frames out. Each visit starts on an empty tape, since the snapshot Turbo restores lacks every frame since. The peer endpoint is not tapped, because only a Go reads it from a Bravo.
