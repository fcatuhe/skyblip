The Rails app serves the simulator, the Bluetooth console and the traffic comparison under `/briefing/simulator`, `/briefing/console` and `/briefing/comparison`.

Reusable browser modules live here and their Node tests live in `server/test/javascript/`. Rails importmap pins `#skyblip/*` to digested assets, and `server/package.json` maps those same module names for Node's native test runner. Serving the app needs no Node runtime, package install, or bundler.

The simulator loads `embed.js`, its generated JavaScript module, and WASM from same-origin `/releases/:tag/:file` URLs after a lazy Turbo frame selects a release. Its case styling is app-owned in `server/app/assets/stylesheets/simulator/device.css`. The firmware's own `firmware/simulator/web/embed.js` remains usable by `server/bin/screenshots` without Rails.

## The console

`ble.js` is the transport and knows nothing about what a page draws: it connects, reassembles the stream, and hands whole lines and decoded frames back. `controllers/console_controller.js` renders the console UI. `test_ble.mjs` pins down the reassembly, because a sentence cut across two notifications is the failure that looks like a firmware bug from the page.

The picker lists anything advertising Nordic UART or HM-10, which is skyBlip and SoftRF both, so the same page is how you read one and configure the other.

**The serial endpoint** is the traffic picture: `$PFLAU`, `$PGRMZ`, `$LK8EX1`, a `$PFLAA` per target, `$GPRMC`/`$GPGGA` with a fix. A notification is a slice of a byte stream and not a sentence, so `ble.js` splits on line ends rather than on notifications, the way an EFB does.

Writing to it reaches skyBlip's `on_stream_write`, which discards everything: that characteristic exists because XCSoar refuses a UART service without one (`firmware/hardware/platform/zephyr/link.cpp`). SoftRF is the opposite and takes its whole configuration there, as `$PSRFC` sentences. `$PSRFC,?` dumps the current settings; echoing that line back with one field edited and field 1 set to the protocol version (`1`) stores it, after which SoftRF drops Bluetooth, writes EEPROM and reboots. A sentence typed without a `*` leaves with its checksum appended, because SoftRF drops what it cannot verify. Send all 19 fields: an empty term still counts as updated and reads back as zero.

**The config endpoint** is skyBlip's own, `69c21302`, one CBOR frame per write and one per notification, its keys the numbers of [`schemas/link.v1.json`](../../../../schemas/link.v1.json). `link.js` turns a plain object keyed by full names into that frame and back, so the console shows each reply as JSON and its text field takes JSON, byte strings in hex either way. The buttons cover `get`, `defaults`, `status`, `timing`, `flash`, `radio`, `update` and `diagnostics`; the text field sends anything else, `set` included, and refuses a name or a value the registry does not hold before anything is written. The rules the firmware enforces are in `firmware/core/comms/README.md`: the first session to write claims the endpoint, a `set` is refused in flight and on a low cell, and what survives those two is staged for a button press on the device.

A frame travels in one write because the unit reads each write as one whole CBOR map and answers one cut short `no_command`. `ble.js` writes config with response and chunks only the serial stream, where 20 bytes is what BLE guarantees and Web Bluetooth exposes no MTU to do better.

**The capture panel** arms, stops and fetches a diagnostics capture without `blip.py`. Arm and Stop send `{"command":"capture","profile":...}` with the profile chosen, or `"stop"`, on the config endpoint, as `scripts/blip_capture.py` does, and word the prompt and the verdict from the acknowledgements the console already hears. Fetch speaks the log endpoint, `69c21303`, through `log.js`: `list` for the count of sessions, `list` with the last index for its entry, then `read` windows of eight chunks from the index reached until a chunk `ends_session`, which is `blip.py fetch --log diagnostics` without `--all`. `diagnostics.js` decodes each 24-byte record as `scripts/blip_records.py` does, and writes the same NDJSON lines, a `session` note, the records and a `torn` note for the last record of a session the unit never closed, with Python's `json.dumps` spacing, so the panel's download and `blip.py fetch --out` are the same file. Fetch passes over a frame that answers no question it asked, such as a chunk of a window an earlier fetch abandoned, of whatever session and index, because the console keeps its link between fetches. The panel gives up on a verdict after 35 s, as `blip_capture.py` does. The table keeps the latest `adsb` record of each address. The `Adsb` record carries no callsign, so the table has none.

## The update client

`update.js` is what the device and firmware pages of the briefing app run, one `Updater` per device that `fleet.js` holds, and it knows nothing about the pages either: it holds the device's update dialect as a state machine and hands every change to one callback. The page renders that state and looks the words up in its own tables, so the two languages live in the page and not here. Importmap resolves the shared module names directly to Rails assets, with no build-time copy.

The update is two channels, and the device refuses the usual mcumgr sequence on purpose (`firmware/core/comms/config.cpp`, `core/dfu/smp_policy.h`). The frames below are written as `link.js` decodes them, and an acknowledgement's `"command":"acknowledgement"` is left out.

Before any of it, the page checks the chosen file against what the device said in its `update` frame, and refuses what the bootloader would. `key` names the signing key the bootloader trusts, the first four bytes of its hash as imgtool writes it in the image's KEYHASH TLV, which the page reads in hex: a file signed by another key is `wrong_key`. `downgrade: true` marks a development unit: without it, a file older than the running image is `older`, and the same version passes, so a release can be installed again. `product` names the product the unit runs, `skyblip_bravo` today. A Go leaves it out, as all firmware before the key did, and `productOf()` takes a unit that names none for a Go, a unit whose `update` frame never arrived included: a file whose image class names another product is `wrong_product` (`firmware/core/dfu/README.md`), so a Go on firmware without the check never receives a Bravo image from the page. A file naming no product, an image built before the class, is `unmarked_image` for a unit that names its product. The same key hides the published files of another product, and keeps the not-activated note off a skyBlip Bravo, which has no address.

The device checks all three again for any client, page or not: the version at `dfu` and on the first chunk, the product on the chunk that completes the image's protected TLVs, refused as image error 5 (`IMG_MGMT_ERR_INVALID_TLV`), which the page words as `wrong_product`, or as `unmarked_image` for a file naming no product, the one a Go cannot refuse before it is sent, and the key once the image has landed.

1. `{"command":"dfu","version":"0.2.0+15"}` on the config endpoint, the version read off the image header. The device answers `confirm_dfu` and asks on its glass, naming that version; two presses answer `{"acknowledge":true,"reason":"dfu"}` and open a ten-minute upload window, on the ground only. A `dfu` without a version is refused as `no_version`, and on a release unit a version older than the running one as `older`. An install also runs on a link that never exchanged its MTU (see "A link that never exchanged its MTU" below).
2. The image over MCUmgr/SMP, image group, upload command: the only SMP write the device accepts, and only inside that window. `smp.js` sends SMP v2 headers, so the image group's own error codes come back (`err`) rather than the generic `rc` the original protocol folds them into; a refusal by the command hook is still a bare `rc` 11. An image older than a release unit allows is refused on its first chunk with the image group's 27, read as `older`: the check `dfu` makes, for a client that never sent one.
3. Nothing more is asked. The glass says RECEIVING through the upload, and one press on it answers `{"acknowledge":false,"reason":"cancelled"}` and closes the window. Once the last chunk is on flash the device closes the window and gives its verdict unasked: `{"acknowledge":true,"reason":"install"}`, or a refusal, `not_approved` for an image other than the version the glass named, `wrong_key` for one signed by a key its bootloader would not verify, `nothing_staged` for a slot it cannot read back, `in_flight` and `low_power` as at the door. The verdict can arrive before the reply to the last chunk. An SMP `image state` write or `os reset` is refused, so none is sent.
4. After `install` the device paints INSTALLING, reboots into the swap, and the link drops. On the next connect it pushes the `update` frame unasked whenever the image is not confirmed, or (with #90) its settings fell back, and `update.js` reads that frame whenever it comes. `reverted` is an image that started and never confirmed itself, so the bootloader swapped the old one back. `refused` is an image the bootloader never started: it scrambles slot 1 instead, which is how the device tells the two apart.

The same client edits the settings. On connect it sends `get` and `defaults` beside `update` and `status`: the stored settings, and the values the firmware ships on, so the page compares the two without a copy of the defaults of its own. A firmware older than `defaults` answers `unknown_command`, and the page offers no reset. `saveSettings()` sends a `set` carrying only the keys that differ from what the device reported; `resetSettings()` is the same call with the defaults. The device answers `confirm` and asks on its glass, two presses answer a bare `{"acknowledge":true}`, and the client asks `get` again so the page shows what the device stored rather than what it sent.

The same client arms a skyBlip Bravo's diagnostics capture, which has no glass to arm it on (#247). `orderCapture(profile)` sends `{"command":"capture","profile":"power_run"}`, or `stop`. The unit answers `confirm_capture` and blinks its prompt on the lamp, and two presses answer `{"acknowledge":true,"reason":"capture"}`, which the client turns into the `capture_armed` or `capture_stopped` notice. Bravo refuses an arm while a capture runs as `capturing`, a stop while none runs as `not_capturing`, and a unit with no capture flash as `no_storage`. The unit reports no capture state the page could read first, so the page offers both buttons and words the refusal. Every notice about a capture is marked `during: 'capture'`. The device page in `/briefing` shows the control below the firmware row, only for a unit whose `update` frame names `skyblip_bravo`, draws the lamp's prompt while it asks, and words each notice from `briefing.capture_notices`. A Go answers `unknown_command`, because its captures are armed on its glass only.

An install, a recovery and a `set` are refused on the page as `in_flight` while the last `status` says `airborne` (`inFlight`), before the device would refuse them itself, and asked on `ground` and on `unknown`, a unit with no fix since boot (`firmware/core/comms/README.md`, The flight gate). The page holds Install, Restart into the USB drive, Save and Back to defaults while `inFlight`. The device pushes `status` when its flight state changes, so the page unlocks on landing without polling. A firmware from before that gate refuses `in_flight` on `unknown` too, and the page shows the refusal and leaves the buttons as they are.

A release has two OTA images of one commit and one version, because the BHI260AP's firmware lives on its own partition of the external flash rather than in every image: `skyblip-go-<version>.signed.bin` (`skyblip-go.signed.bin` from a local build), the slim one, boots the sensor hub from that partition, and `skyblip-go-<version>.full.signed.bin` carries the blob and writes it there once it is confirmed, if the partition does not already hold it. Each image says which it is in two protected TLVs, signed with it: `0x00a0`, the SHA-256 of the blob it pins, and `0x00a1`, one byte, `1` for the full image. `image.js` reads both off the protected TLV area, and an image without one (anything built before the split) pins nothing. The device's `update` reply says what its partition holds in `imu`: `none` (no hub answered, a plain T-Echo), `missing`, `corrupt`, `unreadable` (the external flash did not answer), `writing` (a full image is writing it now, up to a minute), or `held`, with the first eight bytes of the verified blob's SHA-256 in `imu_digest`, which `update.js` turns into the 16 hex characters it compares. `fullImageNeeded()` turns the two into the file the device should get, `state.advice`: slim for `none` or a digest the chosen file pins, full for everything else. The page names it by its ending, `.signed.bin` or `.full.signed.bin`, since the version in front is the release's. A slim file chosen for a device that needs the full one raises `needs_full` without blocking the install, because the device refuses to confirm a slim image without its blob and the next reset reverts it. While the device reports `writing`, or an image on probation, `state.settling` asks the page to send `update` again.

`update.js` refuses only an image strictly older than the running one (`not_newer`), not an equal one: the slim and full images of a release share its version, and reinstalling the full image of the running version is how a device gets its blob.

Every refusal is a `reason` on the config endpoint or an error on the SMP one, and the state machine passes it on as a notice key without deciding what it means. A key the page has no words for is still shown, under its own name.

The unit asks one question at a time, and stops asking a connection whose question the pilot refused (`firmware/core/comms/README.md`, One prompt at a time). While a question stands, a command that would ask another is refused `prompt_pending`, and the standing one keeps its thirty seconds. After one press refuses a question, every command that would ask one is refused `refused_on_device` until that connection drops. Neither client sends a command while a question stands, because both send only from `ready`. So a page meets `refused_on_device` after a refusal on the glass, and words it, and `cancelled` before it, as disconnect and connect again. The update client marks the connection `refusedOnDevice` on a `cancelled` that answers a standing question, not one that stops an upload, and on a `refused_on_device`, and clears it when the link closes. While it is set, the device page shows the `refused_on_device` note with Reconnect, and holds every button that asks a question. A notice about a `set` is marked `during: 'set'`, and the device page shows it under Save rather than on the firmware page.

Sizes come from the device, never from a constant. Web Bluetooth exposes no MTU, but smp_bt cuts every reply at MTU-3, so before the first upload `smp.js` sends an OS echo longer than any ATT payload, in 20-byte writes, and reads the write size off the first slice of the reply. This device's local ATT MTU is 498 (`CONFIG_BT_BUF_ACL_RX_SIZE` 502 less the L2CAP header, and `CONFIG_BT_L2CAP_TX_MTU`), so a Chrome that asks for 517 settles on 498: 495-byte writes. Each image-upload request is then one write of that size, carrying about 470 bytes of image, the way mcumgr-web sizes a chunk to one write. If the browser refuses a write anyway, the size steps down through 244 and 182, the payloads of MTU 247 and 185, to 20, and the upload resumes. A device that does not echo gets the whole `buf_size` packet (`CONFIG_MCUMGR_TRANSPORT_NETBUF_SIZE`, read from the OS group's parameters) in 20-byte slices, which `CONFIG_MCUMGR_TRANSPORT_BT_REASSEMBLY` puts back together. Replies are reassembled on the length in the header. The first upload packet carries the image's SHA-256: img_mgmt answers a second upload of the same image with the offset it reached, so a window that closed mid-image resumes rather than restarts, as long as the device has not rebooted.

### A link that never exchanged its MTU

The unit asks for a larger MTU itself right after a connection, so a link stays at the default only when the phone answers 23 or refuses (`firmware/core/comms/README.md`, Three endpoints). At the default ATT MTU of 23 a notification carries 20 bytes, and the unit answers a reply that does not fit with `{"acknowledge":false,"reason":"small_mtu"}`, 8 bytes, and counts it in `link_drops` (`firmware/core/comms/README.md`, "A reply too wide for its link"). `update.js` and `activation.js` turn it into the `small_mtu` notice whatever they were doing, and the briefing app words it: the phone or browser kept Bluetooth's smallest packet size, so disconnect and connect again, and failing that update the browser and the phone or use another one; the console prints the same under the frame. The status, 20 bytes at its widest, and every acknowledgement, 11 at most, always fit, so the page knows the flight state and hears every prompt and verdict. The `update` frame fits only while it carries neither versions nor a digest: 15 bytes for a confirmed image on a release build whose hub holds no verified blob, 17 on a development build, which adds `downgrade`, and 19 once it also reports a settings fallback; `imu_digest` takes it to 25. A Bravo's is two bytes wider, for `product`. Asked for, a wider one is answered `small_mtu`; pushed at connect, before most centrals exchange their MTU, it is dropped without a word, and the exchange's late `Up` pushes it again. The config reply is 20 bytes for a unit not yet activated with an empty callsign and no own ICAO, 22 with an address from 1 to 23, 23 from 24 to 255 and 24 past it, every callsign character adds one, and an own ICAO up to four: past 20 the page shows no settings and says `small_mtu`, so only a unit not yet activated, with no callsign and no own ICAO, shows its settings at this MTU. `defaults` fits. The challenge reply, 27 bytes, never does: an activation stops at its first step with `small_mtu`, with nothing sent to the server. The writes arrive, as long writes Zephyr reassembles from up to `CONFIG_BT_ATT_PREPARE_COUNT` (2) prepare segments, 36 bytes, which carries every command but `register` (88) and `unlock` (74): `dfu` at its widest version is 18. SMP answers too, because smp_bt cuts its replies at MTU-3, so an install runs on such a link, asked on the glass, in 20-byte writes; without the `update` frame the page does not know the unit's key, so the published list stays empty and the unit checks the key of the file chosen by hand once it has landed, and it takes the unit for a Go, so it sends no Bravo image.

`ble.js` queues every GATT write, config and SMP alike, behind the one before it, because a write issued while another is in flight can fail.

`cbor.js` is the one CBOR codec, for SMP and the link: integers, strings, byte strings, arrays, maps, booleans and null, definite and indefinite length (zcbor opens every map as indefinite), floats and tags on the way in only. `decode(bytes, { deterministic: true })` is the link's grammar, the one the firmware and `blip.py` read too: one map, its keys unsigned and ascending, every head in its shortest form with an argument of at most 32 bits, no indefinite length, float, tag or null, nothing nested but an array of unsigned integers, and text that is UTF-8. It hands the map back as a `Map` keyed by number, and leaves the generic decoding SMP needs untouched. `link.js` holds the link's names over it, from `link_registry.js`, which `scripts/link_registry.py` generates from the registry and `scripts/check_link_registry.py` holds to it, so it is regenerated, never edited. `encodeFrame()` takes an object keyed by full names, an enumeration by its name or its code and a byte string as a `Uint8Array` or hex, refuses a value its key's type does not take (`blip.py` refuses the same ones), and writes the keys in ascending order; `decodeFrame()` gives the names back, enumerations by name and byte strings as `Uint8Array`, and a key or a code the registry does not hold stays a number. Both throw `FrameError`, and `schemas/link.v1.vectors.json` lists what each refuses. Everything above `ble.js` sees only names.

## The devices a browser knows

`fleet.js` holds every device the app has met, as a `Unit` named by its slug, `go-00012a` for `skyBlip Go 00012A` and `skyBlip Go+ 00012A` alike, `bravo-3f2a` for `skyBlip Bravo 3F2A`, `activate-3f2a` for a Go not yet activated. A unit connected once is written to `localStorage` under `skyblip.devices.v1` with its name, product, address, firmware and track, the newest image it was offered, its settings and when it was last seen, and listed again after a reload. A unit not yet activated is written only once it holds its address, under its new name.

`ble.js` holds one GATT link per device and shares it between every client of that device, the `Updater` and the `Activator` alike, so several devices stay connected at once. A device connected once in a page's life connects again with `device.gatt.connect()`, without the chooser: Reconnect after a refusal on the glass, and the `Updater` itself after an install restarts the device, trying every three seconds for two minutes. A device remembered from another visit has no handle, so Connect opens the chooser filtered to its name, and the pilot sees one entry. `navigator.bluetooth.getDevices()` hands back the devices a browser granted, but only behind a Chrome flag today: where it answers, `restore()` connects the remembered ones on its own.

## The activation client

`activation.js` is what `/briefing/activate` runs, and like `update.js` it holds the dialect as a state machine and hands every change to one callback; `controllers/activation_controller.js` draws it with the words of `config/locales/briefing.*.yml`. It rides the link the device's `Updater` opened, so activating needs no second connection. It speaks to two parties: the unit over the config endpoint, and this server through `httpServer()`, which posts JSON with the page's CSRF token. The frames are [`schemas/link.v1.json`](../../../../schemas/link.v1.json)'s, the requests to this server and the messages their signatures cover [`schemas/activation.v1.schema.json`](../../../../schemas/activation.v1.schema.json)'s.

Connect sends `get`: a unit that reports no `address` is not activated, and `update.js` reads the same key, so the app sends such a Go here. Activate sends `challenge`, posts the nonce and the server key id it answers to `/activation/challenges`, and hands the signed answer to the unit as `register`. The two requests to this server stay JSON over HTTPS, where every byte string is hex: the client hexes the byte strings of the frames it relays, and the server's hex goes back to the unit as byte strings through `encodeFrame()`. The unit asks on its glass (`confirm_register`), and two presses answer the `registration` frame, which the client posts to `/activation/registrations` beside the server nonce. The serial and its unlock code go back to the unit as `unlock`, and `{"acknowledge":true,"reason":"unlock"}` ends it: the client sends `get` again and shows the address.

A refusal from the unit is its `reason`, a refusal from the server its `error` prefixed `server_`, so the two `bad_signature` and the two `expired` keep their own words.

Once the unit holds its serial, the page opens the device's settings, where the aircraft type, the callsign and the own ICAO address come first. The own ICAO is the one setting the form shows in another shape than the unit holds it: `settingsOf` turns the unit's 24-bit `own_icao` into its six hex digits, and 0, unset, into an empty field, and `settingsFrame` turns them back into the number a `set` carries, 0 for an empty field, which clears it. The field takes six hex digits or nothing, so a partial address never reaches the unit. A firmware from before #191 sends no `own_icao`, so the page hides and disables the field of every setting the unit's `config` does not carry, rather than show one whose edit Save would never send.

## The traffic comparison

`/briefing/comparison` puts two receivers side by side in one page: a SoftRF Retro Mk II on USB serial and a skyBlip Bravo on Bluetooth, each named by the view and its transport with it, so a test flight shows which aircraft each one heard, how far, how steadily, and which heard it first. `controllers/comparison_controller.js` draws it, `controllers/comparison/tables.js` builds its tables, and the modules below know nothing about the page.

`serial.js` opens the port Web Serial offers at the chosen baud rate, 38400 by default, which is what the Retro Mk II speaks over its CH340 (SoftRF wiki, Retro Edition MkII). Web Serial runs in Chrome or Edge on a computer. Chrome on Android lists no USB serial adapter, so the Retro needs a laptop. Every read goes to both decoders at once, because SoftRF sends GDL 90 by default and NMEA when set to: `gdl90.js` frames and checks GDL 90, and `nmea.js` splits and checks NMEA. NMEA text never holds the GDL 90 flag, `0x7E`, and a binary line fails the NMEA checksum, so neither decoder takes the other's bytes. The Bravo arrives through `ble.js` as the console's stream does.

`nmea.js` reads `$PFLAA`, `$PFLAU`, `$PGRMZ`, and `RMC` and `GGA` from any talker. A `$PFLAA` ID may carry the callsign after a `!`, as skyBlip and OGN send it. `gdl90.js` reads the heartbeat, the ownship report, the ownship geometric altitude and the traffic report of the GDL 90 Data Interface Specification, 560-1058-00 Rev A, and `test_gdl90.mjs` holds it to the specification's own heartbeat and traffic report examples. A field the message marks unavailable decodes to `null`, never to 0.

`traffic.js` folds both into one `TrafficPicture`, by receiver and by 24-bit address. A `$PFLAA` is relative to its receiver, so its distance is its own and its position needs that receiver's fix. A GDL 90 report is absolute, so its distance and its height above us are measured from the reference: the first receiver of `referenceOrder` with a fix heard within `LIVE_MS`, 10 s, and its pressure altitude. The page orders the Bravo first, because the two ride in one aircraft and a Retro without its own GNSS has no ownship report to measure from. A target is live while its receiver reported it within `LIVE_MS`.

Both receivers send their whole table every second whether they heard the aircraft again or not, so a report count measures how long a receiver held a target, not how often it heard it. The picture keeps one sample a second for each target and receiver, and reads steadiness from those. Listed is the share of the seconds either receiver listed the aircraft that this one did. A dropout is a gap longer than `DROPOUT_S`, 3 s, and the longest gap is kept too. A new position is a GDL 90 report whose position differs from the one before: SoftRF exports the last position it decoded, so a repeat means nothing new was heard. `$PFLAA` cannot tell them apart, since the Bravo dead-reckons every target to the moment it sends and SoftRF's NMEA moves with the receiver, so a `$PFLAA` target counts no new positions. The RSSI is the last `$PFLAA` field, shown when a receiver fills it. SoftRF on the Retro's STM32 sends none, in either protocol.

The two lists show different fields because the two receivers speak different protocols: GDL 90 sends an absolute position, the pressure altitude, NIC, NACp and the ADS-B emitter category, and `$PFLAA` a position relative to its receiver, a FLARM aircraft type, and on a skyBlip the source. SoftRF also filters what it exports. It leaves out of GDL 90 an aircraft farther than 25.5 km while it has its own fix (`ALARM_ZONE_NONE`), out of NMEA an ADS-B aircraft farther than 75.5 km (`ALARM_ZONE_NONE_EXT`), and out of both one it has not heard for 5 s (`EXPORT_EXPIRATION_TIME`). The Bravo forgets an airborne aircraft after 6 s and one on the ground after 60 s (`docs/TUNING.md`), so a ground target stays listed longer on the Bravo.

Picking an aircraft in the table or on the chart opens it beside the chart: its fields in common units for each receiver and their difference, how far apart the two receivers place it, and `timeline.js`, the last 15 minutes at most as one lane per receiver, a mark for each second it was listed and a tall one for each new position, over its distance and its RSSI.

`chart.js` draws the France OACI 1:500 000 chart from IGN's Géoplateforme, whose WMTS template is `config.x.oaci_chart.tiles`, with the receivers' aircraft over it. IGN serves the chart at zooms 6 to 11 and allows browser fetches, and the chart stretches zoom 11 for 12 and 13. IGN's terms make SCAN OACI free for professional and non-profit use and charge for a commercial product sold to the public, so the chart stays on this internal page. Save the chart offline fetches the area around a point, 100 km around Merignac by default, at zooms 7 to 11, 353 tiles, into Cache Storage, and every tile is read from there first, so the chart draws with no network in flight. Cache Storage needs https or localhost, and the page itself is not saved, so it is opened before takeoff.

The page keeps every sentence and frame it decoded, with the raw line or frame in hex, and Download NDJSON saves them for analysis after the flight. The log lives in memory until the page closes.

## Tests

From `server`, run `node --test test/javascript/test_*.mjs`. CI runs the same command. `test_activation.mjs` drives `activation.js` against `fake_activation.mjs`, a unit and a server that sign with `node:crypto` and the keys of the vectors, which the first test checks they reproduce. `test_cbor.mjs` holds the codec to the RFC 8949 appendix, `test_link.mjs` the link's subset, a few frames byte for byte and a round trip of every frame the registry lists, `test_image.mjs` the protected TLVs, the image class and the slim-or-full decision, `test_smp.mjs` the framing, the packet budget and the upload's offsets, and `test_update.mjs` the whole flow against `fake_skyblip.mjs`, with images `fake_image.mjs` lays out as imgtool does, which refuses an image of another product on the chunk that completes its protected TLVs, as `core/dfu/product_check.cpp` does, and takes any image as a unit before the check when its `product` is null: a skyBlip behind a fake `navigator.bluetooth`, which answers the config dialect in CBOR through `link.js` as `config.cpp` does (the install verdict, the `settings` and `imu` keys of the update frame, the status keys, and `get`, `defaults` and `set` with a pushed flight state) and the SMP one as Zephyr's img_mgmt does. The fake also truncates or refuses a write longer than its MTU, as a browser might, except a config write with response, which it takes as the long write Zephyr reassembles, up to two prepare segments, and it refuses a notification longer than its MTU less three, as the controller does, so at MTU 23 the status and the acknowledgements arrive and its update frame, its config reply and the challenge reply do not. The fake is a reading of that code, not the code, so a green run says the page agrees with the reading. `test_nmea.mjs`, `test_gdl90.mjs`, `test_traffic.mjs`, `test_chart.mjs` and `test_timeline.mjs` hold the comparison's decoders, its picture and its signal figures, the chart's tile grid and the timeline's span, which matches the tile IGN draws Merignac on. `test_diagnostics.mjs` holds `diagnostics.js` to the records the firmware's host suite pins, and to the NDJSON `blip_records.py` writes for every record type, which it runs `python3` to get. `test_log.mjs` fetches through `log.js` from the fake's log endpoint, `fake_log.mjs`, a reading of `core/comms/log_link.cpp`. `test_fleet.mjs` holds `fleet.js` to the same fake, several of them in range of a chooser that answers the filters it is asked with. The system tests drive the briefing app and the console in Chrome against `test/system/fake_fleet.js`, several units that speak CBOR through the page's own `#skyblip/link`, upload an image over SMP, restart and come back. `comparison_test.rb` drives the traffic comparison against `test/system/fake_receivers.js`, a Retro behind a fake `navigator.serial` that sends GDL 90 and a Bravo behind a fake `navigator.bluetooth` that sends NMEA. Nothing here has run against a device.
