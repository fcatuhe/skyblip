**Tooling** (`uv` is not installed on the bench laptop, so blip runs through mise)
- `B="mise x uv@latest -- uv run -q --script --with bleak scripts/blip.py"`, then `$B scan`, `$B --address <addr> cmd '{"cmd":"diag"}'` and `'{"cmd":"timing"}'`.
- `scripts/bench/fetch_both.sh <tag>` runs scan, then diag and timing (up to 15 tries each), then fetch (up to 30 tries), for both units, into `~/skyblip-captures/<name>-<tag>.ndjson`.
  - Rerunning with the same tag resumes the same files.
  - **Run it from a checkout of this branch.** blip decodes records at fetch time, and the new `levels_fresh` field only decodes with this branch's `blip_records.py`.
- Check the result with `python3 scripts/blip.py decode <file> --summary`: no gap records, no unreadable slots. `bench_check.py` also checks for index holes and duplicates.

**Capture gotchas**
- The capture lives in RAM. It is lost at power-off. A boot, a reset pin press included, always comes up **disarmed**, so arm it on the diagnostics screen after every boot.
- It holds about 54 min at 14 records/s, so a 1 h run needs a fetch partway through.
- The last record of an open session is dropped as possibly torn. That is expected.
- The firmware version is the boot record's `fw_build`. There is no version command. **Stop if a unit is not on the build you expect.**
- Known benign artefacts:
  - `since_edge` exactly 1000 while locked;
  - PPS records stamped at 997–999 ms (the local clock runs about 150 ppm fast);
  - device `tx_ok` and `tx_named` exceeding the capture by the bursts sent before arming;
  - a 13–15 s startup with no fix and no PPS lock if the capture is armed early.

## 4. What to optimise next, in order

Each item ends with the number that decides it.

1. **`kJitterGuardMs` 5 → 3** (`core/timing/slot.h`).
   - The band-switch margins are 2.7 ms (M→O) and 2.9 ms (O→M), so a 3 ms guard leaves about 0.7 and 0.9 ms.
   - The no-RX reinit is about 22.6 ms late at M→O whatever the guard, and never reaches O→M, so it does not block the change.
   - It moves `kSwitchLeadMs` with it, as well as the outer bucket edge of the `timing_stats` histogram and the simulator's aircraft instants (`simulator/world.cpp` around lines 353 and 380).
   - **Decide on:** the minimum `margin_us` for to_oband and to_mband over a 1 h run with a page-5 period. The 0B1B2C page-5 to_oband retune was slower: median 1.40 ms against 1.25, max 1.83.
2. **The stage lead.** Only after item 1 of section 3 shows `tx_keyed_us` max ≤ 130 µs.
   - Stage cost was 0.25–0.7 ms on the 856 bench. Log the stage duration, staged-at to staged-done, in a spare burst field to size the lead from data, then trim it toward the measured p99 plus a tick.
   - This shortens the 0.7 ms deafness before every own burst.
3. **DIO1 interrupt instead of the 200 µs TxDone poll** (`hardware/platform/zephyr/rf.h`).
   - SetTx→TxDone is 4.94–5.37 ms against 4.64 ms of air (§C.2), and up to about 0.2 ms of the difference is the poll noticing.
   - An interrupt dates TxDone exactly, gives the hop and the next dwell that time back, and would let `kCompletionSlackMs` reach 1.
   - **Decide on:** SetTx→TxDone spread before and after.
4. **`link_drops` miscount.** `ConfigService::broadcast()` counts a `WouldBlock` as a drop, but `push_status()` retries it. During a fetch that read 235 drops on E68BD9, probably with no loss.
   - Either count only pushes given up on, or give status its own share of the link.
   - **Decide on:** whether `link_drops` stays 0 during a fetch, and whether the status pushes still arrive.
5. **A per-pass budget for log chunks** (`core/store/record_store.cpp` `continue_read`, up to 5 chunks a pass), but only if section 3 still shows `nav_ms` or dwell shifts inside a fetch window.
6. **No-RX reinit cost**, about 22 ms of uplink listening each time, roughly every 15–20 min.
   - Its cost is set by the datasheet: a reset, two calibrations and three TCXO starts at `0x140 × 15.625 µs = 5 ms` each.
   - The only lever is the TCXO startup delay: each ms off saves about 3 ms. Find the T-Echo Plus TCXO's startup spec, then trim the delay and bench-check for XOSC_START_ERR.
   - Its placement at M→O is already the least harmful.
7. **GSV seconds.** With `nGSV=5`, one second in five still pays about 55–65 ms of GSV before RMC.
   - On E68BD9, whose page-0 `nav_ms` is already 280–330 ms, those seconds can push past 400, the last useful moment for an early slot-0 instant.
   - **Decide on:** the `nav_ms` ≥ 400 count on `levels_fresh` seconds. A fix could split the GSV set across seconds, or drop constellations the page does not draw.

## 5. Open questions, not yet reproduced

- **A duplicate name burst, seen once.** It has no reproduction yet. `burst_check.py` flags spacing other than 10 s.
- **The local clock reads about 150 ppm fast** against PPS, so PPS records get stamped at 997–999 ms. Benign so far, but unexplained.
- **A 37–62 s cold start after a button wake.** The capture can't see it. Time it from the button to the first fixed gnss record.
- **Power-on trials to see `raises` 1** (the GNSS baud raise), with a boot poller.
- **E68BD9's noise floor** read −102 dBm against −107 on earlier runs, while 0B1B2C stayed at −108. This was probably bench placement; check it again with the units where they were before.
- **A false take-off from a GNSS speed glitch on a still unit**: 13 m/s for about 7 s, seen in 4 captures of 0B1B2C. An IMU veto was written and **rejected**, since a glitch this long is rare and the cost on the airborne side is only a few extra bursts. Don't reopen it without a flight case.
