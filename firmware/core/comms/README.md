# comms

The companion link, from the side that does not know what Bluetooth is. A platform fills `ports::Link`; everything here speaks endpoints, sessions and CBOR frames with numbered keys.

## The wire

Every frame on the config, log and peer endpoints is one CBOR map (RFC 8949) in one write or one notification, in the grammar every reader of the link shares: unsigned keys in ascending order, each head in its shortest form with an argument of at most 32 bits, definite lengths, no floats, no tags, and nothing nested but an array of unsigned integers. Key 0 is `command` in every frame and its value is a code that says which frame it is, and so which key table the other numbers belong to. [`schemas/link.v1.json`](../../../schemas/link.v1.json) is the one place the numbers are written: every frame, its command code, and each key's name, number, type and description, with the names and codes of every enumerated value. A key that is an enumeration travels as its code, a nonce, a key, a signature or the raw records of a log chunk as a byte string, and only free text a person reads (a callsign, a version, a receiver's banner) as text. The link spoke JSON under the same names until the registry replaced it.

`scripts/link_registry.py` generates `link_registry.h` here (the command and reason codes as enums, one `<frame>_key` namespace of key numbers per frame, a `<frame>_bytes` one of the fixed widths of its byte strings, which the code that writes and reads them takes rather than restating, and `host_keys()`, the key numbers a host frame of each command may carry), `simulator/world/link_names.h` (the names, for the simulator and the suite), `test/core/test_link_mirrors.cpp` (which holds every enumeration the registry says mirrors a C++ enum to that enum at compile time, both ways: each code to its enumerator, and the enum to the registry through a switch `-Wswitch` refuses once the C++ enum gains a value the registry neither carries nor lists under `off_the_wire`) and `server/app/javascript/skyblip/link_registry.js`; `scripts/check_link_registry.py` fails CI when one of them is not what the registry produces. The device never carries a name: `core/util/cbor.h` writes and reads numbers, and the names live in the clients (`scripts/blip_frames.py`, the server's codec, `simulator/world/link_text.cpp`).

`cbor::Writer` refuses rather than truncates: an entry that will not fit whole, a key out of order, an integer past 32 bits or text that is not UTF-8 refuses the whole frame, `finish()` answers 0, and the sender counts a `link_drops` rather than send a frame with a key missing. `cbor::Reader` checks the whole frame before anything reads it, and refuses what the grammar does not allow: a non-shortest head, an argument past 32 bits, an indefinite length, a float, a tag, a nested map, an array holding anything but unsigned integers, text that is not UTF-8 (an overlong form, a surrogate or past U+10FFFF included), a key out of order or repeated, and a byte after the map. A frame it refuses has no command, so the config endpoint answers `no_command`. A command carrying a key its frame does not list is refused `invalid` before any handler reads it, and a bare ask (`get`, `status`, `diagnostics`, every command a host sends without keys) carrying any key at all: `ConfigService::on_rx()` and `parse_log_request()` hold the frame to `link::host_keys()` with `cbor::Reader::keys_within()`. The keys a `set` lists but the unit does not store, `version`, `address` and `address_mapping_table`, are read-only and ignored. `test/products/test_link_registry.cpp` drives the product through every command and holds both directions to the registry: every frame the unit sends to its keys, types, byte widths, enumeration codes and required keys, and every host frame to being read with all its keys and refused with one more. `schemas/link.v1.vectors.json` lists what the three readers, this one, `scripts/blip_frames.py` and the server's `link.js`, each refuse, and `test/core/test_cbor.cpp` reads it.

Reasons, the words a refusal or an acknowledgement names, are one enumeration for every frame, `link::Reason`.

## Three endpoints, two shapes of send

`events::Endpoint` splits a phone's link in three because the three have different owners. NMEA is the traffic picture and it is broadcast: every subscribed central gets the same bytes, and `ports::Link::send()` reports Ok when one of them took it, so a phone whose controller buffers are full cannot end the pass for the tablet beside it. Config and Log are conversations, and they go out through `send_to()`, addressed to the connection whose request they answer (Sessions). Peer is a fourth endpoint, between a paired Go and Bravo, and no phone speaks it (The peer endpoint).

That is why `payload_bytes()` with no argument is the *smallest* payload any connected central negotiated. One NMEA frame is formatted once and goes to all of them, so it has to fit the narrowest. An iPhone at ATT_MTU 185 sitting beside an Android at 247 pulls every broadcast frame down to 182 bytes, and that is correct, not a compromise: the alternative is formatting the picture once per central. A conversation is sized for its own session instead, by `payload_bytes_to()`, so a central that never exchanged its MTU narrows the broadcast and no one else's replies.

That central is not hypothetical. A central starts the exchange when its stack or app decides to: iOS always does and usually settles on 185, Android only when the app calls `requestMtu()` (XCSoar asks for 256, and Android 14 turns any request into 517). So the unit asks too. Right after a connection, `connected()` in `hardware/platform/zephyr/link.cpp` sends its own Exchange MTU Request as GATT client of the phone (`CONFIG_BT_GATT_CLIENT`), which every central has to answer, so an Android app that never asks still settles past 23. Both requests may cross, which the specification allows: each side's client asks once, and both land at the smaller of the two MTUs. Zephyr's `CONFIG_BT_GATT_AUTO_UPDATE_MTU` would send the same request but only logs its outcome, so the unit sends it itself and records it (Measuring what links settle on). A link still at 23 is a central that answered 23 or refused, and the replies it cannot carry are answered `small_mtu`. Every ATT server has to answer the request; one that never did would lose its link to Zephyr's 30-second ATT transaction timeout, which disconnects.

## Sessions

`LinkSessions` is the table, and it is the same object on both platforms: Zephyr's `connected`/`disconnected`/`att_mtu_updated` callbacks drive it on silicon, `raise_link()`/`drop_link()` drive it in the host suite. It exists so the lifecycle rules are proved once by `make test` rather than living inside a Bluetooth callback nothing can reach.

A session id names a connection only while it lasts. Zephyr's is the controller's slot, `bt_conn_index() + 1`, so the next phone may come up under the same id. `LinkSessions` therefore numbers every connection once, the platform stamps each inbound frame with that number under the lock it queues the frame under, and `ports::Link::connection()` answers the number a session id names now. A frame waits on the platform's queue and then on the bus, so the phone that wrote it may be gone, or replaced under its id, before a service reads it. `ConfigService::from_live_connection()` drops such a frame in the config service's drain and in the flight log's, before it can take the claim or stage a prompt.

A reply can outlive its connection the same way, so every reply is addressed to an `events::Peer`, the session id and the connection number together. The claim holds the holder's peer, and a reply held for a busy link and a log read sent a chunk at a time each keep the peer of the request they answer. A log erase's verdict keeps the peer whose prompt the presses confirmed, so a request another phone sends while the erase runs is answered on its own and never redirects it. Every other verdict that lands late, an install's, a held unlock's or a report's, answers the claim holder, and the holder's disconnect drops it first. `ports::Link::send_to()` takes that peer and answers `Down` once its connection is gone, so a reply the old phone can no longer take is counted as a drop and never reaches the next phone under the same id. On Zephyr the comparison and `bt_conn_ref()` share one critical section under `g_lock`, and the notification goes to that referenced connection after the lock is released, so a reconnect between the check and the send cannot redirect it.

`kMaxSessions` must never exceed `CONFIG_BT_MAX_CONN`. The controller is what actually admits a central; a table larger than the controller's is a table with rows that can never fill, and a table smaller than it means a central the radio accepted that the firmware refuses to serve. A refused connect is counted, not silently served: the bus never hears of that session, so no service answers its frames, and `refused()` is how a bench sees it happened.

A paired Go reserves one of those connections for its Bravo (The Go's link to its Bravo). `reserve_peer(true)` lowers `phone_ceiling()` by one, whether or not Bravo is connected, and `admits()` is what the platform decides advertising on, so a Go with a Bravo paired advertises up to two phones and refuses a third. A reservation is refused `Full` while phones already hold every connection, so the reservation is always made before the Go connects to Bravo. Only phones are sessions: the Go's own link to Bravo is never in this table, so session ids stay the controller's slots and the NMEA broadcast never reaches Bravo. On Bravo the paired Go is a central like a phone, so it is a session, and `reserve_peer_for()` names the slot by the Go's address: `connected()` takes the central's address, admits that address past the phone ceiling, and counts every other central as a phone. `admits()` stays true while that Go is away, so Bravo keeps advertising for it and refuses a third phone at connect. `central()` answers the address of the central on a connection, and nothing once the connection is gone.

Events are one ordered queue rather than a queue per type. A connection is a lifecycle, and an Up read before the Down that came first leaves a service pushing at a link that is gone.

## The claim

Broadcast is for everyone. Configuration is not: two apps writing settings to one device is two apps disagreeing about what is stored, and a prompt authorised on one phone answered on another is a confirmation with no presence behind it.

So `LinkClaim` grants config and log to the first session that writes a command, and holds it until that session disconnects or releases it. A command from any other session is refused with a reason naming the state, never accepted and quietly ignored. The claim is what makes a *dropped* link safe to act on: only the holder's disconnect cancels a pending prompt and closes an upload window, and before the claim existed any second EFB walking out of range did both.

What a claim is not is access control. `CONFIG_BT_SMP` is off on this product, deliberately (see `products/skyblip_go/prj.conf`), so there is no identity behind a session id. The claim stops two cooperating apps from stepping on each other. What stops a hostile one is the MCUboot signature on the image and the confirmation gesture on the device itself, or a browser key that gesture once approved (Trusted browsers).

## One prompt at a time

A prompt takes the glass from the radar and both controls from the pilot, and anyone in range can connect, so the unit caps what one connection does with them. Two rules hold for every command that stages a prompt: `set`, `dfu`, `recovery`, `power_off`, `gnss_cold_start`, `register`, `capture`, `pair`, and the log endpoint's `erase`. A trusted browser's `set`, `dfu`, `register` and `pair` stage none, and they still meet both rules, as does Bravo's `pair`, which never stages one.

- While a prompt stands, such a command is refused `prompt_pending`, and the standing prompt keeps its operation, its detail and its deadline. No command renews a prompt, so it expires `kPromptCeilingMs`, thirty seconds, after it was staged. Before this rule a sender held the glass for as long as it sent a no-op `set` every twenty seconds, and a second `set` replaced what the presses would store while the first stood.
- After the pilot refuses a prompt with one press, every such command from that connection is refused `refused_on_device` until it drops, and a new connection starts clean. Only that press starts it. An expiry, a take-off, a confirmation the flight state refused and a dropped link do not, and neither does the press that stops a running upload, which answers no prompt.

On the config endpoint, `ConfigService::prompt_refused()` asks both after the dispatch has answered what the claim and the key table refuse, and before the command's own checks, so the answer does not depend on what the command carries. A log `erase` reaches the same guard after `FlightLogService`'s own checks: the claim, the parse, the store, an erase already running, the flight state and the store the command names. Every prompt comes from the claim holder, so the refusal belongs to the holder's connection, and the holder's disconnect, which releases the claim, ends it. One prompt may stand at a time, for thirty seconds at most. A dropped link takes it, so a new connection can stage the same kind of prompt before the product's next pass sees `pending()` go back to `None`. `prompts_staged()` counts every prompt staged since boot, and a product that reads a new count treats the prompt as new: it disarms its gesture and asks again (#245). Only a one-press refusal prevents later prompts on the same connection. The pages never meet `prompt_pending` in their own flows, because each sends a command only once the last one is answered (`server/app/javascript/skyblip/README.md`).

## The flight gate

Every command that changes the unit or reads its log is refused `in_flight` while the flight state is `Airborne`, and goes ahead on `Ground` and on `Unknown`: `set`, `dfu`, `recovery`, `power_off`, `gnss_cold_start`, `capture`, `pair`, every request on the log endpoint, and `challenge`, `register`, `unlock` and `attest` on an activated unit (Activation). A `set` from a trusted browser is the one exception: it stages no prompt, so it goes ahead in flight too (Trusted browsers). `ConfigService::in_flight()` and `FlightLogService::in_flight()` ask it of the one value `GroundLatch` publishes (`core/flight/README.md`). A unit with no fix since boot is `Unknown`, which is every unit on a bench indoors, so a bench installs, sets and offloads without a sky view. A fix lost in flight never reads `Unknown`, because the latch holds `Airborne` until a positive `Ground`. The MCUmgr upload hook asks `upload_allowed()`, which takes an image only inside the window a press opened: SMP is unauthenticated, so the window is what stops a stranger in range filling the secondary slot. The gate is asked when the window opens, not after. A taxi fast enough to read as a take-off once aborted an upload the pilot had confirmed, so a take-off does not close the window. In flight the upload runs on behind the radar, since `receiving_firmware()` is false there, and an image that lands in flight is held: the window takes no more chunks, and the image installs once the flight state leaves `Airborne`, because the swap takes the unit dark for its 15 to 25 s. The holder's dropped link drops a held image, as it closes any window, and the page installs it again after the landing.

A take-off cancels a staged prompt, answered `in_flight`, unless it is an unactivated unit's `register` (Activation). It leaves an open upload window open. The link is unauthenticated, and a prompt takes the glass from the radar and both controls from the pilot, the alarm dismissal included. A prompt stands thirty seconds and a new connection may stage another (One prompt at a time), so a stranger in range could otherwise hide live traffic for as long as they kept reconnecting. `Unknown` hides none. `GroundLatch` reports it only while the last solution carried no fix and no take-off is latched, and `AlarmGrader` grades traffic only while own-ship has a fix (`products/common/alarm_grader.cpp`). On the ground there is none to hide either, because `traffic::assess` grades every target `None` while own-ship is on the ground (`core/traffic/alarm.cpp`). What `Unknown` costs is a unit switched on in the air that has not fixed yet: an install, a recovery or a cold start there delays its first fix, and only the press on its glass can ask for one. The press checks the gate again. On the Go the config service ticks before `OwnshipService`, so it hears a take-off one pass after the latch publishes it. `ScreenService` asks `prompt_allowed_in()` with the latch of its own pass, so no prompt is drawn or answered in the pass between, and config cancels the prompt on the next one. The services keep their order because the loop meter records the slowest service by its place in the loop, and the diagnostics schema and `scripts/blip_records.py` decode that place as a fixed code.

Past the gate, one press still cancels a staged `set`, thirty seconds still expire it, a dropped link still takes it, and the power rule is asked at the door and again at the press. The change reaches flash under the same durable-write policy as a menu change, `timing::DurableWriteWindow` in `products/common/services/config_link.cpp`: normally inside an armed receive dwell, clear of the radio's deadlines and of the window own-ship may transmit in, and forced once the policy's ceiling is spent, as any settings write is (`core/timing/durable_write.h`).

## The status reply

`status` is the one frame the device also sends without being asked: `set_flight_state` pushes it when the flight state changes, `set_battery_state` on a charging flip, a level change or a five-percent step, `set_bravo_state` when a paired Go's view of its Bravo changes (What the Go makes of its Bravo), and `set_own_transponder` when the transponder Bravo names on the ground appears, changes or goes, so a page proposes it as the aircraft address as the Go's `AIRCRAFT` menu does. The flight state is what every write is gated on (The flight gate), so a page that holds its buttons in flight learns it landed without polling. So it carries what a pilot's screen shows and nothing a bench reads, and it has to fit `kSmallestSupportedPayloadBytes`, the 182 bytes an iPhone commonly settles at, with every field at its widest. The buffer is that limit: a field that does not fit refuses the frame, and `format_status` then counts a `link_drops`. At its widest the status of a unit that is not paired with a Bravo and hears no transponder is 20 bytes, so even the 20 bytes a central that never exchanged its MTU carries take every push. A paired Go adds `bravo`, two bytes, and its widest status is 22. A unit on the ground that hears its transponder adds `own_transponder`, its callsign, written as the registration the glass shows, and its category, 18 bytes at their widest, so the widest status is 40. On a link that stayed at 20 bytes any status over 20 is dropped and counted, a push silently and an asked one with `small_mtu` (A reply too wide for its link), and for a paired Go in flight that is the usual case: airborne, 80% of charge, a die at 30 C and `live` already make 21. The unit asks for the MTU exchange itself at connect (Three endpoints, two shapes of send), so such a link is one whose central refused it.

What a support case reads lives where it is asked for. The address and the callsign are the config reply's. Why the device came up is `reset` in the diagnostics dump's system group, and whether the gauge is reading the cell is `battery_valid` in its power group, with `cell_mv` what the divider read when it is not: no divider, a refused reading, or the USB rail on the cable (`core/power/README.md`). One boot fact stays, `went_dark_flat`, because "the battery went flat" is the answer a pilot is owed for a unit that switched itself off (`core/power/README.md`). A key with no reading behind it is left out, never sent as a zero: `battery_percent` without a reading of the cell, which on the cable there never is, `die_temperature_c` without a fresh die reading.

`schemas/link.v1.json` numbers and describes the keys, and `scripts/check_link_registry.py` holds `format_status` to it: its keys, their order, their types and which keys may be absent. The widest frame is pinned byte for byte in `test/products/test_comms_report.cpp`.

## The 1090 MHz group

Only a unit with a 1090 MHz receiver, a skyBlip Bravo, sends the `adsb` group of the diagnostics dump. Its keys follow a frame from the LR2021 to the decoder's aircraft:

- `frames`, `frame_rate_hz`, `dropped`, `rearms`, `resets`, `command_errors`, `errors` and `rssi_dbm` are the receiver's own, `ports::AdsbReceiverStatistics`, filled by `hardware/parts/lr2021`.
- `crc` counts the frames `adsb::receive` refused on parity: the CRC failed, and nothing repairs it. Weak or damaged frames land here, and DF16 too, whose parity carries an address.
- `unsupported` counts the frames whose parity held but whose DF17 message the decoder does not read, such as type codes 0 and 23 to 30. They are sound receptions.
- `folded` counts the decoded messages `adsb::Assembly` folded into an aircraft. A message from the aircraft address is not folded.
- `aircraft` is how many aircraft the assembly holds now, with or without a position. `tracked`, in the traffic group, is how many reached the table.

So the frames that reached the decoder are `crc`, plus `unsupported`, plus the frames it read, and `folded` is at most that last term. Key 53, `invalid`, once counted `crc` and `unsupported` together. It is retired and never reused, and `crc`, `unsupported`, `folded` and `aircraft` are 60 to 63. They follow `rssi_dbm`, because a frame's keys ascend.

## The capture group

A unit whose flash holds a capture ring, a Go and a Bravo both, sends the `capture` group of the diagnostics dump, so a page reads whether a capture runs and what one costs before it asks for one. `common::CaptureService::describe()` fills it from what the service publishes on `bus::CaptureState` each second. `armed`, `profile` while one runs, `session`, the log session a fetch reads, and `records`, `records_dropped`, `sectors` and `keeps_s` are the running capture's, as the glass's capture page shows them. `takes_sectors`, `evicts_flights`, `keeps_full_s` and `keeps_power_run_s` are the price of the next one: every profile takes the same sectors and evicts the same flights, and keeps a different span of itself in them. A flight run keeps what a power run keeps, because it records the same types at the same rate (`../diagnostics/README.md`).

## The radio protocols

`protocols` names the radio protocol stacks a unit carries, so a pilot, a page or a bench can check a unit in hand against the ADS-L declaration of conformity. The declaration names firmware versions, and each release names the protocol versions it carries (`protocols/README.md`, Versions). Asked with the bare command, the unit answers one frame with one text key per stack, `<stack>_version`, the stack's `kVersion`, read from `protocols/<stack>/version.h` in `config_reports.cpp`. What each version implements, its `kSpecification`, stays off the link: the release's `PROTOCOLS.md` names it beside the version, so a unit's firmware version leads to its release, and the release to its protocol versions and their specifications. The product hands `ConfigService::set_radio_protocols()` the stacks it carries, the list in `products/<product>/radio_protocols.h`. `test/products/test_radio_protocols.cpp` holds that list to `products/<product>/PROTOCOLS`, which the release notes read, so a Go answers ADS-L and ALP-TAS and a Bravo ADS-B. A `ConfigService` handed no stacks answers `unknown_command`. The versions are not in the diagnostics dump: it carries what the unit measures, and a version never changes while the unit runs.

## How wide the frames are

Every frame is measured at its widest. The status push is 20 bytes, 22 on a paired Go, the config reply 37, and 41 on a paired unit, whose `paired_tag` adds 4, the update report 57 for a release build at the widest versions `scripts/build_image.sh` lets through, 9.99.99+99999, and 59 for a development build, which adds `downgrade`. The identity reply is 39 bytes at the widest version and a tag past 255, and never under 31, so a link that stayed at 20 bytes is answered `small_mtu`. The install report a host asks for after an install or a refused landing is 30 bytes at its widest (`core/dfu/README.md`). The protocols reply is 18 bytes on a Go and 11 on a Bravo at the versions of this release, so every link carries it, and each version character past five adds a byte, which `test/products/test_radio_protocols.cpp` pins. The registration frame is 138, the attestation frame 102, the challenge reply 27, an acknowledgement at most 11. The timing report is 147 at its widest and the widest diagnostics group, the radio's, 162, with the 1090 MHz receiver's 127 and the capture group's 78 next, so on a 182-byte link each answers one frame per question and per subsystem; on a narrower one they split, never mixing two groups. `test/products/test_link_payload.cpp`, `test/products/test_comms_report.cpp` and `test/core/test_diagnostics.cpp` pin these; `scripts/test_blip_frames.py` pins the status byte for byte on the host side.

A log chunk's envelope is 18 bytes at its widest session id and record index, the records' byte string adds a head of two bytes up to ten records and three past it, and a diagnostics chunk names its store in two more. That leaves room for six records at 182 bytes, nine at 244 and nineteen at 495, for either store, and `kMaxLogRecordsPerChunk` is 19.

The `browser_challenge` reply is 22 bytes and a `browser` entry 45 at its widest, with eight browsers trusted and a label of 24 bytes. On the host side the widest writes are a `trust_browser`, 133 bytes, a `register`, 88, and an `unlock`, 74. Every other command fits the two 18-byte prepare segments a link that never exchanged its MTU reassembles: the default ATT_MTU of 23 less a Prepare Write's opcode, handle and offset, twice, because `products/skyblip_go/prj.conf` sets `CONFIG_BT_ATT_PREPARE_COUNT=2`. The widest is `set` with every key the unit stores, at 34 bytes: 28 before `aircraft_address`, which adds 6 at 0xFFFFFE, the widest address the Go stores. `capture` is 6 bytes whatever its profile, and `pair` 8 at a tag past 255. `test/products/test_link_payload.cpp` pins both.

## The peer endpoint

A skyBlip Go paired with a skyBlip Bravo, a Tango, talks to it on its own endpoint, `peer`: one characteristic, `69C21304-0187-4204-A91D-02EB8858B440`, in the skyBlip service. The Go writes it and Bravo notifies it, as a phone writes config and the unit notifies it. Its UUID is the next one on the base config (`...02`) and the log (`...03`) took, because it is our protocol too (`hardware/platform/zephyr/README.md`). Three frames travel on it, in the registry with the rest: `observation` and `health` from Bravo, and `peer_claim` from the Go. On this endpoint the registry's unit is Bravo and its host is the Go. Bravo serves it (`products/skyblip_bravo/README.md`, Paired with a Go): `link.cpp` defines the characteristic only under `CONFIG_SKYBLIP_PEER_SERVER`, which Bravo's `prj.conf` sets, so the Go serves none. The Go reaches Bravo's as a Bluetooth central, `ports::Central` (The Go's link to its Bravo).

The Go never reads Bravo's FLARM NMEA instead. `$PFLAA` has no timestamp, loses whether an altitude is GNSS or pressure, and is relative to Bravo's position.

Each frame is held to the contracts of `core/model/README.md`. An `observation` carries one ADS-B target as `model::AircraftObservation` holds it, with each field's validity and time: a field with no valid reading is absent, never a zero. Its instant is `at_s` and `into_ms`, the UTC second and the milliseconds into it as `events::Stamp` counts them, of the instant `at_ms` names. `into_ms` is absent when the PPS phase is not valid. Each field's age counts back from that instant, as the observation's ages count back from `at_ms`, and is rebased whenever a new position moves it, so a field keeps the instant it was heard. A `peer_claim` carries the Go's own-ship, and its ages count back from the instant the Go wrote it, so they hold on a Go that has no UTC yet. Its `at_s` says when that was, and is absent without UTC. Each own-ship field is valid on its own, so a UTC never stands for a position.

Each side draws a 32-bit `boot_epoch` from its hardware random number generator at boot. An `observation`'s `sequence` counts in one boot: it starts at 0, moves by one each frame, and wraps from 4294967295 to 0. A reader orders two sequences of one epoch by serial number arithmetic (RFC 1982, SERIAL_BITS 32): a is newer than b when (a - b) mod 2^32 lies from 1 to 2^31 - 1. At 100 observations a second, a sequence wraps after 16 months. `health` carries `last_sequence` beside Bravo's own `boot_epoch`, so a number from before a restart is never read as current. The alarm needs no sequence: Bravo plays its Go's call only from a fresh claim, and each announcement carries its own number (The alarm).

A peer frame travels whole in one write or one notification, and is never split. At its widest the `observation` is 126 bytes, the `peer_claim` 82 and the `health` 80, so a pairing needs a payload of 126 bytes, an ATT MTU of 129. A Go whose link to Bravo settles below it refuses the pairing and says why, as #177 decided and #178 builds: Bravo never plays a call it could not be sent whole, and no frame is dropped silently. The Go's ATT MTU ceiling is 498 (`products/skyblip_go/prj.conf`). Zephyr agrees to the smaller of its L2CAP receive and transmit MTUs (`subsys/bluetooth/host/att_internal.h:38` at v4.4.2), and with `CONFIG_BT_SMP` off, as on every skyBlip product, `CONFIG_BT_L2CAP_TX_MTU` defaults to 23 (`subsys/bluetooth/host/Kconfig.l2cap:40`). So Bravo's `prj.conf` (#176) sets `CONFIG_BT_L2CAP_TX_MTU` to 129 or more, and `CONFIG_BT_BUF_ACL_RX_SIZE` to 133 or more, the MTU plus the 4-byte L2CAP header that `BT_L2CAP_RX_MTU` subtracts (`include/zephyr/bluetooth/l2cap.h:39-45`). `CONFIG_BT_BUF_ACL_TX_SIZE` at 133 or more, as on the Go, keeps a widest notification in one ACL packet. A Bravo that sets none of them refuses every pairing. The widest values are the extremes each key's type allows, where the contract sets no tighter range. `test/products/test_peer_frames.cpp`, `scripts/test_blip_frames.py` and the server's `test_link.mjs` pin the three frames byte for byte at their widest.

### A Go and a Bravo in the host suite

`simulator/world/paired_link.h` is the Bluetooth link between them, and `test/products/test_paired_link.cpp` holds it to what follows. It lives in the simulator, which flies a paired Go and Bravo on it too (`simulator/README.md`), and `test/support/paired_link.h` re-exports it. `PairedLink` has no clock. A frame moves only when the case calls `pump()`, so the case steps both sides and the link between their passes, and the same case runs the same way every time. Its peripheral half is a real `platform::host::Link`: `connect()` raises the central's session on it under the central's address, `kCentralAddress` unless the case names another, the central's writes reach it as `RxFrame`s on `Endpoint::Peer`, and every frame the peripheral sends on that endpoint to that session or to all of them goes to the central. Each `PairedLink` taps the peripheral's link, which hands it every frame as it is sent, so two centrals on one Bravo each receive what it sends to all, and a case that clears the link's `sent` frames costs neither a frame. Its central half is a `platform::host::Central`, the port a Go's `BravoService` drives. A case built on a bare `PairedLink` drives it itself, through `connect()`, `write()` and `take()`. A case built with a Go's central lets the Go do it: a scan hears the peripheral's advertised name under `kPeripheralAddress`, tag `3F2A`, a connect the Go asks for comes up with the peripheral's payload, and the Go's writes and the peripheral's notifications flow as above. `set_in_range(false)` stands for a Bravo off or out of range: no scan hears it and no connect takes it. Either half refuses a frame wider than the link's payload, never shortens it. The central half also refuses a write longer than the 256 bytes of `events::RxFrame::data`, as `hardware/platform/zephyr/link.cpp` refuses it on silicon. A write the peripheral's receive queue cannot take yet waits for the next pump, and only a write the queue took counts as delivered. The case sets each direction's flow:

- `Stalled` holds the frames in order on a link that stays up, and `Flowing` releases them on the next pump;
- `Lost` loses every frame the pump finds in that direction, the held ones included;
- `drop()` loses everything in flight, and takes down both halves.

A reboot takes down the rebooted side's half at once, and loses what it held and had not read. The other half stays up and loses what it sends until the case calls `drop()`, its supervision timeout, because that is when a real central or peripheral notices. A reconnect needs both halves down. A rebooted peripheral hands the link a new `platform::host::Link`, `reboot_peripheral()`, so its connections are numbered from 1 again, as a product just booted numbers them. The stub keeps its old link until its next reboot, so the swap counts what the old link sent and the pump had not carried as lost.

`test/support/bravo_stub.h` is Bravo on the peer endpoint for a Go case that needs no real Bravo. `test/products/skyblip_bravo/test_pairing.cpp` runs a whole Go against a whole Bravo instead. It replays a recording of observations on the world's clock, each written by registry name less `boot_epoch` and `sequence`, and sends `health` every second, `BravoStub::kHealthPeriodMs`. After a long gap between passes, the next `health` waits for the next whole period, so no burst catches up. An observation that falls due while no Go is connected, while `health.utc_valid` is false or while `health.export_reference` is `none` is skipped and takes no sequence, because Bravo exports nothing without UTC or a position to place it against (`schemas/link.v1.json`). A reboot draws a new boot epoch from a seeded generator, starts the sequence at 0 again, and keeps the recording where the world is. Every frame is built from the registry's names and fails the case unless it carries every required key at its type (`complete_registry_frame()` in `test/support/registry_frames.h`). The stub records each `peer_claim` it reads, names an own transponder only when the case sets `health.own_transponder_fields`, says a press dismissed a call only when the case sets `health.dismissed_announcement`, and sends `health` with `paired` true to any Go, pressed or not, unless the case sets `health.paired`. The real product pins only on a press and the Go's `paired` claim (#192), and plays only that Go's calls (The alarm). `test/support/paired_products.h` holds a whole Go and a whole Bravo on one link for the cases that need both.

## The Go's link to its Bravo

A Go pairs with one Bravo and keeps it, a skyBlip Tango. `products/skyblip_go/services/bravo.h` is the Go's side and `test/products/test_bravo_pairing.cpp` runs it against the stub over `PairedLink`. Bravo's side is #192.

- **No key and no bonding.** Bluetooth's Security Manager stays off (`products/skyblip_go/prj.conf`). Each side pins the other's whole address, its type included, and Bravo asks for a press of its button. That prevents a mix-up with a neighbour's unit. It is not authentication, and active spoofing is outside this design's threat model. If that changes, the step up is LE Secure Connections with a bond on the peer link alone: the Go is the central there and no browser reads the peer characteristic, so the update service can stay open. A signed challenge using `core/identity` is not the step up: Bravo holds no key, so it would prove only the Go to Bravo, and it would sign on every reconnect, in flight too.
- **Pairing.** The pilot opens the `BRAVO` row of the settings menu. The Go reserves Bravo's connection, which is refused while three phones are connected, and scans at `BravoService::kPairingScanWindowUs` in every `kPairingScanPeriodUs`. A Bravo is an advertiser whose name starts `skyBlip Bravo `, which `products/common/README.md` gives Bravo, and the page lists it by its tag, the low 16 bits of its address. A press picks it, a second confirms it. The Go connects, and once the link is up and subscribed it writes `peer_claim`, which is its pairing request, once a second. Every `health` says whether Bravo holds, or offers after its button was pressed, this Go's pin. The first `health` that says `paired` true stores the Go's pin, and the Go's next `peer_claim` says `paired` true, which stores Bravo's (`products/skyblip_bravo/README.md`, Paired with a Go). `kConnectCeilingMs` bounds the connection and `kAnswerCeilingMs` the wait for the press. A browser can start the same pairing by naming the Bravo's tag (Pairing from a browser).
- **Refusals.** Each ends the pairing with a reason on the glass and stores nothing: three phones connected, until one goes; a link below `comms::kPeerPayloadFloorBytes`, 126 bytes, which is refused before anything is written, so no frame is dropped and no alarm is taken; no answer in time; the link lost; and a `health` whose `protocol_version` is not 2, `comms::kPeerProtocolVersion`, which `comms::read_health()` refuses, as it refuses a `health` with none, before anything is pinned.
- **Paired.** The pin is in the settings blob, version 13. On every boot and every loss the Go connects to the pinned address again at `kReconnectScanWindowUs` in every `kReconnectScanPeriodUs`, the scan duty cap, and the reservation holds while Bravo is away. A paired Go that meets a link below the floor, or a Bravo speaking another protocol version, stays disconnected and says so on the BRAVO page until it is paired again or restarts. A reconnected Go reads `CONNECTED` only once a `health` says `paired` true. One that says false means Bravo holds no pin for this Go, from a pairing cut short, a Bravo that lost its settings or a Bravo paired with another Go. The Go then drops its pin and asks again on the same link, as a new pairing does: its `peer_claim` says `paired` false, Bravo's lamp blinks blue, and `BRAVO LOST THIS GO` over any page but an alarm counts down `kAnswerCeilingMs`. One press on Bravo pairs both sides again. With no press in time, or the link lost, the Go frees its phone slot and shows `NOT PAIRED ON BRAVO` once. Bravo raises no request from a Go it already told `paired` false on that connection while its own pinned Go is connected, so a press never hands Bravo back to a Go another one replaced. Unpairing while connected writes one `peer_claim` with `paired` false and holds the link until Bravo answers, at most `kFarewellCeilingMs`, so Bravo drops its pin too. An unpaired Go never scans and shows no Bravo state.
- **What the Go reads.** `health` drives `go::AircraftAddressWarning`: each one calls `paired(aircraft_address_set)`, and a lost link or an unpair calls `unpaired()`. Its optional `own_transponder` keys name the transponder Bravo takes for the aircraft's own, which the Go proposes as its aircraft address on the ground (`products/skyblip_go/README.md`, Aircraft address). `comms::read_health()` refuses a callsign or a category that comes without the address. Below are the observations and what `health` says of the Bravo.
- **The alarm.** The Go grades the traffic for both units, and Bravo plays its calls. The alarm below says how.

### The alarm

While Bravo is paired with a Go, the Go's `ALARM` row sets the alarm for both units, and the Go is the only grader while the link is up: it grades its own ADS-L traffic and Bravo's ADS-B, and Bravo plays what it decides. The row is `OFF`, `VISUAL`, `SOFT` and `LOUD` on a Go+. A plain Go has no buzzer and no motor, so it offers `OFF` and `VISUAL` alone, and `BRAVO SOFT` and `BRAVO LOUD` too while it is paired (`products/skyblip_go/pages/README.md`). It switches to `BRAVO LOUD` when it pairs, its default while paired, so a new pair sounds out of the box, and its config says `annunciator_fitted` false so a page knows it cannot sound itself. `VISUAL` takes the Go's glass and lamp and Bravo's lamp, and `SOFT` and `LOUD` add the tone and the motor on every unit that has them, so a Go+ and its Bravo both sound and a plain Go never does. A Go+ no longer keeps Bravo silent: the `alarm_requested` and `alarm_granted` keys that did are retired.

Every `peer_claim` carries the call: `alarm`, the row's value, `announcing`, the level the Go's buzzer plays, `undismissed`, the level its glass and lamp show, and `announcement`, the number of announcements the Go has made since it booted. `common::AlarmService` publishes them on `bus::State::alarm_call`, and `BravoService` writes a claim at once whenever any of them changes, as well as once a second, `kClaimPeriodMs`. A claim the link refuses is written again on the next pass. So a new aircraft, a second one under a standing alarm, a dismissal and a change of the row reach Bravo within the link's latency, not on the claim cadence.

Bravo plays the call while a claim from its pinned Go is younger than `PeerService::kCallMaxAgeMs`, three claim periods, and the link is up. `core/annunciation`'s `Follower` turns the calls into what Bravo's annunciation policy reads: the level, and an announcement whenever the number moves, so both units start the same call on the same announcement. A Bravo in flight plays one low note when it stops playing its Go's calls, since a plain Go has no tone of its own for the lost link. Bravo still sends its observations and keeps grading its own ADS-B, for its `$PFLAU` and `$PFLAA` and its capture, but none of that grading sounds or lights while it plays the Go's call (`products/skyblip_bravo/README.md`, The alarm).

A press on either unit dismisses the alarm on both while the link is up. The Go's long touch dismisses its tracker, so its next claim says `none` and Bravo falls silent. A press on Bravo silences Bravo at once and sends a `health` without waiting for the period, whose `dismissed_announcement` names the announcement it heard. The Go dismisses its tracker, as its long touch does, only while that number is still its own announcement, so a press never dismisses a call Bravo had not played yet. `dismissed_announcement` stays in every `health` on that connection, which is harmless: the Go's number moves with each new call, so an old press never matches it again.

`protocol_version` is 2 for this, because what a paired Bravo does changed meaning. Under version 1 a Bravo graded its own ADS-B and kept silent while a Go+ asked it to. Under version 2 it plays its Go's call and grades nothing of its own for its alarm while the link is up. Keys left as well: a version 1 Bravo refuses every claim without `alarm_requested`, which it requires, and a version 2 Bravo refuses every claim without the call. A Go reads Bravo's version off every `health` and refuses the other one, as `UNKNOWN PROTOCOL` while it pairs and `UPDATE NECESSARY` once paired, so a pair never runs half of each version, and both units are updated together.

### What the Go makes of its Bravo

An `observation` enters the Go's table through `traffic::TrafficTable::update`, the door the radio uses, from `BravoService::fold()` in `products/skyblip_go/services/bravo_fold.cpp`, and only from the pinned Bravo while the link is up and its `health` has said `paired` true. `comms::read_observation()` reads each field with its validity and its age, and skips a key it does not know, because `protocol_version` moves when a key changes meaning, not when Bravo adds one. It refuses the whole frame for half a field, a field without its age, a code no enumeration names, and a value outside the range the Go computes with: a latitude past 90 degrees or a longitude past 180, a pressure altitude outside -1200 to 126700 ft, the extremes `protocol::altitude_ft_of` decodes, and a height outside -1318 to 39572 m, those extremes widened by the 3125 ft GNSS-baro difference an unsaturated velocity message carries. Inside those bounds every height the Go carries in millimetres stays far below the 2147483 m whose millimetres an int32 holds, past which the alarm's arithmetic overflowed. `BravoService::refused()` counts each frame it refuses. The Go places the frame's instant on its own clock through the UTC second's edge: the PPS edge `timing::ClockState` anchored that second to, or else the fix that named it. `at_ms` is that edge plus `into_ms`, or the edge alone when `into_ms` is absent, so a field known to the second only is dated at the start of its second and only ever ages. The ages are copied as Bravo sent them, so every field keeps the instant Bravo heard it, and `received.at_s` is the frame's `at_s`. Nothing reads when the frame arrived, so a frame forwarded late is held to its own lease and no longer. Two GNSS clocks may disagree by a second, so an instant up to `BravoService::kAheadCeilingMs` after the Go's own now keeps its place, and a frame forwarded again on either side of now lands on the same instant. The table holds a reception dated up to two of its seconds ahead as new, its own second lagging its clock by one (`../traffic/README.md`). A frame dated further ahead is no clock's: it is refused and counted in `BravoService::unplaced()`, as is every frame a Go with no UTC cannot place in time. The alarm tracker dates a reception from that same instant, so a target forwarded late stops sounding with its own age, never with its arrival. A frame's `callsign` goes to `traffic::CallsignTable` under table 5, dated by `callsign_heard_s`, or by `at_s` when Bravo dated the name before it held UTC. Each folded observation is offered to `common::AdsbCapture` before the table, as on Bravo (`../diagnostics/README.md`). RSSI is not carried, so a folded target's `rssi_dbm` stays 0.

`health` alone says whether the Bravo is there, never the traffic: an empty sky sends no observation and is a healthy one. `BravoService` publishes `bus::State::bravo`, a `comms::BravoState`, on every pass:

| State | When |
|---|---|
| `Unpaired` | the Go holds no pin |
| `Waiting` | paired, not live, its receiver listening, and not yet counted on: no `health` younger than `kHealthMaxAgeMs`, or one that says `utc_valid` false (#193) |
| `Live` | a `health` younger than `kHealthMaxAgeMs` whose `listening` and `utc_valid` are both true |
| `ReceiverDown` | that `health` says `listening` false |
| `NoUtc` | that `health` says `utc_valid` false while the Go counts on its Bravo, so Bravo exports nothing (#192) |
| `LinkDown` | no `health` younger than `kHealthMaxAgeMs` while the Go counts on its Bravo |

`kHealthMaxAgeMs` is three `health` periods, so one lost notification is no loss. The Go counts on its Bravo once the pinned Bravo has said `utc_valid` true since the Go booted or paired, or once the Go has rolled, `state.flight.rolling`, taxiing or flying, after `kBootSettleMs` from boot. Until then a Bravo that is not live is still coming up: a Bravo that has just booted sends `health` before its GNSS gives it UTC, for about a second in the simulator and on an X1 until the AG3335 dates a fix, and its link comes up in a few scan windows. The Go reads that as `Waiting`, which plays no tone, so switching a Tango on in the hangar is silent. From the taxi on, the pilot can still fix a Bravo that is not live and has to be told: it reads lost, with its tone, whatever the reason, so a pilot who taxis out with Bravo switched off or under a hangar roof hears it before takeoff. Rolling counts only from `kBootSettleMs` after boot, the connection ceiling, so a Go switched on in a rolling aircraft, or rebooting in flight, gives its Bravo the time to connect before calling it lost. The two facts are `BravoService::counted_on()` and live in RAM, so a Go that reboots forgets them. Once Bravo has said UTC, a `health` without it is `NoUtc` whatever its `boot_epoch`, so a Bravo that reboots in flight reads lost until it has UTC again. A reconnect keeps the fact. Unpairing, or Bravo saying it holds no pin for this Go, drops both facts with the pin, so the next Bravo paired on the ground waits for its own UTC. A receiver that is not listening is never coming up by itself, so `ReceiverDown` is lost from the first `health` that says so. Bravo plays the Go's calls whatever the Go reads of it, so a Bravo that waits for UTC still sounds the Go's ADS-L traffic. The last three states are a lost Bravo, `comms::lost()`. The glass shows `BRAVO` over the reason in its top-right corner, black on white while Bravo is waiting and reversed once it is lost (`products/skyblip_go/pages/README.md`, Bravo has its corner), `common::AlarmService` plays one tone on the pass it is lost, on a Go whose alarm sounds (`../annunciation/README.md`), the flight log writes a `bravo` record, while a flight is open, on the fix it is lost and on the fix it is back (`../flight/README.md`), and `status` carries the state as `bravo`. A Go that is not paired publishes `Unpaired`, and none of them ever says anything.

The scan duty cap is unverified until #194 measures what the central link costs the 868 MHz timing on silicon. The reconnect duty is the Bluetooth Core's slow scanning mode 1, 11.25 ms every 1.28 s, under 1% of the radio. The pairing duty is fast scanning, 30 ms every 60 ms, while a pilot watches the list.

## Pairing from a browser

`pair` pairs a Go and a Bravo from a browser, with one key, `tag`: on a Go it names the Bravo to pair with, on a Bravo the Go to accept. A unit's tag is the low 16 bits of its Bluetooth address, the one it advertises: `skyBlip Bravo 3F2A`, `activate 3F2A skyBlip`, and `bluetooth_tag` in its `identity` frame, each read off FICR DEVICEADDR. The address the peer link pins is that same address. Zephyr's controller takes its static random identity address from FICR DEVICEADDR (`subsys/bluetooth/controller/ll_sw/nordic/hci/hci_vendor.c`), neither product enables `CONFIG_BT_PRIVACY`, `hardware/platform/zephyr/bluetooth_address.h` copies `bt_addr_le_t` least significant byte first, and `events::bluetooth_tag()` reads the two low bytes. So the tag a page reads from one unit's `identity` is the tag the other unit pins. The config reply carries `paired_tag`, the tag of the unit a Go or a Bravo is paired with, and leaves it out while it is not paired. `pair` is refused `in_flight` on both, and answered `paired` at once when the unit is already paired with that tag. The handlers are `ConfigService` methods in `pair_link.cpp`, and each product says which side it serves with `ConfigService::serve_pairing()`.

On a Go a trusted session's `pair` starts at once and is answered `pair`. Any other session's stands on the glass as `PAIR BRAVO` over `PAIR WITH BRAVO 3F2A`, under `confirm_pair`, and the press trusts the browser, starts the pairing and answers `pair` (Trusted browsers). `BravoService::pair_with()` then unpairs the Bravo the Go holds, if any, with the farewell an unpairing writes. It scans at the pairing duty for the advertiser named `skyBlip Bravo 3F2A` whose address has that tag, and goes on as a pairing from the menu does (The Go's link to its Bravo). The glass opens the `BRAVO` page on the pairing: `PAIRING` over the tag and `WAIT` while it searches and connects, then `PUSH THE BUTTON ON BRAVO` with its countdown (`products/skyblip_go/pages/README.md`). When the pairing ends, the Go sends the session that asked an acknowledgement nobody asked for, if that session is still connected, as an install sends its verdict:

| Verdict | When |
|---|---|
| `paired` | the first `health` that says `paired` true, and the Go has stored the pin |
| `not_found` | no advertiser with that name and tag heard within `BravoService::kConnectCeilingMs` |
| `phones_connected` | three phones hold every connection, so the Go cannot keep one for Bravo |
| `narrow_link` | the link to Bravo settled below `kPeerPayloadFloorBytes` |
| `no_answer` | Bravo's button was not pressed, and no trusted browser armed it, within `kAnswerCeilingMs` |
| `link_lost` | the connection failed or dropped before Bravo answered |
| `unknown_protocol` | Bravo's `health` speaks another `protocol_version` |
| `cancelled` | the pilot left the `BRAVO` page, or a newer `pair` replaced this one |

`acknowledge` is true for `paired` alone. A session that dropped hears nothing, and the pairing goes on, since the pilot watches it on the glass.

Bravo has no glass to ask on, so it answers `pair` only to a trusted session, and refuses any other `untrusted`: the page then asks for the usual press while the lamp blinks blue. A trusted `pair` arms Bravo for `PeerService::kAcceptanceWindowMs`, 60 s, and is answered `pair`. While it is armed, the request of the Go whose address has that tag is answered as soon as it stands, through `PeerService::answer()`, the path the button takes. That happens in the pass the request arrives, so the lamp shows nothing. The window is twice the press window, because the page turns from Bravo to the Go through the browser's device chooser. A request from another Go is left on the lamp for the button. No peer frame changed for any of this.

## A reply too wide for its link

A reply that is whole but wider than the payload of the session that asked is never handed down, and never left unanswered: the sender counts a `link_drops` and answers `small_mtu` instead, an acknowledgement of 8 bytes on the config endpoint and 8 or 10 on the log endpoint, where it names its store like every log reply, so it reaches a link that never exchanged its MTU. Each endpoint does it in the one place its replies leave, `ConfigService::reply_to()` and `RecordPool::send()`, so no frame carries a check of its own. Four refusals come before any frame exists and are not counted as drops: a timing or diagnostics report whose fields cannot be split into frames this narrow, a `register` whose registration frame the link could not carry, an `attest` whose attestation frame it could not carry, and a `read` whose chunk could not hold one record (the log dialect's `payload` reason, folded into this one). At 20 bytes that is a paired Go's asked `status` once it passes 20 bytes, the config reply of every activated unit, and of an unactivated one with a callsign, an aircraft address or a pairing, because `aircraft_address` is always in it, 0 while unset, and takes an unactivated unit with none of them to exactly 20, the challenge reply, an asked `update` frame with versions or a digest, the timing report, every chunk, and a session entry once it holds 256 records.

A frame nobody asked for is not refused, because the refusal would be noise. The `status` push of a unit that is not paired and hears no transponder fits every link, and a paired Go's push past 20 bytes is dropped on a 20-byte link like any push that does not fit. The `update` frame a connection is pushed leaves on its first `Up`, before most centrals have exchanged their MTU, and the late exchange's second `Up` pushes it again: a refusal on the first would tell a page its phone is too narrow a moment before the frame arrives. A push that does not fit is counted in `link_drops` and dropped, as it always was.

## Measuring what links settle on

Each connection leaves one `Link` `down` record in a `Full` capture, which carries two fields: `payload_bytes`, the payload the link settled on, and `mtu_exchange_started_by`, which side started the ATT MTU exchange. `central` is the phone, or a link that came up past 20 bytes. `unit` is the request `link.cpp` sends at connect, answered. `both` is the two requests crossing, and `none` is a link where no exchange landed and that ran at 20 bytes. `LinkSessions` works it out at the `Down`: Zephyr calls `att_mtu_updated` for every exchange, the unit's own included, just before the unit's response callback, so an update the unit's answered request does not account for is the central's. On the bench, arm a `Full` capture on the CAPTURE page, connect each phone, browser and app a few times, fetch with `./scripts/blip.py fetch --log diagnostics --all --out capture.ndjson`, and read the `action=down` lines of `./scripts/blip.py decode capture.ndjson --type link`, one per connection. Splitting replies across notifications is worth building once a supported phone or browser ends at 20 bytes on two runs out of two, which is a pilot who cannot activate or update from it.

## Activation

`challenge`, `register` and `unlock` travel on the config endpoint like every other command, and live apart from it: `IdentityLink` in `identity_link.h` holds the session, and the three handlers are `ConfigService` methods defined beside it in `identity_link.cpp`. `schemas/link.v1.json` describes the frames, `schemas/activation.v1.schema.json` what the browser relays to the server and what each signature covers, and `core/identity/README.md` the messages they sign.

`challenge` draws `unit_nonce`, 16 bytes from the hardware RNG, for the session that holds the claim, and answers it with `server_key_id`, the id of the server key this build trusts, in a frame of fixed width, `IdentityLink::kChallengeFrameBytes` (27), that is dropped and counted in `link_drops` rather than sent short should its buffer ever overflow. The nonce is single-use and dies when `unlock` spends it, when the claim holder's link drops, or at `IdentityLink::kNonceForgetMs`, ten minutes: `live()` takes the session and the time, so a command on the pass that reaches the deadline already finds it dead, and the tick closes it once past, so it stays dead when `milliseconds()` wraps back into the old window 2^32 ms later. A new `challenge` replaces it. `register` verifies the server's signature over `unit_nonce` and `server_nonce`, then stands `Pending::Register` on the glass under `confirm_register`, and one press answers the registration frame, signed by the unit's key, which says after `server_key_id` whether the build is a release. A trusted browser's `register` is answered the registration frame at once, after the same checks (Trusted browsers). `unlock` verifies the unlock signature over the unit's own DEVICEID, its current key, the serial and `unit_nonce`, and refuses serial 0, which would put 0x000000 on the air. The nonce is spent before the check, so a refused code is never retried on it. The code is written and read back before the acknowledgement naming `unlock` goes out. On an unactivated unit the radio is off and the page is written at once; on an activated one the radio runs, so the verified code waits in `IdentityLink` and the product places the write as it places a settings write, through a `timing::DurableWriteWindow` of its own, outside a dwell, and answers then (`products/common/services/config_link.cpp`). The power rule is asked again at the moment of writing: a cell that fell through it, or a supply warning, while the code waited drops the code with `low_power`, never a forced write. A held code belongs to the session that sent it and dies with that link, so its answer can never reach another app.

On an unactivated unit none of it is gated on the flight state. A unit with no serial transmits nothing, so the gate would protect nothing, and its `Pending::Register` confirms, and survives a take-off, whatever the flight state. An activated unit transmits, so it owes the gate like an install does (The flight gate): `challenge`, `register`, `unlock` and `attest` are refused `in_flight` while it is airborne, and its register prompt is cancelled at take-off. One press still cancels a prompt, thirty seconds still expire it, and a dropped link still takes it.

Every identity refusal but `small_mtu` and `invalid` is written in `identity_link.cpp` as `refuse(link::Reason::Word)`, and none as `acknowledge(false, ...)` in `config.cpp`, so the server's activation page can grep its rows apart from the update page's. `small_mtu` is `refuse_too_wide()`, the refusal every reply shares, which `config.cpp` writes, so both pages word it:

| Word | When |
|---|---|
| `keyless` | the unit has no key, drew no nonce, or cannot read its own version: it cannot be activated as it is. A unit short of a required part never gets this far, because it runs no service and advertises nothing |
| `in_flight` | an activated unit in flight |
| `low_power` | an `unlock` while the cell is below the settings write rule (`core/power/cutoff.h`): the nonce stays live for a retry on the charger |
| `no_session` | no live nonce for this claim holder: no `challenge`, a spent nonce, a dropped link, ten minutes, or a `challenge` since the registration was staged |
| `bad_signature` | the register or the unlock signature does not verify with the trusted key, or the field is not a byte string of the width the registry pins |
| `small_mtu` | the claim holder's link cannot carry the registration frame, `IdentityLink::kRegistrationFrameBytes` (138) at the widest version, in one notification: an iPhone's 182 bytes carry it. The challenge reply, 27 bytes, is answered the same way by any link narrower than it (A reply too wide for its link) |
| `flash` | the identity page did not take the code, or did not read it back |

`cancelled`, `expired`, `prompt_pending` and `refused_on_device` come from the prompt machinery every command shares, `claimed`, `unknown_command` and `invalid` (a key the frame does not list) from the dispatch. A product that hands `ConfigService` no `IdentityLink` answers all three commands `unknown_command`, and `attest` too.

### Attestation

`attest` asks an activated unit to sign the firmware it runs, so skyblip.eu holds which version each unit runs on the unit's own word rather than a browser's. The page asks the server for a nonce, `server_nonce`, and sends it in `attest`. The unit answers at once with the `attestation` frame: its product, its variant, its running version, whether the build is a release, its DEVICEID, the keys and order of the `identity` frame, and its signature over `skyblip:attestation:v1` followed by the DEVICEID, its public key, `server_nonce`, the release, product and variant bytes and the version (`core/identity/README.md`). The variant is signed, so a Plus that boots as a Go is on the unit's own word. The page posts the frame to the server, which checks it against the unit's active key and spends `server_nonce`. The handler is `ConfigService::attest()` in `identity_link.cpp`, beside the activation's, and it holds no session: `server_nonce` is the server's to spend, so the unit keeps nothing between two frames.

It stages no prompt: signing does not take the glass from the pilot, and any central in range can already read the running version over SMP. The label is the attestation's alone, so no attestation passes for a registration or any other message, and the unit only signs its own version under it. A stranger who asks for one gets a statement the server takes once, within five minutes of minting its `server_nonce`. It keeps the flight gate of the other identity commands: an activated unit refuses it `in_flight` while airborne, so the signature never runs on the main thread in flight. The refusals, in the order checked, are `in_flight`, `keyless` (no key, or no running version to report), `small_mtu` (the claim holder's link cannot carry `IdentityLink::kAttestationFrameBytes`, 102 bytes at the widest version, checked before anything is signed) and `invalid` (no `server_nonce` of 16 bytes). A Bravo has no key, so it answers `keyless`.

### Identity

`identity` asks any unit who it is and what it runs, and every product answers it with the same keys: the product, `go` or `bravo`, the variant, `plus` on a Go with the inclinometer, the buzzer and the haptic motor fitted and `standard` otherwise, the running version, whether the build is a release, the DEVICEID and the Bluetooth tag. They are the words `docs/ADSL_NMEA_PROPOSAL.md` gives a display in `$PDSLV`, so the link, the NMEA family and the server's records name a unit alike. The page asks on every connection and the server keeps the answer as the unit's record. Nothing is signed here: an activated unit vouches for the same product, variant and firmware in its attestation. `ConfigService::send_identity()` in `config_reports.cpp` answers it, beside the other reports, in flight too, since it changes nothing, and refuses it `no_version` only when the unit cannot read its running version. The variant is worked out at every boot from the parts the board's probes found, and stored nowhere, so a Plus whose haptic driver no longer answers its probe reads `standard` from that boot on.

## Trusted browsers

A browser the pilot approved once with a press, or the browser that installed the unit, changes the settings, starts an update, activates the unit and pairs it with no press after that. The link has no pairing and no bonding, and a phone connects from a new private address each time, so the browser proves a key it holds instead. `BrowserLink` in `browser_link.h` holds the session, `TrustedBrowsers` in `trusted_browsers.h` the list, and the handlers are `ConfigService` methods in `browser_link.cpp`.

- **The proof.** `browser_challenge` draws 16 bytes from the hardware RNG for the session that holds the claim. `trust_browser` carries the browser's raw Ed25519 public key, its signature over `skyblip:browser:v1` followed by that nonce, and a label of at most 24 bytes. The nonce is spent before the check, and a dropped link takes it. A key on the list makes the session trusted until its link drops or it asks `browser_challenge` again. Any other key is answered `untrusted` and held as the session's proven key.
- **Enrollment.** The next `set`, `dfu`, `register` or `pair` that a press confirms on that link stores the proven key with its label. The Go's confirm page says so under the detail, `TRUSTS BROWSER`, whenever `ConfigService::prompt_trusts_browser()` holds, so a page that is not ours cannot enroll a key unseen. Bravo has no glass, and our page says it beside the prompt it draws. A one-press refusal, an expiry, a take-off and any other confirmed prompt store nothing. The unit keeps eight keys, and a ninth replaces the one stored first.
- **What trust skips.** One rule covers every press a trusted browser skips: the command goes ahead at once, after every check the pressed command meets, and the press that would have confirmed it for an untrusted browser also trusts that browser. A trusted session's `set` is stored at once and answered with an acknowledgement with no reason, in flight too, because no prompt takes the glass from the radar. Its `dfu` opens the upload window at once and is answered `dfu`, still refused `in_flight` and `low_power` at the door: an install restarts the unit. The power rule, the version check, the signature on the image and the product check hold as for a pressed update. Its `register` is answered the registration frame at once, still refused `keyless`, `no_session`, `bad_signature`, `small_mtu` and, on an activated unit in flight, `in_flight` (Activation). Its `pair` starts the pairing at once and is answered `pair` (Pairing from a browser). `recovery`, `power_off`, `gnss_cold_start`, `capture` and the log `erase` still ask, trusted or not.
- **The list.** `browsers` asks for one entry by index and `browser` answers it: the first eight bytes of the key as `id`, and the label. `forget_browser` drops one by `id`. Both answer only a trusted session. A session that forgets its own key is trusted no more and enrolls nothing until it proves a key again. The page offers forgetting one browser and forgetting all the others (`server/app/javascript/skyblip/README.md`). Neither unit offers a gesture of its own to clear the list, and Bravo has no glass to show it, so the Briefing device page is where a pilot reads and clears it. A pilot who lost the trusted phone connects another browser, trusts it with one press on the unit, and forgets the others.
- **Where it lives.** The list is one NVS record, `browsers`, beside `settings` in the internal flash's `storage_partition`, which no `.uf2` and no update writes. A `.uf2` reaches it only through the install trust record below. It is a sealed blob (`core/settings/blob.h`), version 1, of 462 bytes. `ConfigLinkService` reads it at setup and writes it when an enrollment or a forget marks it dirty, placed by its own `DurableWriteWindow` and held on a cell the settings write rule refuses, as a settings change is. A blob that will not read leaves the list empty, so every browser asks for the press again.

What trust does not cover. A trusted key changes the settings in flight with nothing on the glass, the alarm and the aircraft address included, so a lost phone keeps that power until another trusted browser forgets it. The proof authenticates the start of a session, not each frame, so a radio able to inject frames into a live connection could ride a trusted session. The page cannot tell a skyBlip from a device that relays another unit's nonce to it, which is the active spoofing the peer link also leaves out of its threat model (The Go's link to its Bravo).

### The browser that installed the unit

Briefing installs a unit that runs Meshtastic over USB: it restarts the unit into the factory UF2 bootloader over Web Serial and writes the release `.uf2` to the `TECHOBOOT` or `X1` drive. Before it writes the file, it adds one record that names its own browser key, on a page of its own inside slot0. The unit then trusts that browser from its first boot, as if a press had enrolled it. `InstallTrust` in `install_trust.h` reads the record through `ports::Dfu`'s view of slot0, `read_running_slot()` and `erase_running_slot_page()`. `hardware/platform/zephyr/dfu.h` fills that view with `flash_area` on `slot0_partition`, and the host suite with a byte array.

The page is the first 4096-byte boundary at or after the end of the slot0 image. The image ends where MCUboot ends it (`boot_read_image_size`): at slot0's start, plus `ih_hdr_size`, `ih_img_size` and `ih_protect_tlv_size` of the image header at slot0's start, plus `it_tlv_tot` of the unprotected TLV info (magic 0x6907) that follows them. Every field is little-endian. slot0 starts at 0x34000 on the T-Echo, 0xB6000 bytes long, and at 0x35000 on the X1, 0xB5000 bytes long. The page must end before slot0's last sector, which holds MCUboot's trailer and which `scripts/mkuf2.py` blanks in every `.uf2`. An image that leaves no such page carries no record.

The record is 77 bytes at the start of the page, and the rest of the page is 0xFF:

| Offset | Bytes | Field |
|---|---|---|
| 0 | 16 | magic, ASCII `skyblip:trust:v1` |
| 16 | 32 | the browser's raw Ed25519 public key |
| 48 | 1 | the label's length, 0 to 24 |
| 49 | 24 | the label, UTF-8, padded with zero bytes |
| 73 | 4 | CRC-32 (IEEE 802.3, zlib's `crc32`) of bytes 0 to 72, little-endian |

The label follows the rules of `trust_browser`: at most 24 bytes of UTF-8, with no zero byte inside its length. `schemas/trust_record.v1.vectors.json` holds a record for a fixed key and label, the placement of one image on both boards, and a record with a wrong CRC. `test/core/test_install_trust.cpp` reads it, and the server's writer is tested against the same file.

`ConfigLinkService` reads the page at setup, after the trusted browsers. A record with a wrong magic, CRC, label length, label or padding is ignored silently, and the unit boots as it would with none. A valid record stores its key and label in `TrustedBrowsers` as an enrollment does, so a key already held is not added twice, and marks the list for writing. The `browsers` record is written through the same placed write as any enrollment. Only once that write has landed is the page erased, through a `DurableWriteWindow` of its own, because a page erase stalls the core as an NVS write does. A power cut between the two leaves the page, and the next boot adds the same key again, which changes nothing. A unit with no storage ignores the record. The erase keeps the settings write rule, so a cell below it keeps the page until the unit is charged.

The record gives nobody more than they already had. Over USB, the factory bootloader writes any byte of the application area, so a hand on the cable already has full control. Over the air, the record must never travel into slot0 with an update. MCUboot's swap using offset copies whole sectors up to the larger of the two images, and moves slot1's sector N+1 to slot0's sector N (`boot/bootutil/src/swap_offset.c`, `swap_run()` and `boot_swap_sectors()`, at the MCUboot that Zephyr v4.5.0 pins). Its skip test lets the first sector past the new image through. So when the running image is longer than the new one, slot0's first page past the new image, which is the trust page, receives slot1's sector past the new image's end. An SMP upload declared longer than its image could fill that sector with a forged record. `dfu::ProductCheck` therefore refuses an upload whose declared length is not exactly the end of its image, header, body, protected TLVs and TLV area. It refuses on the chunk that brings the TLV info, before img_mgmt writes any byte past the image (`../dfu/README.md`). Past the image, slot1 then holds only what a swap carried there from slot0: our own signed images, or a record the installing browser wrote itself. The one gap left is a sector an image built before this check took in an over-long upload, which needed an upload window a press opened, and which a later shorter image could still carry over.

## The log dialect

`log_link.h` is the log partition's half of the link: the same CBOR `config.h` speaks, on its own endpoint, with three commands, list, read and erase. Every reply fits one frame and carries the record index it starts at, which is what makes the transfer acknowledged by construction: the next command IS the acknowledgement, a host that lost chunks asks again from the index it kept, and a chunk that never left the device consumed nothing, so asking again is the whole recovery.

`parse_log_request()` is the boundary. A request it does not understand comes back with `understood` false and `reason` set to the code a service refuses with, so a refusal names what was wrong rather than answering something adjacent.

### Either store, named on both halves

`core/store` puts two rings on the partition and this dialect addresses either through an optional `log` key on any command: `flights`, `diagnostics`, or absent, which is flights. A code that is neither is refused as `unknown_log`; it is never quietly read as flights, because the two stores share a session id space and the wrong one would answer with a plausible flight. The selector is `store::SectorOwner` itself rather than a second enum beside it, so a store this dialect can name is a store the allocator owns. The same holds for the numbers a command carries: an `index`, a `session`, a `from` or a `count` that is not an unsigned integer is refused as `invalid`, never read as absent, which would have read a session from record 0 or a list as a bare count. So is a command carrying a key its frame does not list. A `read` without a `session` names nothing and is refused `unknown_command`.

The service side refuses by name for the same reason the parser does: a store this build has no writer for is `no_diagnostics` rather than `no_storage`, because a phone told the partition is missing would stop asking, and an erase aimed at a store that is recycled rather than erased is `flights_only`.

A reply names its store by the same rule: `log` is `diagnostics` on every diagnostics reply, absent for flights. Two fetches in flight on one link can then never misfile a chunk. The two bytes it costs are counted: the chunk envelope is sized to the byte at the widest session id and record index (18), and `log_records_per_chunk()` takes the store for that reason. At 182, 244 and 495 bytes both stores carry the same six, nine and nineteen records; at 164 bytes flights carry six and diagnostics five.

A chunk carries its records as one byte string, the 24 bytes of each as the flash holds them, CRC and all, so the host verifies each against the checksum the flash wrote. How many it carries is the string's length over 24, and `ends_session` says it is the session's last.

### A window of chunks

`read` with `session` S, `from` X and `count` K asks for K chunks back to back, `count` absent meaning one. One chunk per round trip was the throughput ceiling: a round trip on this link is 99 ms measured on the device, so a 288-byte chunk each time is about 2.9 kB/s, where notifications leave at a 498-byte frame per connection interval, roughly 16 kB/s. A full partition is seven minutes at the first rate and eighty seconds at the second.

K is clamped to `kMaxLogReadChunks`, 8, at the parse boundary. Eight notifications are eight connection intervals, about a quarter of a second at the interval those figures were measured at, which is as much of a second as an offload may take from the traffic picture the same link is broadcasting; eight chunks is also 152 records.

`plan_log_window()` holds the arithmetic, and the three ways a window goes wrong are what it is tested on: it cuts the window at the end of the session instead of wrapping into the next one, it yields no chunks at all for a `from` past the last record, and it sets `ends_session` on the chunk that ends the session and on no other. A window changes nothing about the acknowledgement model, since each chunk still carries its own index: a host that received three of eight asks again from the fourth.

### A record keeps its index while the ring rotates

A session's records are indexed from the sector it opened in, and an index names the same record for as long as the unit runs. Until 2026-11-17 the index counted from the oldest sector the session still held, so each sector the ring recycled under a session renumbered every record after it by 170. A fetch of a running capture then read one sector too far at every rotation, a hole the width of a sector between two indices that still looked continuous (#368), and a resume found another record at the index it had kept, or none (#367).

The allocator counts, per ring, the sectors it recycled from the front of a session (`store::SectorAllocator::recycled_sectors()`). A ring recycles only its oldest sector, so one session per ring loses its front at a time. A session's entry names the index of its first kept record as `first`, absent while it is 0, and `records` counts from there. A `read` below `first` is answered from `first`, and its chunk says so in `from`. The service checks that before every chunk, because a window goes out over several passes and the ring may recycle its front between two of them: the window then skips to `first` and keeps the chunks it had left.

The count lives in RAM. The sector label has no room for it, so a restart numbers what is left of a truncated session from 0 again, as builds before the count did. A host that resumes by index therefore reads its last kept record back before it trusts the index (`scripts/README.md`, Fetch a capture).

### A session still being written

`closed` is false for a session the power cut and for the one the unit is still writing, and the two read differently: the last record of a cut session may be torn, and the last record of a running one is whole. So the entry of the session the store is writing carries `recording`, true, between the store's `begin_session()` and `end_session()`, and every other entry leaves it out. `blip.py` and the console keep the last record of a `recording` session and print `recording` in place of `power cut`. The flag lives in RAM like the store's session, so a unit that restarts lists nothing as recording.
