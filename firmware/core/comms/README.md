# comms

The companion link, from the side that does not know what Bluetooth is. A platform fills `ports::Link`; everything here speaks endpoints, sessions and CBOR frames with numbered keys.

## The wire

Every frame on the config and log endpoints is one CBOR map (RFC 8949) in one write or one notification, in the grammar every reader of the link shares: unsigned keys in ascending order, each head in its shortest form with an argument of at most 32 bits, definite lengths, no floats, no tags, and nothing nested but an array of unsigned integers. Key 0 is `command` in every frame and its value is a code that says which frame it is, and so which key table the other numbers belong to. [`schemas/link.v1.json`](../../../schemas/link.v1.json) is the one place the numbers are written: every frame, its command code, and each key's name, number, type and description, with the names and codes of every enumerated value. A key that is an enumeration travels as its code, a nonce, a key, a signature or the raw records of a log chunk as a byte string, and only free text a person reads (a callsign, a version, a receiver's banner) as text. The link spoke JSON under the same names until the registry replaced it.

`scripts/link_registry.py` generates `link_registry.h` here (the command and reason codes as enums, one `<frame>_key` namespace of key numbers per frame, and a `<frame>_bytes` one of the fixed widths of its byte strings, which the code that writes and reads them takes rather than restating), `simulator/world/link_names.h` (the names, for the simulator and the suite), `test/core/test_link_mirrors.cpp` (which holds every enumeration the registry says mirrors a C++ enum to that enum at compile time, both ways: each code to its enumerator, and the enum to the registry through a switch `-Wswitch` refuses once the C++ enum gains a value the registry neither carries nor lists under `off_the_wire`) and `server/app/javascript/skyblip/link_registry.js`; `scripts/check_link_registry.py` fails CI when one of them is not what the registry produces. The device never carries a name: `core/util/cbor.h` writes and reads numbers, and the names live in the clients (`scripts/blip_frames.py`, the server's codec, `simulator/world/link_text.cpp`).

`cbor::Writer` refuses rather than truncates: an entry that will not fit whole, a key out of order, an integer past 32 bits or text that is not UTF-8 refuses the whole frame, `finish()` answers 0, and the sender counts a `link_drops` rather than send a frame with a key missing. `cbor::Reader` checks the whole frame before anything reads it, and refuses what the grammar does not allow: a non-shortest head, an argument past 32 bits, an indefinite length, a float, a tag, a nested map, an array holding anything but unsigned integers, text that is not UTF-8 (an overlong form, a surrogate or past U+10FFFF included), a key out of order or repeated, and a byte after the map. A frame it refuses has no command, so the config endpoint answers `no_command`. `schemas/link.v1.vectors.json` lists what the three readers, this one, `scripts/blip_frames.py` and the server's `link.js`, each refuse, and `test/core/test_cbor.cpp` reads it.

Reasons, the words a refusal or an acknowledgement names, are one enumeration for every frame, `link::Reason`.

## Three endpoints, two shapes of send

`events::Endpoint` splits the link in three because the three have different owners. NMEA is the traffic picture and it is broadcast: every subscribed central gets the same bytes, and `ports::Link::send()` reports Ok when one of them took it, so a phone whose controller buffers are full cannot end the pass for the tablet beside it. Config and Log are conversations, and they go out through `send_to()`, addressed to the session whose request they answer.

That is why `payload_bytes()` with no argument is the *smallest* payload any connected central negotiated. One NMEA frame is formatted once and goes to all of them, so it has to fit the narrowest. An iPhone at ATT_MTU 185 sitting beside an Android at 247 pulls every broadcast frame down to 182 bytes, and that is correct, not a compromise: the alternative is formatting the picture once per central. A conversation is sized for its own session instead, by `payload_bytes_to()`, so a central that never exchanged its MTU narrows the broadcast and no one else's replies.

That central is not hypothetical. A central starts the exchange when its stack or app decides to: iOS always does and usually settles on 185, Android only when the app calls `requestMtu()` (XCSoar asks for 256, and Android 14 turns any request into 517). So the unit asks too. Right after a connection, `connected()` in `hardware/platform/zephyr/link.cpp` sends its own Exchange MTU Request as GATT client of the phone (`CONFIG_BT_GATT_CLIENT`), which every central has to answer, so an Android app that never asks still settles past 23. Both requests may cross, which the specification allows: each side's client asks once, and both land at the smaller of the two MTUs. Zephyr's `CONFIG_BT_GATT_AUTO_UPDATE_MTU` would send the same request but only logs its outcome, so the unit sends it itself and records it (Measuring what links settle on). A link still at 23 is a central that answered 23 or refused, and the replies it cannot carry are answered `small_mtu`. Every ATT server has to answer the request; one that never did would lose its link to Zephyr's 30-second ATT transaction timeout, which disconnects.

## Sessions

`LinkSessions` is the table, and it is the same object on both platforms: Zephyr's `connected`/`disconnected`/`att_mtu_updated` callbacks drive it on silicon, `raise_link()`/`drop_link()` drive it in the host suite. It exists so the lifecycle rules are proved once by `make test` rather than living inside a Bluetooth callback nothing can reach.

`kMaxSessions` must never exceed `CONFIG_BT_MAX_CONN`. The controller is what actually admits a central; a table larger than the controller's is a table with rows that can never fill, and a table smaller than it means a central the radio accepted that the firmware refuses to serve. A refused connect is counted, not silently served: the bus never hears of that session, so no service answers its frames, and `refused()` is how a bench sees it happened.

Events are one ordered queue rather than a queue per type. A connection is a lifecycle, and an Up read before the Down that came first leaves a service pushing at a link that is gone.

## The claim

Broadcast is for everyone. Configuration is not: two apps writing settings to one device is two apps disagreeing about what is stored, and a prompt authorised on one phone answered on another is a confirmation with no presence behind it.

So `LinkClaim` grants config and log to the first session that writes a command, and holds it until that session disconnects or releases it. A command from any other session is refused with a reason naming the state, never accepted and quietly ignored. The claim is what makes a *dropped* link safe to act on: only the holder's disconnect cancels a pending prompt and closes an upload window, and before the claim existed any second EFB walking out of range did both.

What a claim is not is access control. `CONFIG_BT_SMP` is off on this product, deliberately (see `products/skyblip_go/prj.conf`), so there is no identity behind a session id. The claim stops two cooperating apps from stepping on each other. What stops a hostile one is the MCUboot signature on the image and the confirmation gesture on the device itself.

## The status reply

`status` is the one frame the device also sends without being asked: `set_flight_state` pushes it when the flight state changes, and `set_battery_state` on a charging flip, a level change or a five-percent step. The flight state is what every write is gated on, so a page that holds its buttons for the ground learns it landed without polling. So it carries what a pilot's screen shows and nothing a bench reads, and it has to fit `kSmallestSupportedPayloadBytes`, the 182 bytes an iPhone commonly settles at, with every field at its widest. The buffer is that limit: a field that does not fit refuses the frame, and `format_status` then counts a `link_drops`. At its widest the status is 20 bytes, so even the 20 bytes a central that never exchanged its MTU carries take every push.

What a support case reads lives where it is asked for. The address and the callsign are the config reply's. Why the device came up is `reset` in the diagnostics dump's system group, and whether the gauge is reading the cell is `battery_valid` in its power group, with `cell_mv` what the divider read when it is not: no divider, a refused reading, or the USB rail on the cable (`core/power/README.md`). One boot fact stays, `went_dark_flat`, because "the battery went flat" is the answer a pilot is owed for a unit that switched itself off (`core/power/README.md`). A key with no reading behind it is left out, never sent as a zero: `battery_percent` without a reading of the cell, which on the cable there never is, `die_temperature_c` without a fresh die reading.

`schemas/link.v1.json` numbers and describes the keys, and `scripts/check_link_registry.py` holds `format_status` to it: its keys, their order, their types and which keys may be absent. The widest frame is pinned byte for byte in `test/products/test_comms_report.cpp`.

## How wide the frames are

Every frame is measured at its widest. The status push is 20 bytes, the config reply 31, the update report 57 for a release build at the widest versions `scripts/build_image.sh` lets through, 9.99.99+99999, and 59 for a development build, which adds `downgrade`. The registration frame is 138, the challenge reply 27, an acknowledgement at most 11. The timing report is 147 at its widest and the widest diagnostics group, the radio's, 112, so on a 182-byte link each answers one frame per question and per subsystem; on a narrower one they split, never mixing two groups. `test/products/test_link_payload.cpp`, `test/products/test_comms_report.cpp` and `test/core/test_diagnostics.cpp` pin these; `scripts/test_blip_frames.py` pins the status byte for byte on the host side.

A log chunk's envelope is 18 bytes at its widest session id and record index, the records' byte string adds a head of two bytes up to ten records and three past it, and a diagnostics chunk names its store in two more. That leaves room for six records at 182 bytes, nine at 244 and nineteen at 495, for either store, and `kMaxLogRecordsPerChunk` is 19.

On the host side the widest writes are a `register`, 88 bytes, and an `unlock`, 74. Every other command, `set` with every key included at 28, fits the two 18-byte prepare segments a link that never exchanged its MTU reassembles.

## A reply too wide for its link

A reply that is whole but wider than the payload of the session that asked is never handed down, and never left unanswered: the sender counts a `link_drops` and answers `small_mtu` instead, an acknowledgement of 8 bytes on the config endpoint and 8 or 10 on the log endpoint, where it names its store like every log reply, so it reaches a link that never exchanged its MTU. Each endpoint does it in the one place its replies leave, `ConfigService::reply_to()` and `RecordPool::send()`, so no frame carries a check of its own. Three refusals come before any frame exists and are not counted as drops: a timing or diagnostics report whose fields cannot be split into frames this narrow, a `register` whose registration frame the link could not carry, and a `read` whose chunk could not hold one record (the log dialect's `payload` reason, folded into this one). At 20 bytes that is the config reply past serial 23 or with a callsign, the challenge reply, an asked `update` frame with versions or a digest, the timing report, every chunk, and a session entry once it holds 256 records.

A frame nobody asked for is not refused, because the refusal would be noise. The `status` push fits every link. The `update` frame a connection is pushed leaves on its first `Up`, before most centrals have exchanged their MTU, and the late exchange's second `Up` pushes it again: a refusal on the first would tell a page its phone is too narrow a moment before the frame arrives. A push that does not fit is counted in `link_drops` and dropped, as it always was.

## Measuring what links settle on

Each connection leaves one `Link` `down` record in a `Full` capture, which carries two fields: `payload_bytes`, the payload the link settled on, and `mtu_exchange_started_by`, which side started the ATT MTU exchange. `central` is the phone, or a link that came up past 20 bytes. `unit` is the request `link.cpp` sends at connect, answered. `both` is the two requests crossing, and `none` is a link where no exchange landed and that ran at 20 bytes. `LinkSessions` works it out at the `Down`: Zephyr calls `att_mtu_updated` for every exchange, the unit's own included, just before the unit's response callback, so an update the unit's answered request does not account for is the central's. On the bench, arm a `Full` capture on the CAPTURE page, connect each phone, browser and app a few times, fetch with `./scripts/blip.py fetch --log diagnostics --all --out capture.ndjson`, and read the `action=down` lines of `./scripts/blip.py decode capture.ndjson --type link`, one per connection. Splitting replies across notifications is worth building once a supported phone or browser ends at 20 bytes on two runs out of two, which is a pilot who cannot activate or update from it.

## Activation

`challenge`, `register` and `unlock` travel on the config endpoint like every other command, and live apart from it: `IdentityLink` in `identity_link.h` holds the session, and the three handlers are `ConfigService` methods defined beside it in `identity_link.cpp`. `schemas/link.v1.json` describes the frames, `schemas/activation.v1.schema.json` what the browser relays to the server and what each signature covers, and `core/identity/README.md` the messages they sign.

`challenge` draws Nu, 16 bytes from the hardware RNG, for the session that holds the claim, and answers it with `server_key_id`, the id of the server key this build trusts, in a frame of fixed width, `IdentityLink::kChallengeFrameBytes` (27), that is dropped and counted in `link_drops` rather than sent short should its buffer ever overflow. The nonce is single-use and dies when `unlock` spends it, when the claim holder's link drops, or at `IdentityLink::kNonceForgetMs`, ten minutes: `live()` takes the session and the time, so a command on the pass that reaches the deadline already finds it dead, and the tick closes it once past, so it stays dead when `milliseconds()` wraps back into the old window 2^32 ms later. A new `challenge` replaces it. `register` verifies the server's R over Nu and Ns, then stands `Pending::Register` on the glass under `confirm_register`, and two presses answer the registration frame, signed by the unit's key, which says after `server_key_id` whether the build is a release. `unlock` verifies U over the unit's own DEVICEID, its current key, the serial and Nu, and refuses serial 0, which would put 0x000000 on the air. The nonce is spent before the check, so a refused code is never retried on it. The code is written and read back before the acknowledgement naming `unlock` goes out. On an unactivated unit the radio is off and the page is written at once; on an activated one the radio runs, so the verified code waits in `IdentityLink` and the product places the write as it places a settings write, through a `timing::DurableWriteWindow` of its own, outside a dwell, and answers then (`products/skyblip_go/services/config_link.cpp`). The power rule is asked again at the moment of writing: a cell that fell through it, or a supply warning, while the code waited drops the code with `low_power`, never a forced write. A held code belongs to the session that sent it and dies with that link, so its answer can never reach another app.

On an unactivated unit none of it is gated on the ground. Every other prompt is refused unless the flight state is positively `Ground`, and `Unknown`, a unit with no fix since boot, is not: activation on a bench indoors would always fail. A unit with no serial transmits nothing, so the gate would protect nothing, and its `Pending::Register` confirms, and survives a take-off, whatever the flight state. An activated unit transmits, so it owes the gate like every other command: `challenge`, `register` and `unlock` are refused `in_flight` unless it is on the ground, and its register prompt is cancelled at take-off. One press still cancels a prompt, thirty seconds still expire it, and a dropped link still takes it.

Every identity refusal but `small_mtu` is written in `identity_link.cpp` as `refuse(link::Reason::Word)`, and none as `acknowledge(false, ...)` in `config.cpp`, so the server's activation page can grep its rows apart from the update page's. `small_mtu` is `refuse_too_wide()`, the refusal every reply shares, which `config.cpp` writes, so both pages word it:

| Word | When |
|---|---|
| `keyless` | the unit has no key, drew no nonce, or cannot read its own version: it cannot be activated as it is. A unit short of a required part never gets this far, because it runs no service and advertises nothing |
| `in_flight` | an activated unit off the ground |
| `low_power` | an `unlock` while the cell is below the settings write rule (`core/power/cutoff.h`): the nonce stays live for a retry on the charger |
| `no_session` | no live nonce for this claim holder: no `challenge`, a spent nonce, a dropped link, ten minutes, or a `challenge` since the registration was staged |
| `bad_signature` | R or U does not verify with the trusted key, or the field is not a byte string of the width the registry pins |
| `small_mtu` | the claim holder's link cannot carry the registration frame, `IdentityLink::kRegistrationFrameBytes` (138) at the widest version, in one notification: an iPhone's 182 bytes carry it. The challenge reply, 27 bytes, is answered the same way by any link narrower than it (A reply too wide for its link) |
| `flash` | the identity page did not take the code, or did not read it back |

`cancelled` and `expired` come from the prompt machinery every command shares, `claimed` and `unknown_command` from the dispatch. A product that hands `ConfigService` no `IdentityLink` answers all three commands `unknown_command`.

## The log dialect

`log_link.h` is the log partition's half of the link: the same CBOR `config.h` speaks, on its own endpoint, with three commands, list, read and erase. Every reply fits one frame and carries the record index it starts at, which is what makes the transfer acknowledged by construction: the next command IS the acknowledgement, a host that lost chunks asks again from the index it kept, and a chunk that never left the device consumed nothing, so asking again is the whole recovery.

`parse_log_request()` is the boundary. A request it does not understand comes back with `understood` false and `reason` set to the code a service refuses with, so a refusal names what was wrong rather than answering something adjacent.

### Either store, named on both halves

`core/store` puts two rings on the partition and this dialect addresses either through an optional `log` key on any command: `flights`, `diagnostics`, or absent, which is flights. A code that is neither is refused as `unknown_log`; it is never quietly read as flights, because the two stores share a session id space and the wrong one would answer with a plausible flight. The selector is `store::SectorOwner` itself rather than a second enum beside it, so a store this dialect can name is a store the allocator owns. The same holds for the numbers a command carries: an `index`, a `session`, a `from` or a `count` that is not an unsigned integer is refused as `invalid`, never read as absent, which would have read a session from record 0 or a list as a bare count.

The service side refuses by name for the same reason the parser does: a store this build has no writer for is `no_diagnostics` rather than `no_storage`, because a phone told the partition is missing would stop asking, and an erase aimed at a store that is recycled rather than erased is `flights_only`.

A reply names its store by the same rule: `log` is `diagnostics` on every diagnostics reply, absent for flights. Two fetches in flight on one link can then never misfile a chunk. The two bytes it costs are counted: the chunk envelope is sized to the byte at the widest session id and record index (18), and `log_records_per_chunk()` takes the store for that reason. At 182, 244 and 495 bytes both stores carry the same six, nine and nineteen records; at 164 bytes flights carry six and diagnostics five.

A chunk carries its records as one byte string, the 24 bytes of each as the flash holds them, CRC and all, so the host verifies each against the checksum the flash wrote. How many it carries is the string's length over 24, and `ends_session` says it is the session's last.

### A window of chunks

`read` with `session` S, `from` X and `count` K asks for K chunks back to back, `count` absent meaning one. One chunk per round trip was the throughput ceiling: a round trip on this link is 99 ms measured on the device, so a 288-byte chunk each time is about 2.9 kB/s, where notifications leave at a 498-byte frame per connection interval, roughly 16 kB/s. A full partition is seven minutes at the first rate and eighty seconds at the second.

K is clamped to `kMaxLogReadChunks`, 8, at the parse boundary. Eight notifications are eight connection intervals, about a quarter of a second at the interval those figures were measured at, which is as much of a second as an offload may take from the traffic picture the same link is broadcasting; eight chunks is also 152 records.

`plan_log_window()` holds the arithmetic, and the three ways a window goes wrong are what it is tested on: it cuts the window at the end of the session instead of wrapping into the next one, it yields no chunks at all for a `from` past the last record, and it sets `ends_session` on the chunk that ends the session and on no other. A window changes nothing about the acknowledgement model, since each chunk still carries its own index: a host that received three of eight asks again from the fourth.
