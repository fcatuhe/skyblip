# the Bluetooth link

What `link.cpp` puts on the air, and why those UUIDs.

## Three services, because an EFB and our own app want different things

| Service | Characteristics | Who reads it |
|---|---|---|
| Nordic UART `6E400001-B5A3-F393-E0A9-E50E24DCCA9E` | `...0002` written by the app, `...0003` notified by us | XCSoar, Enroute Flight Navigation, LK8000 since 7.6.8, anything SoftRF-shaped |
| HM-10 `FFE0` | `FFE1`, notify and write on one characteristic | SkyDemon, LK8000 before 7.6.8, Enroute on a device without Nordic UART, and the profile PowerFLARM Fusion and Flex ship |
| skyBlip `69C21301-0187-4204-A91D-02EB8858B440` | `...02` config, `...03` flight log, each write and notify, and `...04` peer, written by a paired Go and notified by Bravo, which only a product that sets `CONFIG_SKYBLIP_PEER_SERVER` serves, Bravo (#192) | our own configuration page, and a paired Go (`core/comms/README.md`, The peer endpoint) |

The NMEA stream goes out on both public profiles at once, which is what SoftRF does (`src/platform/bluetooth/Bluefruit.cpp`, `bleuart_HM10` beside `bleuart_NUS`). The two conventions split the market: the open-source soaring stack prefers Nordic UART and XCSoar checks it first, while FLARM chose `FFE0`/`FFE1` for Fusion and Flex, their only Bluetooth interface since Hub 1.80, and its Hub EFB guide lists SkyDemon among the apps that read it (FTD-115 v1.02). Offering both costs one service definition and covers every client we know of.

The EFB chooses the service, not the firmware. Each app looks up the UUID it knows, whatever its place in the GATT table: XCSoar and Enroute try Nordic UART first, and Enroute falls back to `FFE0` only when a device has no Nordic UART (`TrafficDataSource_BluetoothLowEnergy.cpp` at enroute `8e5bc1b`). LK8000 from 7.6.8 subscribes to every UART characteristic it knows (`BluetoothGattClientPort.configureCharacteristics()`). `notify_one()` sends each frame on one service per connection, Nordic UART when the connection subscribed to it, so a client subscribed to both gets each frame once.

Nordic's roles are not ours to reinterpret. `6E400002` is what the central writes and `6E400003` is what the peripheral notifies, and XCSoar refuses a service missing either (`android/src/BleSerialPort.java`). So `...0002` exists, accepts writes and drops them: nothing in this firmware reads an inbound NMEA sentence yet. Config and the log are on our own base, from `uuidgen`, because they are our protocol and a UART pipe is what three apps would read them as.

Before September 2026 the config and log characteristics sat on `6E400002` and `6E400003` themselves. That was the Nordic base with the roles inverted: an EFB that knew the convention would have subscribed to our config characteristic and waited for `$PFLAA` that was never coming.

## What is advertised

The advertisement is full: flags, the 128-bit Nordic UART UUID, the 16-bit `FFE0`. That is 25 of 31 bytes, and it is not optional padding. XCSoar builds its LE scan filters from service UUIDs (`android/src/BluetoothHelper.java`), so a device advertising only a name never appears in its list.

The name therefore rides the scan response, where 29 characters fit, and the product decides it (`core/identity/README.md`). Before activation it is `activate 3F2A skyBlip`, 21 characters, where `3F2A` is the low 16 bits of FICR `DEVICEADDR`, the address Zephyr advertises with, and the glass shows the same four digits. After it is `skyBlip Go 00012A` or `skyBlip Go+ 00012A`, the unit's own address, which is the one the self-test page shows, so the entry in a phone's list matches the glass. It stays the unit's own while the unit transmits an own ICAO in its place (`core/settings/README.md`). A Bravo is never activated and is always `skyBlip Bravo 3F2A`, from the same tag (`products/skyblip_bravo/README.md`). The Nordic UART UUID is advertised either way, which is what our activation page's chooser filters on.

`begin()` only enables Bluetooth. Advertising starts on the first `advertise_as()`, which the product calls once it has verified the stored unlock code, so no phone ever sees a name that is about to change. A later `advertise_as()`, after an unlock, renames the unit live: `bt_set_name()` for the GAP characteristic, `bt_le_adv_update_data()` for the scan response, no reboot. The scan response is double-buffered and swapped whole through an atomic pointer, because the loop renames while the host thread may be restarting advertising after a connection.

## The unit's identity

`identity.{h,cpp}` fills `ports::Identity`: the DEVICEID through hwinfo, the tag, the key in UICR `CUSTOMER`, the unlock code in `identity_partition` at 0xEA000, and nonces from the RNG behind `zephyr,entropy`. The tag is the low 16 bits of FICR `DEVICEADDR`, read by `bluetooth_tag.h` apart from the rest, because it names a unit on the air whether or not the unit is activated: Bravo has the tag and no key. `TEchoPlus::begin()` (`t_echo_plus.h`) provisions the key before it enables Bluetooth. `MeshtrackerX1` (`meshtracker_x1.h`) holds no `Identity` and provisions none: it fills the role with `ports::KeylessIdentity` and the tag. `identity.cpp` is built only for a product that sets `CONFIG_SKYBLIP_ACTIVATION`. The UICR write is NVMC word writes through the nRF HAL, read back as memory before it is trusted, and `CONFIG_SOC_FLASH_NRF_UICR` stays off, so no flash driver call can ever reach UICR, let alone erase it. Which slot holds the key is `core/identity/key_slots.cpp`'s to decide. The server key the build trusts is compiled in from `skyblip_server_key.inc`, which `cmake/skyblip.cmake` generates from `firmware/keys/server.pub`.

## Several centrals

`CONFIG_BT_MAX_CONN` is 3 and `comms::LinkSessions::kMaxSessions` equals it, with a `static_assert` here so the two cannot drift: every connection a phone can take is a row in the table, and a reserved Bravo still finds a free connection object. A session id is `bt_conn_index() + 1`, the controller's own slot, so ids never collide and never outlive the connection.

`link.cpp` serves phones only, the connections where the unit is the peripheral. A connection where the Go is the central, its link to a paired Bravo, is `central.cpp`'s: `connected()` here skips it by its role, from `bt_conn_get_info()`, and `disconnected()` and the MTU callback skip it because it never entered `g_connections`, so it never enters `LinkSessions`, never gets the unit's MTU request, never takes a share of the NMEA broadcast, and a write it makes to a characteristic here is refused `WRITE_NOT_PERMITTED`. While a Bravo is paired, `reserve_peer_connection(true)` lowers the phone ceiling to two: advertising stops at two phones, even while Bravo is away, and a third phone that connects in the instant before it stops is disconnected with `REMOTE_LOW_RESOURCES` and never reaches the bus. On Bravo its Go connects here as a central, so `connected()` hands `LinkSessions` the address `bt_conn_get_dst()` gives, and `reserve_peer_connection_for()` keeps the slot for that address: advertising goes on while the Go is away, and a third phone is disconnected the same way. A peer write reaches the bus as an `RxFrame` on `Endpoint::Peer`, and `central_of()` names its sender's address under the same lock.

## The Go's central

`central.cpp` is built only where `CONFIG_BT_CENTRAL` is set, which is the Go's `prj.conf` (`cmake/skyblip.cmake`). It fills `ports::Central`:

- a scan is active, because the name rides the scan response, with duplicates filtered, and reports only an advertiser whose complete name starts with the prefix the product passes, `skyBlip Bravo `, so a hangar full of phones cannot fill the event queue ahead of a Bravo that the duplicate filter then never reports again;
- a connection is `bt_conn_le_create()` to the pinned address, its type included, with the initiator listening at the duty the product passes and Zephyr's 3-second create timeout (`CONFIG_BT_CREATE_CONN_TIMEOUT`), after which the product asks again;
- once connected the Go asks for the MTU as GATT client, discovers the peer characteristic, `...04`, and subscribes to it with `CONFIG_BT_GATT_AUTO_DISCOVER_CCC`. The link is `Up` only then, with the payload it settled on, so the product can refuse one below 126 bytes before writing anything;
- `peer_claim` goes out as a write without response, refused when wider than the payload. The service loop never makes the write itself: off the system work queue, `bt_att_create_pdu()` waits forever for a buffer (`subsys/bluetooth/host/att.c:794-815` at v4.4.2), so `write()` takes the connection and the characteristic's handle under the lock that clears them, copies the frame, and submits it to the system work queue, where an empty pool answers `-ENOMEM` at once. One write is in flight at a time, `kCentralWritesInFlight`, and the next answers `WouldBlock` until its sent callback lands; a write the work queue could not send is counted in `writes_refused()`;
- a notification goes onto its own queue of eight frames, and one the queue cannot take or longer than an `RxFrame` is counted in `dropped()`, with an event the event queue could not take. `dropped()` and `writes_refused()` are logged, `bluetooth: Bravo's link dropped ... and refused ... since boot`, at most every 10 seconds and only when one of them moved.

The ATT pool is sized for it in `att_budget.h`: `CONFIG_BT_ATT_TX_COUNT`, 18, holds three phones' shares of six, four notifications, a response and an SMP reply, and holds a paired Go's two phones and Bravo's three, one write, one request and one response. So a Bravo that stops taking frames, with two phones connected, costs the phones nothing: its one write stays in flight, the `peer_claim` after it is refused `WouldBlock` and counted in `writes_refused()`, the loop never waits, and the supervision timeout of `BT_LE_CONN_PARAM_DEFAULT`, 4 s, ends the link, after which the Go reconnects. Zephyr drops the sent callbacks of a link that is gone, so each new link starts its write count at zero, and a callback from an older link is told apart by a generation number and ignored. A write the work queue fails, `-ENOTCONN` from a link that went while it waited included, gives its count back whatever link it belonged to, because that count is the work item's own.

`connect()` creates the connection into a local and publishes it under the lock that the callbacks release it under, and each callback releases only the connection it is given, if the lock still holds it. A create that fails before it is published is found disconnected once published, and released there, so its reference is dropped once either way.

No SMP and no bonding, on this link as on the phones', so the Windows Web Bluetooth update path keeps working. The address is pinned on both sides instead (`core/comms/README.md`, The Go's link to its Bravo).

Subscription state is not held here. `bt_gatt_is_subscribed()` is per connection and already correct; the three booleans this file used to keep were one device's worth of state for what is now three centrals.

Advertising stops the instant a connection is created, and Zephyr 4.4 does not resume it. Both `connected()` and `recycled()` start it again: the first picks up the next free connection object, the second is the stack saying one has been freed. `-ENOMEM` from either is normal and means every object is in use.
